## 一、数据结构与算法

### 1. 总体知识讲解

#### 1.1 时间与空间复杂度：分析增长，不是测秒数

设输入规模为 `n`。时间复杂度描述主要操作次数随 `n` 增大的趋势，空间复杂度描述所需空间的增长。本节谈空间时默认指**辅助空间**，不计输入本身，递归调用栈计入。

常用增长顺序为：`O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2ⁿ)`。大 O 是渐近上界，不是精确次数；把 `3n + 10` 写为 `O(n)`，不意味着每次恰好执行 `n` 步，也不保证小输入时一定比另一实现更快。

- 顺序执行：相加后保留增长最快项，例如先扫描 `n` 次再做 `n²` 次，整体为 `O(n²)`。
- 嵌套循环：按实际执行次数求和，不能见到两层就断言 `O(n²)`。内层每次翻倍时只有约 `log₂ n` 轮。
- 递归：同时考虑每层工作和层数。二分查找每次把规模减半，所以为 `O(log n)`；递归版本还用 `O(log n)` 调用栈。
- **最好、平均、最坏、均摊**是不同问题。动态数组一次扩容可能搬动 `n` 个元素，但一串尾部追加的均摊成本可为 `O(1)`；均摊不等于“这一次最坏也是常数”。

举例：扫描数组找最大值必须看完各元素，时间 `O(n)`；只保存一个当前最大值，辅助空间 `O(1)`。复杂度分析的基本规则与常见算法表可对照 [Princeton《Algorithms》作者资料](https://algs4.cs.princeton.edu/cheatsheet/)。

#### 1.2 数组、链表、栈、队列与哈希表

数组把元素按顺序放在连续的存储区域；知道下标就能算出位置。链表把节点用指针连接起来，节点未必连续，访问第 `k` 个节点往往需要从头走过去。

| 结构或操作 | 典型成本 | 为什么 / 限制 |
|---|---|---|
| 数组按下标访问 | `O(1)` | 地址可直接计算；不是按值查找 |
| 无序数组按值查找 | `O(n)` | 最坏要逐个比较 |
| 数组中间插入、删除 | `O(n)` | 需要移动后面的元素 |
| 链表按下标访问、按值查找 | `O(n)` | 沿指针逐个走 |
| 已知前驱节点，在单链表中插入/删除其后节点 | `O(1)` | 只修改少量指针；寻找前驱的时间另算 |
| 栈的入栈、出栈 | 合适实现下 `O(1)` 或均摊 `O(1)` | 操作同一端；可用链表或动态数组 |
| 队列的入队、出队 | 合适实现下 `O(1)` 或均摊 `O(1)` | 用循环数组或链表；数组每次删除首元素可能为 `O(n)` |

栈是**后进先出 LIFO**，像一摞盘子：最后压入的最先取出，适合括号匹配、函数调用、撤销操作。队列是**先进先出 FIFO**，像排队办理业务：最早进入的最先处理，适合任务缓冲和层序遍历。这里讲的是普通栈、普通队列；优先队列按优先级取元素，不是 FIFO。结构定义可对照 [Princeton 栈与队列](https://algs4.cs.princeton.edu/13stacks/)。

哈希表先用哈希函数把键映射到桶，再在桶内确认键是否相等。哈希冲突是**不同键落到同一位置**，不意味着两个键相同。负载因子过大或冲突严重，会增加查找工作；扩容会重新组织元素。

在哈希函数分布合理、负载受控且键的哈希/比较成本视为常数的常用模型下，查找的平均成本为 `O(1)`。普通冲突处理模型最坏可退化到 `O(n)`，所以不能写“所有哈希表永远是 `O(1)`”；有些实现会用平衡树等结构优化冲突桶，具体结论需看实现。哈希表也不天然提供按键大小排序。哈希分布与负载的模型见 [Princeton 哈希表讲解](https://algs4.cs.princeton.edu/34hash/)；CPython 容器的具体成本可对照 [Python Wiki：容器复杂度](https://wiki.python.org/moin/TimeComplexity)。

#### 1.3 二分查找：先定义区间，再更新边界

二分查找需要序列按目标比较规则有序；它利用中点把候选范围缩小一半。普通数组支持常数时间访问中点，所以二分查找是 `O(log n)`；直接在普通链表上定位中点会有额外遍历成本。

“找某个值”和“找第一个满足条件的位置”不是同一个问题。有重复值时，遇到相等就返回可能得到中间那个，而不是第一个。下面固定使用左闭右开区间 `[left, right)`，寻找**第一个大于或等于 `target` 的位置**：

```python
def lower_bound(a, target):
    left, right = 0, len(a)
    while left < right:
        mid = left + (right - left) // 2
        if a[mid] < target:
            left = mid + 1
        else:
            right = mid
    return left
```

关键是维持含义：`left` 左侧都小于目标，`right` 及其右侧都大于或等于目标。循环结束时二者相等，就是分界点；返回值可能等于 `len(a)`，表示没有元素满足条件。若要判断目标是否存在，还要检查 `pos < len(a)` 且 `a[pos] == target`。

右边界查找则找“第一个严格大于目标的位置”；目标出现次数可由 `upper_bound - lower_bound` 得到。左闭右开模板中的 `right = mid` 不要和闭区间 `[left, right]` 模板中的 `right = mid - 1` 混用。可对照 [Python `bisect_left` / `bisect_right` 官方定义](https://docs.python.org/3/library/bisect.html)。

#### 1.4 排序：稳定性与复杂度是两条独立维度

**稳定排序**是指比较键相等的元素，排序后仍保持原来的相对次序。例如原序列是 `(80, 张三), (70, 李四), (80, 王五)`，只按分数升序，稳定排序后张三仍在王五前面。稳定不等于速度快，也不等于只能排一次。

下表限定常规数组版本、比较排序及通常的实现方式；具体变体可能改变稳定性或空间成本。

| 算法 | 基本思路 | 平均 / 最坏时间 | 通常稳定？ | 典型辅助空间 |
|---|---|---|---|---|
| 冒泡 | 相邻逆序元素交换，多轮把大元素推后 | `O(n²)` / `O(n²)` | 是，前提是相等不交换 | `O(1)` |
| 插入 | 把新元素插入已排序前缀 | `O(n²)` / `O(n²)` | 是，前提是相等不越过 | `O(1)` |
| 选择 | 每轮选最小值，交换到前方 | `O(n²)` / `O(n²)` | 通常否，远距离交换会跨过相等元素 | `O(1)` |
| 归并 | 分开排序，再合并有序段 | `O(n log n)` / `O(n log n)` | 是，合并时相等优先取左段 | 数组版本 `O(n)` |
| 快速 | 选基准，划分后递归处理两侧 | 期望/平均 `O(n log n)`，最坏 `O(n²)` | 通常否 | 常规递归版本平均 `O(log n)`、最坏 `O(n)` 栈空间 |
| 堆 | 利用堆反复取出最大值或最小值 | `O(n log n)` / `O(n log n)` | 通常否 | 原地数组版本 `O(1)` |

补充两点：插入排序在已经有序时可为 `O(n)`；带“本轮无交换则停止”的冒泡排序最好也可为 `O(n)`。快速排序在每次划分极度不均衡时可能退化；随机选基准提供的是期望性能改善，不是消除理论最坏情况。以上排序属性可核对 [Princeton 排序算法对照表](https://algs4.cs.princeton.edu/cheatsheet/)。

#### 1.5 树、BFS 与 DFS：画出访问顺序

树是连通且无环的结构。二叉树每个节点最多有两个孩子；二叉搜索树另外要求按键值满足左右子树的大小规则，二者不能混用。

**BFS（广度优先）**先访问根，再依次访问下一层，通常用队列。**DFS（深度优先）**沿一条分支往下走，再回溯，通常用递归或显式栈。二叉树 DFS 的常用次序如下：

- 前序：根 → 左 → 右。
- 中序：左 → 根 → 右；满足搜索树规则时，中序结果才按键有序。
- 后序：左 → 右 → 根；适合先处理孩子再处理父节点。

对含 `n` 个节点的树，完整 BFS / DFS 都访问每个节点一次，时间为 `O(n)`。BFS 队列空间与最大层宽相关；递归 DFS 栈空间与树高相关，极度偏斜的树可达到 `O(n)`。图上遍历还要记录已访问节点，避免环导致重复访问；无权图的 BFS 可求最少边数路径，普通 DFS 不保证这一点。遍历原则可对照 [Princeton 图遍历讲解](https://algs4.cs.princeton.edu/41graph/)。

### 2. 原创练习与逐题讲解（5 题）

#### FND-01｜循环复杂度（计算题）

题目：`n ≥ 2`，下面代码的时间复杂度和辅助空间复杂度分别是什么？`count += 1` 按常数时间计算。

```python
count = 0
for i in range(n):
    j = 1
    while j < n:
        count += 1
        j *= 2
```

**答案：时间 `O(n log n)`，辅助空间 `O(1)`。**

逐步推理：

1. 外层执行 `n` 次。
2. 每轮内层的 `j` 为 `1, 2, 4, 8, ...`，不是依次加 1；执行次数为 `⌈log₂ n⌉`。
3. 总执行次数为 `n × ⌈log₂ n⌉`。例如 `n = 8`，每轮内层 3 次，合计 24 次。
4. 只使用 `count、i、j` 等固定数量变量，没有随 `n` 增长的容器，辅助空间为常数。

易错点：把“两层循环”直接记成平方复杂度；把数值变大当成“多用了 `n` 个存储单元”。这里按笔试常用单位成本模型分析整数操作。

知识关联：1.1 复杂度、循环次数、单位成本模型。

#### FND-02｜数组、链表与哈希（多选题）

题目：在常规数据结构模型下，哪些说法正确？

- A. 数组按合法下标访问通常为 `O(1)`，但按值查找无序数组最坏为 `O(n)`。
- B. 在单链表的第 `k` 个位置插入元素，无论是否已知前驱，都为 `O(1)`。
- C. 分布合理且负载受控的哈希表，查找平均可为 `O(1)`；普通冲突模型最坏可能退化到 `O(n)`。
- D. 任何哈希表遍历都必然按照键从小到大的次序输出。

**答案：A、C。**

逐项辨析：

- A 正确：下标是位置，值是内容。能够直接算地址，不代表知道目标值在哪里。
- B 错误：已知前驱后改指针是 `O(1)`；从表头找到第 `k` 个位置的前驱通常还要 `O(k)`，最坏 `O(n)`。
- C 正确：结论带有哈希分布与负载前提。若所有键碰撞到同一桶，可能需要逐个比较。
- D 错误：哈希定位与大小排序没有必然关系。某语言字典保持插入次序，也不等于按键排序。

易错点：把“修改结构的成本”和“找到修改位置的成本”合在一起时漏掉后者；把某个语言实现的特性扩大成所有数据结构的定义。

知识关联：1.2 数据结构选择、平均与最坏成本。

#### FND-03｜重复元素的二分边界（追踪题）

题目：对 `a = [2, 4, 4, 4, 9, 12]` 执行 1.3 的 `lower_bound(a, 4)`。写出每轮的 `left、right、mid`，并说明返回值。下标从 0 开始。

**答案：返回 1，即第一个 4 的下标。**

| 轮次 | 比较前 left | 比较前 right | mid | 比较 | 更新 |
|---|---:|---:|---:|---|---|
| 1 | 0 | 6 | 3 | `a[3] = 4 ≥ 4` | `right = 3` |
| 2 | 0 | 3 | 1 | `a[1] = 4 ≥ 4` | `right = 1` |
| 3 | 0 | 1 | 0 | `a[0] = 2 < 4` | `left = 1` |

最后 `left == right == 1`，循环停止。第一轮遇到相等仍缩小右边界，是因为更早的位置可能也有 4。若改查 `13`，应返回 6；6 是合法的插入位置，但不是可读取的数组下标。

易错点：第一次遇到相等就返回，得到下标 3；初始化 `right = len(a)` 后又使用 `while left <= right`，可能读到不存在的 `a[len(a)]`。

知识关联：1.3 左闭右开区间、重复值、越界判断。

#### FND-04｜排序稳定性（多选题）

题目：按 1.4 表中的常规实现，哪些说法正确？

- A. 快速排序的最坏时间复杂度一定为 `O(n log n)`。
- B. 稳定排序要求比较键相等的元素保持原来的相对次序。
- C. 堆排序因为总能取到当前最大元素，所以必然稳定。
- D. 常规归并排序可同时具备稳定性和最坏 `O(n log n)` 的时间界。

**答案：B、D。**

逐项辨析：

- A 错误：若划分反复产生长度为 0 与 `n-1` 的两段，总工作量类似 `n + (n-1) + ... + 1`，为 `O(n²)`。
- B 正确：关注的是“相等键之间的次序”。不同键按排序规则重新排列不影响稳定性的定义。
- C 错误：堆调整及首尾交换可能改变相等元素的相对位置。能取最大值说明排序正确，不说明稳定。
- D 正确：归并时相等优先取左段，就能保持原有次序；分治约有 `log n` 层，各层总合并成本为 `O(n)`。

易错点：把“能正确排序”“运行快”“稳定”看成同一属性；忘记稳定性依赖实现如何处理相等元素。

知识关联：1.4 排序性质、分治、最坏情况。

#### FND-05｜栈、队列与树遍历（追踪题）

题目分两部分：

1. 初始为空。对栈依次执行 `push(A), push(B), pop(), push(C), pop(), pop()`；对普通队列执行 `enqueue(A), enqueue(B), dequeue(), enqueue(C), dequeue(), dequeue()`。分别写出被取出的次序。
2. 下列二叉树按从左到右的孩子顺序访问，分别写出 BFS 与前序 DFS 的结果。

```text
        1
       / \
      2   3
     / \   \
    4   5   6
```

**答案：栈取出 `B、C、A`；队列取出 `A、B、C`；BFS 为 `1、2、3、4、5、6`；前序 DFS 为 `1、2、4、5、3、6`。**

逐步推理：

- 栈：压入 A、B 后 B 在顶端，先取 B；压入 C 后先取 C，最后取 A。
- 队列：A 比 B 先进入，先取 A；C 加在 B 后面，因此随后依次取 B、C。
- BFS：队列先放 1；取 1 后放 2、3；取 2 后放 4、5；取 3 后放 6，因此 3 会早于 4 被访问。
- 前序 DFS：访问 1 后一路处理左子树 `2、4、5`，再处理右子树 `3、6`。

易错点：把树画得靠左当成“必须先访问”；BFS 按层，前序 DFS 按根、左、右。普通二叉树的中序结果也不一定升序。

知识关联：1.2 LIFO/FIFO、1.5 BFS/DFS。

## 二、操作系统

### 1. 总体知识讲解

#### 1.1 进程与线程：资源边界和执行流

程序是存放的指令与数据，**进程是正在运行的程序实例**，操作系统用它管理地址空间、打开的文件等资源。进程通常有独立虚拟地址空间，需要通过管道、共享内存、套接字等机制进行进程间通信；独立虚拟地址空间也不意味着绝不共享物理页。参见 [OSTEP：进程抽象](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-intro.pdf)。

一个进程可以包含多个**线程**，每个线程是一个执行流。常规同进程线程共享代码、堆和进程资源，各自有程序计数器、寄存器状态及调用栈。例如服务器的多个线程可以读取同一个订单表缓存；共享带来通信方便，也带来竞态风险。参见 [OSTEP：线程与并发](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-intro.pdf)。

要区分三件事：

- **并发**：多个任务在一段时间内交错推进，单核也可实现。
- **并行**：同一时刻有多个任务实际执行，通常需要多个执行核心。
- **上下文切换**：保存当前执行状态，恢复另一个执行状态。线程切换不意味着把整个进程内存全部复制一遍。

常用三状态：就绪表示可以运行但暂时没有 CPU；运行表示正在使用 CPU；阻塞表示等待 I/O 或某个事件，暂不能运行。时间片用完常是“运行 → 就绪”；发起需要等待的 I/O 常是“运行 → 阻塞”；I/O 完成通常是“阻塞 → 就绪”，不保证马上获得 CPU。

#### 1.2 调度：先明确目标，再计算时间

调度决定下一步把 CPU 分给谁。不同策略偏重不同目标：降低平均等待、尽快让交互任务获得第一次响应、提高吞吐或满足公平性，不能笼统说某一种永远最好。

| 算法 | 规则 | 典型特点 |
|---|---|---|
| FCFS，先来先服务 | 按进入就绪队列的次序运行，基础模型中非抢占 | 简单；长任务可能让短任务久等 |
| SJF，短作业优先 | 就绪任务中先选预计运行时间短者 | 在特定已知时长模型中可降低平均等待；真实时长难准确知道 |
| SRTF，最短剩余时间优先 | 比较剩余时长，可抢占 | 新短任务到来时可能抢占长任务 |
| RR，时间片轮转 | 每次最多运行一个时间片，未完成则重新排队 | 改善交互响应；时间片过小会增加切换开销 |
| 优先级调度 | 按优先级选择 | 低优先级任务可能饥饿，可用老化等措施缓解 |

做纯 CPU 调度题常用：`周转时间 = 完成时刻 - 到达时刻`；若没有 I/O，`等待时间 = 周转时间 - 总 CPU 运行时间`；`响应时间 = 第一次获得 CPU 的时刻 - 到达时刻`。有 I/O 的题不能直接把所有非 CPU 时间都算成就绪等待。调度规则与指标可对照 [OSTEP：调度](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-sched.pdf)。

#### 1.3 互斥与同步：一边防同时修改，一边安排先后顺序

**临界区**是访问共享资源、需要控制并发的代码区域。互斥要求同一时刻只有允许数量的执行者进入，例如用同一把互斥锁保护共享计数器。

`x += 1` 在一般语言/机器模型中不能直接当作原子操作：它可能拆为“读 x → 加 1 → 写回”。两个线程都读到 0，再各自写 1，就丢失了一次更新。锁需要保护整个读、改、写过程；仅给最后写入加锁仍可能使用旧值。参见 [OSTEP：锁](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-locks.pdf)。

**同步**强调先后或条件关系，例如消费者必须等到缓冲区非空才能取数据。互斥锁可以保护队列的修改，条件变量或信号量可以帮助等待“有数据”这个条件。两者常配合使用。

信号量可理解为受原子操作保护的许可计数：初始化为 1，可用于控制一次一个执行者进入；初始化为 0，可用于等待另一个任务发出完成通知；初始化为 `k`，可控制至多 `k` 个许可。具体阻塞与唤醒由原语实现，不能把普通整数加减当作信号量。参见 [OSTEP：信号量](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-sema.pdf)。

#### 1.4 死锁：逐项检查资源与等待关系

死锁是一些任务相互等待，导致这些任务都无法继续。例如 T1 持有锁 A、等待 B；T2 持有 B、等待 A，双方都不释放已有锁。

经典资源模型下，死锁需要以下四个条件：

| 条件 | 含义 | 一个破坏条件的方法 |
|---|---|---|
| 互斥 | 某些资源一次只能被一个任务占有 | 能共享的资源改为共享；锁通常仍需互斥 |
| 占有并等待 | 持有已有资源时继续申请新资源 | 一次申请全部所需资源，或申请失败先释放已有资源 |
| 不可抢占 | 已分配资源不能由外部随意强制拿走 | 对允许撤销的资源设计回滚/释放机制 |
| 循环等待 | 存在首尾相接的等待链 | 统一资源申请顺序，例如所有线程先 A 后 B |

每项都是**必要条件**，单独一项不是充分条件。系统允许互斥、占有等待等行为，并不能证明此刻已经死锁；应检查实际分配和等待关系。资源分配图有环时，若每种资源只有一个实例，可判定相关死锁；若有多个实例，有环仍可能因为其他实例被释放而打破等待，不能只凭环判死锁。四条件及预防方法见 [OSTEP：并发错误与死锁](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-bugs.pdf)，单实例与多实例的判定区别见 [Illinois CS 341 官方课程教材](https://cs341.cs.illinois.edu/coursebook/Deadlock)。

另一区分：饥饿是某任务长期拿不到资源，但其他任务可能不断推进；死锁是相关任务互相卡住。银行家算法属于死锁避免：分配前检查是否仍处于安全状态；“不安全”表示无法保证完成顺序，不等于死锁已经发生。

#### 1.5 虚拟内存、分页与缺页

进程看到虚拟地址，系统通过地址转换把它映射到物理内存。**页**是虚拟地址空间中的固定大小单位，**页框/帧**是物理内存中对应大小的单位，页表记录映射与权限等信息。页的大小相同，因此页内偏移在转换中保持不变。

若页大小为 `P` 字节，按字节寻址的虚拟地址为 `v`：

```text
虚拟页号 = v // P
页内偏移 = v % P
物理地址 = 物理页框号 × P + 页内偏移
```

例如页大小 `4 KiB = 4096 B`，偏移占 12 位。页表若将虚拟页 2 映射到物理页框 9，地址 `2×4096+100` 会转换为 `9×4096+100`；虚拟页号和物理页框号无需相同。参见 [OSTEP：分页](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-paging.pdf)。

**TLB**缓存近期的地址转换结果。TLB 未命中时需要查页表，但页面可能已经在内存，所以 TLB 未命中不等于缺页。访问的合法页面不在内存时，可能触发缺页异常，由操作系统补充页面再恢复执行。页面可能从文件/交换区读入，也可能是首次使用时分配并清零；因此并非每次缺页都要读磁盘。若地址无效或权限不允许，异常也可能导致进程被终止，而不是成功调入页面。参见 [OSTEP：TLB](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-tlbs.pdf) 及 [完整虚拟内存系统中的按需清零](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-complete.pdf)。

内存有空闲页框时可直接放入页面；没有足够空闲页框时才需要考虑淘汰。脏页可能需要回写，干净的文件页通常可直接丢弃后按需重读。

#### 1.6 页面淘汰：FIFO 与 LRU

FIFO 淘汰**最早进入内存**的页，命中不改变进入次序。LRU 淘汰**最长时间没有被访问**的页，每次访问都更新近期使用信息；精确 LRU 有维护成本，真实系统常使用近似策略。

简例：3 个空页框，访问 `1、2、3、1、4`。前三次缺页，第四次访问 1 命中。访问 4 时，FIFO 仍淘汰最先装入的 1；LRU 淘汰 2，因为 1 刚被访问过。最优 OPT 淘汰未来最久不用的页，但通常只能作为知道未来访问序列的理论对照。

FIFO 可能出现增加页框反而增加缺页的 Belady 异常，不能把“页框越多，所有算法缺页必然越少”当作通则。页面策略可对照 [OSTEP：页面替换策略](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-beyondphys-policy.pdf)。

### 2. 原创练习与逐题讲解（5 题）

#### FND-06｜进程、线程与并发（多选题）

题目：按常规操作系统模型，哪些说法正确？

- A. 同一进程的多个线程通常共享该进程的地址空间和堆。
- B. 每个线程仍需维护自己的寄存器状态、程序计数器和调用栈。
- C. 线程切换必须把该进程的全部内存复制一遍。
- D. 只要多个任务并发执行，就说明它们必定在同一瞬间并行运行。

**答案：A、B。**

逐项辨析：

- A 正确：共享数据使通信方便，也要求对并发访问进行保护。
- B 正确：执行位置、函数调用过程可能不同，不能共用同一份执行现场。
- C 错误：切换主要保存/恢复执行状态；不是复制整个地址空间。
- D 错误：单核通过交替调度也可实现并发；同时实际运行才是并行。

易错点：把“线程共享资源”理解成“线程没有独立执行状态”；把线程多当成一定能按线程数量提升运行速度。

知识关联：1.1 进程/线程、并发/并行、上下文切换。

#### FND-07｜FCFS 与时间片轮转（计算题）

题目：P1、P2、P3 均在时刻 0 到达，纯 CPU 运行时间分别为 6、2、1；初始队列为 P1 → P2 → P3，无 I/O，忽略切换开销。计算 FCFS 和时间片为 2 的 RR 的执行顺序、平均等待时间、平均响应时间。

**答案：FCFS 平均等待与平均响应均为 `14/3 ≈ 4.67`；RR 平均等待为 3，平均响应为 2。**

逐步推理：

```text
FCFS：0 ── P1 ── 6 ─ P2 ─ 8 ─ P3 ─ 9
RR：  0 ─ P1 ─ 2 ─ P2 ─ 4 ─ P3 ─ 5 ─ P1 ─ 7 ─ P1 ─ 9
```

| 策略 | 任务 | 完成时刻 | 等待 = 完成 - 运行时长 | 首次运行时刻 / 响应时间 |
|---|---|---:|---:|---:|
| FCFS | P1 | 6 | 0 | 0 |
| FCFS | P2 | 8 | 6 | 6 |
| FCFS | P3 | 9 | 8 | 8 |
| RR | P1 | 9 | 3 | 0 |
| RR | P2 | 4 | 2 | 2 |
| RR | P3 | 5 | 4 | 4 |

FCFS 平均等待 `(0+6+8)/3 = 14/3`；RR 平均等待 `(3+2+4)/3 = 3`。响应只看第一次得到 CPU，RR 为 `(0+2+4)/3 = 2`。时刻 7 只剩 P1，下一片仍由 P1 执行；不能为了“轮转”虚构空闲时间。

易错点：把响应时间算成完成时间；只算 P1 首次等待而漏掉被抢占后再次等待。本例 RR 的平均值更小，不代表它在所有输入和切换成本下都更好。

知识关联：1.2 调度规则、等待/响应/周转指标。

#### FND-08｜共享计数器与锁顺序（多选题）

题目：两个线程操作共享计数器 `x`；另有资源锁 A、B。假设普通读改写不是原子的，且锁是常规互斥锁。哪些说法正确？

- A. 两个线程都用同一把锁保护完整的“读 x、加 1、写回”过程，可以防止这两个线程之间的丢失更新。
- B. 只给写回 `x` 的最后一步加锁，就一定不会丢失更新。
- C. 所有需要 A、B 的线程均先申请 A 后申请 B，可以破坏由这两把锁形成的循环等待。
- D. 只要系统的锁不可被强制抢占，就可以认定当前已经发生死锁。

**答案：A、C。**

逐项辨析：

- A 正确：前提是所有相关访问都遵守同一保护规则；先持锁再读取，避免另一个线程插入修改。
- B 错误：两线程可能先同时读到 `x = 0`，各自计算 1，再依次持锁写入 1；最后仍只有 1。
- C 正确：统一顺序后，不会出现一个线程持 A 等 B、另一个持 B 等 A 的相反申请关系。仍需检查系统中的其他锁及代码路径。
- D 错误：不可抢占是必要条件之一，单独存在不足以判断死锁；没有实际等待环时可能一切正常。

易错点：认为“出现了锁”就能保证正确；锁的作用取决于保护范围、是否使用同一把锁，以及获取顺序。

知识关联：1.3 竞态与临界区、1.4 死锁四条件。

#### FND-09｜分页地址转换（计算题）

题目：系统按字节寻址，页面大小为 4096 B。某进程虚拟地址为十进制 13210，页表显示对应虚拟页映射到物理页框 7，且页面存在、权限允许。求虚拟页号、页内偏移和物理地址。如果该页合法但不在内存，应如何处理？

**答案：虚拟页号 3，页内偏移 922，物理地址 29594。**

逐步推理：

1. `13210 = 3×4096 + 922`，因此虚拟页号为 3，偏移为 922。
2. 页表把虚拟页 3 映射到物理页框 7，物理地址为 `7×4096+922 = 28672+922 = 29594`。
3. 偏移 922 不变，改变的是页号所对应的页框。
4. 若页面合法但未驻留，产生缺页异常，由操作系统安排装入或首次分配，必要时选择被替换页；成功处理并更新映射后继续执行。不能用一个不存在的页框号直接计算有效地址。

易错点：把 4 KiB 写成 4000 B；把页号 3 直接当成物理页框；把 TLB 未命中一律当作必须访问磁盘的缺页。

知识关联：1.5 虚拟页/物理页框、页表、缺页、TLB。

#### FND-10｜FIFO 与 LRU 缺页计数（追踪题）

题目：3 个初始为空的页框，访问序列为 `1、2、3、1、4、1、2、5`。分别按 FIFO 与精确 LRU 计算缺页次数。首次装入也算缺页；命中不计缺页。

**答案：FIFO 7 次，LRU 6 次。**

表中 FIFO 从左到右为最早装入到最晚装入；LRU 从左到右为最久未访问到最近访问。列表次序表示策略状态，不是固定物理页框位置。

| 次数 | 访问页 | FIFO 状态 | FIFO 结果 | LRU 状态 | LRU 结果 |
|---|---:|---|---|---|---|
| 1 | 1 | `[1]` | 缺页 | `[1]` | 缺页 |
| 2 | 2 | `[1,2]` | 缺页 | `[1,2]` | 缺页 |
| 3 | 3 | `[1,2,3]` | 缺页 | `[1,2,3]` | 缺页 |
| 4 | 1 | `[1,2,3]` | 命中，装入顺序不变 | `[2,3,1]` | 命中，1 更新为最近使用 |
| 5 | 4 | `[2,3,4]` | 缺页，淘汰 1 | `[3,1,4]` | 缺页，淘汰 2 |
| 6 | 1 | `[3,4,1]` | 缺页，淘汰 2 | `[3,4,1]` | 命中 |
| 7 | 2 | `[4,1,2]` | 缺页，淘汰 3 | `[4,1,2]` | 缺页，淘汰 3 |
| 8 | 5 | `[1,2,5]` | 缺页，淘汰 4 | `[1,2,5]` | 缺页，淘汰 4 |

FIFO 除第 4 次外均缺页，共 7 次；LRU 第 4、6 次命中，共 6 次缺页。本序列中 LRU 更好，不能据此推断它对每一条序列都严格优于 FIFO。

易错点：FIFO 命中后也移动到队尾，就把 FIFO 做成了 LRU；忘记初始三个空框中的首次访问也计入缺页。

知识关联：1.6 页面替换、状态追踪与初始条件。

## 三、计算机网络

### 1. 总体知识讲解

#### 1.1 分层：每层解决什么问题

分层让上层不必知道每一种底层实现。笔试中常见 OSI 七层与 TCP/IP 模型，不要把某层的序号机械套进另一模型。

| TCP/IP 常用四层 | 主要任务 | 例子 | 与 OSI 的常见对应 |
|---|---|---|---|
| 应用层 | 应用如何表达请求、响应与数据 | HTTP、DNS | 应用、表示、会话三层 |
| 传输层 | 端到端进程间传输，使用端口区分服务 | TCP、UDP | 传输层 |
| 网际层 | 寻址、路由，把包送到目标主机所在网络 | IP | 网络层 |
| 链路层 | 相邻节点之间传帧及底层传输 | 以太网、Wi-Fi | 数据链路层、物理层 |

教学中的“五层模型”把最后一层再拆成数据链路层与物理层。IP 地址用于网络寻址，端口用于区分主机上的应用服务；MAC 地址用于相应链路上的帧转发，不是跨互联网的统一应用标识。

封装可理解为 HTTP 内容放入传输数据，再放入 IP 包，再放入链路帧。经过路由器时链路封装会变化，应用并不直接处理每一跳的 MAC 地址。协议分层定位可结合 [TCP 标准的协议说明](https://www.rfc-editor.org/rfc/rfc9293.html#section-2) 和 [UDP 标准](https://www.rfc-editor.org/rfc/rfc768.html) 阅读。

#### 1.2 一次 HTTPS 请求：DNS → TCP → TLS → HTTP

下面限定**需要解析域名、没有可复用连接的新 HTTP/1.1 或 HTTP/2 HTTPS 连接**，用来建立基础流程：

1. **DNS**把域名解析为 IP 地址，先可能查看缓存；缺失时通过解析器查询。DNS 服务属于应用层，不负责把业务网页本身下载回来。参见 [RFC 1034：DNS 概念与设施](https://www.rfc-editor.org/rfc/rfc1034.html)。
2. **TCP**连接目标 IP 与端口，例如 HTTPS 常用 443，协商初始序号等状态。
3. **TLS**建立受保护的通道，协商参数，并验证服务器证书等身份信息。
4. **HTTP**在该通道中发送请求，接收状态码、响应头和内容。

这是帮助理解依赖关系的简化流程。缓存命中可能不发起 DNS 查询，连接复用可能不重新建立 TCP/TLS，重定向可能再次请求。HTTP/3 使用 QUIC，不能套用“HTTPS 必须先建立 TCP”的断言，参见 [RFC 9114：HTTP/3](https://www.rfc-editor.org/rfc/rfc9114.html)。

#### 1.3 TCP 三次握手与关闭连接

TCP 提供可靠、有序的**字节流**。建立连接通常经历：客户端发 `SYN`，服务器回 `SYN+ACK`，客户端回 `ACK`。双方不仅要宣布自己的初始序号，也要确认收到对方的序号；第三步让服务器获得对自己 SYN 的确认，并减少旧的重复连接请求造成混乱。

如果客户端初始序号为 `x`、服务器为 `y`，基本形式为：

```text
客户端 → 服务器：SYN，seq=x
服务器 → 客户端：SYN+ACK，seq=y，ack=x+1
客户端 → 服务器：ACK，seq=x+1，ack=y+1
```

`SYN` 和 `FIN` 各占用一个序号；不带数据的纯 ACK 不占用序号。ACK 值表示接收方接下来期望的序号。

关闭时，两端的发送方向分别结束：A 发 FIN 表示“A 不再发送”；B 可先 ACK 确认，但它自己的数据可能尚未发完；B 发完后再发 FIN，A 再确认，因此常见“四次挥手”。确认 A 的 FIN 不等于 B 立刻也必须关闭发送方向；ACK 与 FIN 有时可合并，所以不能说每次恰好四个报文。TIME_WAIT 有助于确认关闭和让旧报文退出网络，不能简单把它解释为内存泄漏。建立与关闭流程见 [RFC 9293 第 3.5 节](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.5) 与 [第 3.6 节](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.6)。

#### 1.4 TCP / UDP 的可靠性边界

| 对比项 | TCP | UDP |
|---|---|---|
| 基本模型 | 面向连接、字节流 | 无连接、数据报 |
| 内置可靠机制 | 序号、确认、重传等，提供有序字节流 | 本身不保证交付、顺序或去重 |
| 消息边界 | 不保留应用消息边界，应用需定义长度/分隔规则 | 保留数据报边界 |
| 流量与拥塞管理 | 有相关机制 | UDP 本身不内置 TCP 式机制，应用/上层协议需负责 |

TCP 的可靠性是传输层服务，不是“网络永远不会断”，也不是“业务必定成功一次”。即使数据到达接收端 TCP，服务器应用也可能未处理、处理后响应丢失，或业务事务失败。订单提交的去重、结果查询及幂等仍需应用层设计。

UDP 丢包并非必然发生；“不保证”不等于“每次都会丢”。应用可以在 UDP 上实现确认、重传与排序，例如更复杂的上层协议。因此不能用“实时任务都必须 UDP”或“UDP 上不可能可靠”作绝对判断。可靠字节流与数据报语义分别见 [RFC 9293 第 2.2 节](https://www.rfc-editor.org/rfc/rfc9293.html#section-2.2) 和 [RFC 768](https://www.rfc-editor.org/rfc/rfc768.html)。

#### 1.5 HTTP 方法、状态码与幂等

方法表达客户端对资源的意图；状态码表达服务端对这次请求的处理结果。

| 方法 | 常见语义 | 按标准语义安全？ | 按标准语义幂等？ |
|---|---|---|---|
| GET | 获取资源表示 | 是 | 是 |
| HEAD | 获取类似 GET 的响应元信息，不返回响应内容 | 是 | 是 |
| POST | 提交数据，按资源定义执行处理，例如创建订单 | 否 | 无通用幂等保证 |
| PUT | 创建或替换指定目标资源的状态 | 否 | 是 |
| DELETE | 删除目标资源的关联 | 否 | 是 |
| PATCH | 应用部分修改 | 否 | 无通用幂等保证，具体操作可设计为幂等 |

**安全**指按方法语义客户端没有请求修改资源状态，不表示服务端不会记日志；**幂等**指多次相同请求对服务端的预期效果与一次相同。DELETE 第一次返回 204、第二次返回 404，仍可能幂等，因为资源最终都处于已删除状态，响应码不要求一样。POST 也可以通过业务幂等键实现去重，但不能只因为叫 POST 就默认具有这一保证。定义见 [RFC 9110：安全与幂等方法](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2)；PATCH 定义与幂等边界见 [RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html#section-2)。

| 类别 / 状态码 | 基本含义 | 常见误读 |
|---|---|---|
| 1xx | 信息性响应 | 不代表业务最终成功 |
| 2xx；200、201、204 | 成功；请求成功、创建成功、成功但无响应内容 | HTTP 成功不保证业务数据一定正确 |
| 3xx；301、302、304 | 重定向类；永久、临时重定向、条件请求下资源未修改 | 304 不是“服务端出错”，可用于缓存复用 |
| 4xx；400 | 客户端请求有问题，例如语法问题 | 不能仅凭 400 判断具体字段错误 |
| 401 | 缺少或没有通过有效认证 | 与“已识别身份但拒绝权限”的常见 403 不同 |
| 403、404、405 | 拒绝请求、资源未找到、方法不允许 | 404 有时也用来隐藏资源存在性 |
| 5xx；500、502、503 | 服务端错误、网关收到无效上游响应、服务暂不可用 | 不都表示代码语法错误 |

状态码细节可对照 [MDN HTTP 状态码参考](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status)。测试接口时，应分别检查 HTTP 结果、业务返回值、数据库变化和重复请求的效果。

#### 1.6 HTTPS 保护到哪里

HTTPS 是 HTTP 通过 TLS 等受保护连接通信。正常验证证书并使用安全配置时，TLS 提供传输内容的机密性、完整性和服务器身份验证；双向 TLS 还可验证客户端证书，但普通 HTTPS 不自动等于已认证业务用户。TLS 的目标见 [MDN TLS 安全说明](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Transport_Layer_Security) 和 [RFC 8446 的安全目标](https://www.rfc-editor.org/rfc/rfc8446.html#section-1)。

请求路径、查询参数、HTTP 头和内容在连接中受到加密保护；但浏览器/服务端会看到明文，TLS 在代理或网关终止后，后续链路仍需相应保护。HTTPS 不能修复 SQL 注入、越权或错误扣款，也不能保证网页内容可信。目标 IP 等连接信息通常仍可见；域名是否暴露还与 DNS 加密和 TLS 握手隐私机制有关，不能简化为“所有访问痕迹都不可见”。

#### 1.7 IPv4 子网：把前缀当作位数

IPv4 地址共 32 位，`/p` 表示前 `p` 位是网络前缀，其余 `32-p` 位用于该网段内的地址。前缀越长，单个地址块越小。CIDR 前缀定义见 [RFC 4632](https://www.rfc-editor.org/rfc/rfc4632.html)。

以 `/26` 为例：网络位 26、主机位 6，地址总数 `2⁶ = 64`；掩码为 `255.255.255.192`，最后一段的地址块起点为 0、64、128、192。普通广播子网中，主机位全 0 是网络地址、全 1 是广播地址，常用主机地址数为 `64-2 = 62`。

例如 `192.168.10.77/26`：77 落在 64～127 这一块，所以网络地址 `.64`，广播地址 `.127`，常用主机范围 `.65～.126`。也可以逐位计算 `IP AND 掩码` 得到网络地址。

不要机械把所有前缀都套入 `2^(32-p)-2`：`/31` 点到点链路的两个地址可作为端点地址，见 [RFC 3021](https://www.rfc-editor.org/rfc/rfc3021.html)；`/32` 表示单个地址。题目若规定“普通广播子网”，再按减 2 的模型计算。

### 2. 原创练习与逐题讲解（5 题）

#### FND-11｜请求过程与分层（多选题）

题目：需要域名解析，且没有缓存结果或可复用连接，新建 HTTP/1.1 HTTPS 连接。哪些说法正确？

- A. DNS 是应用层协议，TCP 是传输层协议。
- B. 基础过程可概括为 DNS 解析、TCP 建连、TLS 建立受保护通道、发送 HTTP 请求。
- C. HTTP 直接负责每一跳的链路层 MAC 地址转发。
- D. 所有版本的 HTTPS 都必须使用 TCP，所以 HTTP/3 也先执行 TCP 三次握手。

**答案：A、B。**

逐项辨析：

- A 正确：分层取决于解决的问题，不能因为 DNS 常用某种传输就把它算作传输层。
- B 正确：题设排除了缓存与连接复用，且明确是经 TCP 的 HTTP/1.1 HTTPS 基础模型。
- C 错误：HTTP 表达应用请求；链路层与网络层承担相应的传帧、路由任务。
- D 错误：HTTP/3 使用 QUIC，不能把特定版本的流程推广到所有 HTTPS。

易错点：忽视协议版本与缓存等前提；把“四层”“五层”“七层”的层号直接混用。

知识关联：1.1 分层、1.2 请求依赖关系。

#### FND-12｜TCP 序号与关闭（单选题）

题目：无数据携带的基本三次握手中，客户端 SYN 的 `seq = 100`，服务端 SYN+ACK 的 `seq = 500`。下列说法哪项正确？

- A. 服务端 SYN+ACK 的 `ack` 应为 100，因为客户端没有发送业务数据。
- B. 客户端最后一个纯 ACK 的 `ack` 应为 501。
- C. 服务端确认客户端的 FIN 后，必须马上发自己的 FIN，不允许再发送剩余数据。
- D. 所有 TCP 正常关闭过程一定恰好包含四个报文，不能合并。

**答案：B。**

逐项辨析与计算：

- A 错误：SYN 本身占用一个序号，所以服务器期望客户端下一序号为 `100+1 = 101`。
- B 正确：服务端 SYN 也占一个序号，客户端确认值为 `500+1 = 501`；最后 ACK 的 `seq` 通常为 101。
- C 错误：客户端 FIN 仅结束客户端的发送方向；服务器确认收到后仍可能发送尚未发完的数据。
- D 错误：常见过程分为 FIN、ACK、FIN、ACK；若条件允许，一端 ACK 与自己的 FIN 可以组合。

易错点：认为只有业务数据才占用序号；把 TCP 双向通信当成一个整体开关，忽视半关闭。

知识关联：1.3 握手、序号、双向独立关闭。

#### FND-13｜可靠传输与 HTTPS（多选题）

题目：哪些说法正确？

- A. TCP 可靠，所以只要请求通过 TCP 发送，银行转账一定恰好成功一次。
- B. UDP 本身不保证数据报到达、按顺序到达或去重，但应用可以自行补充可靠机制。
- C. HTTPS 可以保护传输中的 HTTP 内容，但服务端仍会看到解密后的请求，也仍可能存在业务漏洞。
- D. 某网页使用 HTTPS，就能保证其经营者可信且不存在钓鱼内容。

**答案：B、C。**

逐项辨析：

- A 错误：传输可靠与事务成功不同。服务器可能已扣款，但回包丢失；客户端重试若无去重可能产生重复处理，需要业务幂等及结果查询。
- B 正确：UDP 的边界是自身不提供这些保证，不是上层绝对无法实现。
- C 正确：TLS 保护连接上的内容，不能替代权限校验、数据库事务和输入处理。
- D 错误：证书验证服务身份与加密通道，不等于保证经营诚信、页面内容或业务代码都正确。

易错点：把“可靠”“安全”“业务正确”混为一谈；把 UDP 的“不保证”记成“必然失败”。

知识关联：1.4 传输可靠性边界、1.6 HTTPS 保护边界。

#### FND-14｜幂等与状态码（多选题）

题目：按 HTTP 标准语义，哪些说法正确？

- A. 相同 DELETE 请求第一次返回 204、第二次返回 404，足以证明它不幂等。
- B. 创建订单的 POST 若没有业务去重约束，超时后直接重复提交可能重复创建。
- C. 401 的标准含义是“身份认证已经成功，只是没有访问权限”。
- D. 500 属于服务端错误类别；即使某请求返回 200，测试也仍应检查业务结果是否正确。

**答案：B、D。**

逐项辨析：

- A 错误：幂等看服务端预期效果，不看每次返回是否相同；两次后资源都已删除，仍可幂等。
- B 正确：超时只说明客户端没及时得到结果，不能确定服务端完全没处理。应根据接口设计查询结果或使用业务幂等键。
- C 错误：401 表示缺少有效认证；认证身份已知但访问被拒时常见 403。实际应用可能隐藏资源或采用不同授权策略，还要看接口规范。
- D 正确：500 是 5xx；200 只表达 HTTP 层面的成功语义，仍需验证金额、订单状态等业务断言。

易错点：把幂等理解为“返回文本完全一致”；把 200 当作测试通过的唯一条件。

知识关联：1.5 HTTP 方法、认证/授权、状态与业务校验。

#### FND-15｜IPv4 子网划分（计算题）

题目：某普通 IPv4 广播子网的主机地址为 `192.168.10.77/26`。求子网掩码、网络地址、广播地址、常用主机地址范围及数量；`192.168.10.130/26` 是否在同一子网？

**答案：掩码 `255.255.255.192`；网络 `.64`；广播 `.127`；主机 `.65～.126`，共 62 个；`.130/26` 属于另一子网。**

逐步推理：

1. IPv4 共 32 位，`/26` 留下 `32-26 = 6` 位主机位，地址块大小 `2⁶ = 64`。
2. 掩码最后一段前两位为 1、后六位为 0，即 `11000000₂ = 192`；前三段为 255。
3. 最后一段地址块是 `0～63、64～127、128～191、192～255`。77 落在 `64～127`。
4. 将主机位全置 0 得 `.64`；全置 1 得 `.127`。普通主机地址在两者之间：`.65～.126`，数量 `64-2 = 62`。
5. 130 落在 `128～191`，网络地址为 `192.168.10.128`，与 `.64` 不同。不同子网仍可能通过路由通信；“不在同一子网”不等于“绝不可能通信”。

易错点：把 77 本身当作网络起点；把 `/26` 当成 26 个地址；最后一位相同或前三段相同不能单独决定是否同一网段。

知识关联：1.7 前缀、掩码、网络/广播地址、路由边界。
