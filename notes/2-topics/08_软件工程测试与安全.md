# 软件工程测试与安全知识和题目讲解

## 一 软件工程总体知识

需求决定“应该做什么”，设计决定“如何组织实现”，测试检查“实现是否符合预期”。例如报销限额的需求若没说明是单笔还是每日累计，测试和代码都不能自行选一种当成事实。先把规则写清楚，再给正常和异常输入定义预期结果。

面向对象的封装把状态和操作放到合适边界；抽象只暴露使用者需要的能力；继承表达可替代的类型关系；多态让同一接口有不同实现。“高内聚”表示一个模块里的工作围绕一个职责，“低耦合”表示模块之间少依赖不必要细节。设计模式帮助组织变化，不能替代需求判断。

| 概念 | 通俗解释 | 笔试辨别 |
|---|---|---|
| 瀑布式开发 | 按阶段逐步交付，阶段边界较明确 | 不等于完全禁止反馈与返工 |
| 迭代开发 | 多轮逐渐完善 | 每轮依据反馈调整，不是一次写完所有功能 |
| 敏捷 | 重视可工作的成果与协作反馈 | 不等于不要计划、文档、测试 |
| 重构 | 保持外部行为，改善内部结构 | 改审批规则属于功能变更，应单独说明 |
| 版本控制 | 保存可追溯的代码历史 | 提交代码不等于代码已部署 |
| 持续集成 | 经常集成并自动检查变化 | 检查通过只是当前检查范围的证据 |

需求、代码、测试和缺陷之间要能对应。发现“审批后还能撤回”时，缺陷记录写清步骤、预期、实际、环境和证据；不要只写“系统有问题”。修改后既检查原缺陷，也检查相关正常路径。

## 二 测试总体知识

### 测试方法与测试层次

黑盒方法根据输入输出和需求设计用例；白盒方法根据代码结构设计用例。单元测试关注较小模块，集成测试检查模块协作，系统或端到端测试检查更完整的流程；这些层次不能直接等同于黑盒或白盒。

等价类将输入分成预期处理相似的组，例如有效年龄和无效年龄；边界值强调边界及其邻近值；判定表列出多条件的组合与动作；状态转换测试检查哪些操作可从当前状态进入下一状态。它们可以共同使用。方法与术语参考 [ISTQB基础级官方资料](https://istqb.org/certifications/certified-tester-foundation-level-ctfl-v4-0/)，本章用例是按虚构需求原创设计。

| 场景 | 更适合先用的办法 | 举例 |
|---|---|---|
| 数值范围 | 等价类与边界值 | 金额1至100000分，检查0、1、2、99999、100000、100001 |
| 多条件审批 | 判定表 | 是否本人、是否待审批、金额是否合规 |
| 多状态业务 | 状态转换 | 草稿→已提交→已批准；已批准不能直接编辑 |
| 输入组合很多 | 按风险选组合，必要时用组合测试 | 不声称测了少数用例就穷尽所有组合 |

代码覆盖率说明测试执行了多少代码结构，不保证断言正确或需求完整。语句覆盖检查语句是否执行，分支覆盖检查各判定结果是否走过；二者都不等于条件组合穷尽。

Mock用受控替身隔离依赖，适合让支付网关“固定超时”来验证本地错误处理。但Mock没有真的请求网关，不能证明真实协议、认证或网络可用。单元测试旁边仍需要相应的集成验证。参见 [Python unittest.mock官方说明](https://docs.python.org/3/library/unittest.mock.html)。

### 并发和失败场景

顺序点击一次按钮通过，不证明并发安全。两个审批请求可能同时看到“待审批”，各执行一次扣款。应检查状态更新是否原子、业务唯一约束是否生效、事务失败是否回滚以及重试是否重复产生副作用。

幂等表示重复执行相同操作的最终预期效果与执行一次相同；返回内容不一定每次完全一致。唯一请求键应与用户和请求内容绑定，同键不同内容要定义拒绝或冲突行为。数据库事务可以保护库内一致性，外部支付和邮件不自动随数据库回滚，应另有可靠投递或补偿设计。

## 三 安全总体知识

认证判断“你是谁”，授权判断“你能对这个对象做什么”。用户成功登录后仍可能不能读别人的报销。授权应在服务端检查身份、对象归属、操作权限及状态，前端隐藏按钮不能构成权限边界。参见 [OWASP授权说明](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

| 风险或概念 | 核心问题 | 主要控制 |
|---|---|---|
| SQL注入 | 用户文本被拼成SQL代码 | 绑定值参数；动态表名和排序字段用白名单 |
| XSS | 不可信内容被浏览器当成脚本 | 按输出上下文编码、使用安全DOM接口；允许富文本时做适当净化 |
| CSRF | 浏览器携带凭证发出用户未授权的状态变更请求 | 反CSRF机制、合适的Cookie属性与来源验证，按架构组合 |
| 越权 | 有身份但无对象或操作权限 | 服务端逐次检查对象和操作授权 |
| 加密 | 有密钥可解回明文，保护保密性 | 正确算法、密钥管理和使用方式 |
| 哈希 | 生成摘要，通常不能反向恢复原文 | 不是所有哈希都适合保存密码 |
| 数字签名 | 私钥签名、公钥验证 | 验证来源与完整性，本身不隐藏正文 |
| 最小权限 | 只授予完成工作所需权限 | 应用账号不直接拥有数据库管理员权限 |

SQL参数化不会解决对象越权，XSS防护不能只靠过滤一个关键词。密码应使用带盐的专用密码哈希方案并设置合适成本；普通SHA-256速度快，面对离线猜测不合适。具体方案按当前实现文档选取。参见 [OWASP SQL注入防护](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)、[XSS防护](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)、[密码存储](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)。

日志有助于追溯，不能把访问Token、密码等完整记录进去。一次攻击字符串没有生效，只说明该输入在该路径上没有触发漏洞；需要结合控制机制、其他入口和回归测试判断。

## 四 十道题与解析

### SE01 高内聚低耦合单选题

**题目：** 报销模块直接操作邮件服务器配置、计算税额并渲染页面。为减少联动修改，哪项更合理？

- A. 把所有功能放进一个更大的类
- B. 为业务规则、通知和展示划分职责，通过明确接口协作
- C. 删除全部接口，直接读写其他模块私有变量
- D. 只把函数改名，不改变依赖

**答案：B。** B把不同变化原因分开，通知实现改变时不必连带改金额规则。A扩大职责，C增加对内部细节的依赖，D只改名字无法减少耦合。

**易错点：** 模块越多不一定越好；划分要有真实职责边界。关联知识：单一职责、依赖倒置、设计模式。

### SE02 边界值分析题

**题目：** 年龄字段只接受整数18至60，采用每个边界及其两侧邻近整数的检查方式，写出数值用例，并补两种类型或格式异常。

**答案：** 数值为17、18、19、59、60、61；17和61应拒绝，18、19、59、60应接受。格式异常可选空值与小数18.5，均拒绝。本题约定不接受自动类型转换；字符串是否允许应由接口契约明确。

**讲解：** 最小边界18及附近是17、18、19，最大边界60及附近是59、60、61。再加非整数或缺失输入，覆盖不同失败原因。

**易错点：** 只测20和40都在有效类内，无法检查范围符号写反。关联知识：等价类和输入契约。

### SE03 判定表分析题

**题目：** 仅在“请求者是审批人”和“状态为待审批”同时满足时允许批准。列出两个布尔条件的全部组合及结果。

| 是审批人 | 待审批 | 预期 |
|---|---|---|
| 是 | 是 | 允许批准 |
| 是 | 否 | 拒绝状态不合法 |
| 否 | 是 | 拒绝无权限 |
| 否 | 否 | 拒绝；错误优先级按接口约定 |

**讲解：** 两个二值条件有 `2×2=4` 种组合。把它们列齐，容易发现代码误写OR会放行两类错误请求。

**易错点：** “同时有两种错误”并不自动决定返回哪种错误码，应先有契约。关联知识：逻辑条件、授权、状态机。

### SE04 状态转换单选题

**题目：** 约定草稿可提交、待审批可批准或拒绝，已批准不可再编辑金额。最应加入哪个测试？

- A. 只测试草稿提交成功
- B. 把已批准单据改金额，检查服务端拒绝且原金额不变
- C. 只观察页面按钮颜色
- D. 删除状态字段，使所有动作都能执行

**答案：B。** B覆盖禁止的状态转换并检查数据没有被改。A只测正常路径，C不检查服务端，D破坏业务约束。

**易错点：** 只返回错误码但数据库已被修改，也属于失败。关联知识：状态转换、异常副作用、事务。

### SE05 语句覆盖单选题

**题目：** 下列程序仅输入 `x=1`，语句覆盖达到100%。能否认为两个判定结果都已测试？

```python
def positive_flag(x):
    flag = 0
    if x > 0:
        flag = 1
    return flag
```

- A. 能，所有可执行语句都走过
- B. 不能，还需输入0或负数检查判定为假
- C. 能，只有有else时才需要分支测试
- D. 不能，必须测试全部整数

**答案：B。** 输入1执行了所有语句，但没有走 `x>0` 为假的路径。A混淆指标，C忽略隐含的假路径，D要求穷尽无限输入，不符合本题目标。

**易错点：** 覆盖率高也可能没有有效断言。关联知识：语句覆盖、分支覆盖和测试预期。

### SE06 Mock能力边界单选题

**题目：** Mock支付接口返回超时，本地程序正确提示失败。能证明什么？

- A. 真实支付服务认证和协议都兼容
- B. 本地对该超时响应的处理符合测试预期
- C. 生产网络不会超时
- D. 真实支付绝不会重复扣款

**答案：B。** 只有替身设置的响应及本地路径得到检验。A需要真实集成验证，C无法由一次替身测试证明，D还需幂等、状态查询等检查。

**易错点：** Mock全部通过不等于集成通过。关联知识：测试层次、依赖隔离。

### SE07 幂等与并发多选题

**题目：** 用户超时后重复提交同一报销，怎样避免重复创建并验证实现？

- A. 只禁用前端按钮
- B. 服务端使用有作用域的请求键与数据库唯一约束
- C. 检查同键同内容重试、同键不同内容以及两个同时提交的请求
- D. 每次重试生成全新请求键

**答案：B、C。** B提供服务端防重边界，C覆盖重试语义和竞态。A可被直接HTTP请求绕过，D会让同一操作看起来是不同操作。

**易错点：** 只先SELECT再INSERT可能并发穿透，应依赖原子机制，并定义失败或冲突处理。关联知识：唯一约束、事务、幂等。

### SE08 SQL注入防护单选题

**题目：** 用户名来自请求参数，下列哪项是主要防护？

- A. 拼接SQL前仅删除空格
- B. 用参数化查询绑定用户名值
- C. 把数据库账号升级为管理员
- D. 改用HTTPS后继续拼接

**答案：B。** B让用户值作为数据传给数据库。A不足以覆盖SQL语法，C扩大风险，D保护传输却不改变后端拼接逻辑。

**易错点：** 动态表名等标识符通常不能作为普通值参数绑定，要用固定映射或白名单。关联知识：数据库访问与输入边界。

### SE09 登录后仍可能越权单选题

**题目：** 用户A登录后，把报销编号改成用户B的编号便能查询B的记录。最直接的缺陷是什么？

- A. 只存在密码强度问题
- B. 对具体报销对象缺少授权检查
- C. TCP三次握手少了一次
- D. 索引过多

**答案：B。** 身份已确认，但系统没有确认A是否能读B的对象。A是另一类问题，C和D不能解释对象归属绕过。

**易错点：** 将编号换成随机UUID可以降低猜测机会，仍不能替代授权。关联知识：认证、授权和水平越权。

### SE10 密码存储与签名单选题

**题目：** 哪项说法正确？

- A. 普通SHA-256足够适合所有密码存储
- B. 数字签名自动加密正文
- C. 专用密码哈希配合盐和合适成本，用于增加离线猜测代价
- D. 最小权限表示任何账号都不能执行操作

**答案：C。** 盐减弱预计算与相同密码摘要关联，合适成本增加猜测代价。A忽略快速通用哈希的风险，B混淆签名与加密，D误解“只授予必需权限”。

**易错点：** 盐不必保密，它与秘密密钥或pepper的角色不同；带盐哈希仍不能弥补极弱密码。关联知识：密码哈希、完整性、保密性。

## 五 一页速记与自测

做场景题时依次检查输入、身份与对象权限、业务状态、重复与并发、事务或外部失败、输出与日志。对每个控制说清楚“放在哪一层、验证什么、失败后数据应怎样”。

- 等价类看输入分组，边界值看临界位置，判定表看条件组合，状态转换看允许和禁止的动作。
- 重测检查原缺陷已修复；回归检查相关功能有没有被改坏。
- 认证成功仍需授权；HTTPS保护传输，不能修复服务端注入或越权。
- 高覆盖率、Mock通过、一个正常样例通过，各自只能证明有限范围。

达标标准：独立给“提交报销”写出至少8个用例，包含正常、金额边界、缺字段、他人对象、非法状态、重复提交、并发、依赖失败；每个都写预期响应和预期数据状态。再用自己的话解释参数化、授权与幂等分别解决什么问题。

## 六 测试与工程知识拓展

### 覆盖率之间的区别

| 指标 | 覆盖对象 | 不能单独证明的事 |
|---|---|---|
| 语句覆盖 | 可执行语句是否走过 | 判定真假两个方向都走过 |
| 判定覆盖 | 整体判定的真和假结果 | 每个原子条件分别起作用 |
| 条件覆盖 | 每个原子条件的真和假取值 | 整个判定真和假都出现 |
| 条件组合覆盖 | 原子条件的可能组合 | 需求完整、断言准确 |
| MC/DC | 每个条件能独立影响判定结果 | 所有路径或所有输入都覆盖 |

以 `A AND B` 为例，按逻辑真值表，`(真,假)` 和 `(假,真)` 让两个条件都出现过真和假，但整体结果都是假；条件覆盖不能直接推出判定覆盖。若分析具体短路语言的运行覆盖，还要检查某个条件是否真的被求值，不能只根据输入取值计覆盖。

MC/DC要求展示各条件能够独立影响判定结果。本节用unique-cause方式说明：其他条件固定，只改变一个条件就改变整体判定。例如 `(真,真)` 对 `(假,真)` 展示A的作用，`(真,真)` 对 `(真,假)` 展示B的作用。这是简单表达式的例子，不代表所有带重复条件或约束的表达式都只需相同数量用例；masking等变体不在本节展开。参见 [NASA的MC/DC教程](https://shemesh.larc.nasa.gov/fm/papers/Hayhurst-2001-tm210876-MCDC.pdf)。

覆盖率是定位测试缺口的线索，测试还要有正确的预期和断言。即使每行都走过，如果从不检查余额变化，转账代码写错仍可能通过测试。

### 性能指标与测试目标

吞吐量表示单位时间完成多少工作；QPS常按请求计，TPS按业务事务计，二者口径未必相同。响应时间测从哪个入口到哪个出口，要先约定是否包含排队、网络和重试。并发数表示同一时刻正在处理或等待的任务数，不等于每秒请求数，也不直接等于注册用户数。

平均延迟会掩盖长尾。P95描述约95%的样本延迟不超过某个位置的值，P99观察更靠后的尾部；具体工具可能使用不同的样本排序或插值算法，做计算题以题目给定算法为准。不同实例的P95通常不能直接平均为全局P95；需要适当合并分布或使用原始样本计算。

| 测试类型 | 想解决的问题 | 主要观察 |
|---|---|---|
| 负载测试 | 预期业务负载下表现如何 | 吞吐、延迟分布、错误率、资源利用 |
| 压力测试 | 超出正常承载时如何退化 | 限流、排队、失败方式、恢复能力 |
| 稳定性测试 | 持续运行是否退化 | 内存泄漏、连接泄漏、累积延迟 |
| 突发测试 | 短时间流量陡增怎样响应 | 扩容速度、缓存击穿、队列积压 |

性能结果必须附数据规模、并发模型、测试时长、软硬件和错误口径。请求快速失败可能让吞吐看似很高；缓存全命中与真实业务混合负载也不能直接比较。先保证业务结果正确，再判断是否满足性能目标。

### 缺陷定位与Git状态

一次失败先确定可复现输入、环境和时间，再沿请求链查接口、日志、依赖和数据库状态。不要把“最后出现错误的模块”直接当根因；数据库连接池耗尽的根因可能是上游未释放连接。

Git工作区保存当前文件，暂存区保存准备提交的快照，提交是记录在版本历史里的快照。`git add`更新暂存内容，不等于提交；修改已add过的文件后，还需重新add才能让新的改动进入下一次提交。

| 操作 | 主要影响 | 选择依据 |
|---|---|---|
| diff | 比较工作区、暂存区或提交差异 | 先看清实际改了什么 |
| revert | 用新提交表达对旧提交的反向修改 | 共享历史中需要撤销具体已提交改动 |
| reset | 按模式调整HEAD、暂存区及可能的工作区 | 理解不同模式影响后再用，不能等同于revert |
| merge | 合并分支历史与改动 | 可能产生合并提交或冲突 |
| rebase | 把提交重放到新基点，通常改写提交身份 | 对共享历史需要协作约定 |

这里用于辨析命令，不执行仓库修改。官方语义见 [Git revert](https://git-scm.com/docs/git-revert) 与 [Git reset](https://git-scm.com/docs/git-reset)。

### 数据库事务以外的可靠性

把“修改报销状态”和“给用户发邮件”放在一个普通数据库事务代码块里，不代表邮件能回滚。邮件发出后数据库提交失败，用户可能收到一个从未成功发生的业务通知。

一种常见设计是事务发件箱：在同一数据库事务里写业务状态和待发送事件，提交后由后台任务发送事件。发送成功但确认记录失败时仍可能重发，所以消费者要按业务事件键去重，并设计重试、积压观察与失败处理。发件箱减少“业务已提交却没留下待发送记录”的缺口，不承诺任意外部系统恰好处理一次。参见 [Microsoft事务发件箱说明](https://learn.microsoft.com/en-us/azure/architecture/databases/guide/transactional-out-box-cosmos)，本节只借用通用原理，不要求使用Azure。

另一方向是补偿：把已经完成的外部动作通过新的业务操作纠正。补偿本身也可能失败，且不一定是原动作的完全逆操作；不能把它与数据库ROLLBACK画等号。

## 七 Web安全知识拓展

### 会话Cookie与JWT

Cookie是浏览器存储并按规则随请求发送数据的机制；Session常指服务端保存的会话状态，浏览器可能只保存会话标识。JWT是一种令牌表示方式，不等于一个完整的登录、注销和授权方案。

常见签名JWT的载荷可以被读取，Base64url编码不是加密。服务端需要固定允许的验证方式，核验签名或MAC，以及适用的issuer、audience、过期时间等声明；校验令牌后仍要判断当前对象和操作权限。只解码出用户名就信任令牌是错误做法。JWT已签发并不意味着角色变化或注销会自动撤销所有副本，需要有效期与撤销策略。参见 [OWASP REST安全中的JWT](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html#jwt)。

HMAC用共享秘密验证消息完整性与真实性，知道秘密的双方都可生成合法MAC；数字签名用私钥签名、公钥验证，密钥分工不同。普通哈希没有秘密，任何人都能为修改后的内容重新算摘要，不能独立承担消息来源认证。HMAC结构定义见 [RFC 2104](https://www.rfc-editor.org/rfc/rfc2104.html)；这里不沿用其早期算法举例作为当前选型建议。

### XSS与CSRF的不同路径

XSS让攻击者控制的脚本进入可信站点上下文执行；CSRF利用用户浏览器自动附带凭证，发出用户未授权的操作请求。CSRF不一定需要读取响应，也不要求先窃取Cookie；仅阻止跨域读取响应并不等于阻止所有伪造操作。

HttpOnly主要限制脚本直接读取对应Cookie，不阻止浏览器正常发送它；Secure限制Cookie在安全传输条件下发送；SameSite影响跨站携带Cookie的规则，但仍需按具体登录流和请求路径设计CSRF防护。常见措施包括框架自带的CSRF校验、不可预测且正确绑定的token、适当来源校验和Cookie策略。参见 [OWASP CSRF防护](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)。

防XSS要看数据最终进入HTML、属性、URL还是脚本上下文，选择适当输出编码和安全API；输入一个通用转义函数不能自动覆盖所有上下文。允许用户提交富文本时，还需使用适合的净化机制。详见前文XSS来源。

### SSRF文件访问与审计

服务端代用户抓取URL时，需要考虑SSRF：用户可能诱导服务端访问原本不应访问的位置。设计上应限定目标、协议与网络出口，并考虑解析结果、重定向及地址变化，不只检查输入字符串前缀，见 [OWASP SSRF防护](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)。文件下载与上传接口则需考虑路径规范化、文件类型、存储位置和访问权限，不能把用户文件名直接当可信路径。

审计日志应保留谁在何时对什么对象执行了什么动作及结果，并能关联请求；密码、完整访问令牌等敏感信息应排除。日志本身也要访问控制和完整性保护。对象授权、输入处理、凭证管理和日志是相互配合的控制，各自解决不同问题。

## 八 六道补充练习与解析

### SE11 条件覆盖不等于判定覆盖

**题目：** 按逻辑真值表分析 `A AND B`，不计程序短路。测试集合为 `(真,假)`、`(假,真)`。是否满足条件覆盖与判定覆盖？怎样用三组输入展示两个条件分别独立影响判定？

**答案：** 满足题设的条件真值覆盖，不满足判定覆盖，因为两次整体都为假。选择 `(真,真)`、`(假,真)`、`(真,假)`：第一与第二只变A并改变结果，第一与第三只变B并改变结果。

**推理：** 分别列出A、B两列可看到各有真假；再计算结果列为假、假，缺少整体为真。不要用输入列的覆盖替代输出列覆盖。

**易错点：** 实际语言若短路，某次B可能没被求值；真实覆盖报告要按工具定义和执行轨迹判断。关联知识：条件、判定与MC/DC。

### SE12 吞吐量与尾延迟计算

**题目：** 在10秒观测窗口内完成100个请求，其中2个失败。所有100个延迟样本中，95个为100毫秒，5个为5000毫秒。算完成QPS、成功QPS、失败率、平均延迟、P95与P99。分位数采用升序后第 `ceil(p×n)` 个样本。

**答案：** 完成QPS=10，成功QPS=9.8，失败率2%；平均延迟345毫秒，P95=100毫秒，P99=5000毫秒。

**推理：** `100/10=10`，`98/10=9.8`，`2/100=2%`；平均 `(95×100+5×5000)/100=345`。第95个样本仍是100，第99个已经是5000。

**易错点：** P95不是平均值的95%，各机器的P95也不能简单平均得到全局P95。题目只给一个观测窗口，不能据此推断长期稳态容量或CPU瓶颈。关联知识：指标分母、分位数与长尾。

### SE13 CSRF与Cookie多选

**题目：** 哪些说法正确？

- A. HttpOnly令浏览器完全不再发送Cookie
- B. CSRF可能在攻击页面无法读取目标响应的情况下造成状态变更
- C. 只要存在CORS限制，所有CSRF都会被自动阻止
- D. 应结合会话传递方式和接口设计进行CSRF校验，不能只看是否开启HTTPS

**答案：B、D。** A混淆脚本读取与浏览器自动携带；B描述CSRF的关键边界；C把跨域读限制当成所有请求都不会发生；D区分传输保护和请求授权。

**易错点：** “攻击者读不到响应”不代表请求没有执行。关联知识：浏览器凭证、CORS、CSRF。

### SE14 JWT与消息认证多选

- A. 对JWT载荷做Base64url解码后，字段就可无条件信任
- B. 常见签名JWT不自动隐藏载荷内容
- C. 令牌签名有效后仍需要核验适用声明及对象授权
- D. 把消息和普通SHA-256摘要一起发送，就足以防止有能力同时修改二者的人篡改消息

**答案：B、C。** A缺少真实性、有效期等验证；B区分签名与加密；C补齐接受令牌的上下文和业务授权；D忽略攻击者可以重算无密钥摘要。

**易错点：** JWT是格式与相关处理机制，不等于完整会话生命周期方案。关联知识：签名、MAC、哈希与授权。

### SE15 共享历史中的撤销单选

**题目：** 一个普通提交已被团队拉取，希望通过新增一条可审阅记录撤销其改动，应优先理解哪个操作？

- A. revert该提交，检查反向补丁并处理可能的冲突
- B. 直接删除整个仓库目录
- C. 用reset改写本地分支后，认为其他人的历史已自动同步
- D. 只修改提交说明，认为代码也随之恢复

**答案：A。** revert以新提交表达撤销，保留可追溯历史；B与目标无关且破坏性大，C不会自动改变其他人的仓库，D不改变代码快照。

**易错点：** revert也可能冲突；撤销合并提交还要理解主线选择，不能机械套用普通提交例子。关联知识：工作区、提交历史与协作。

### SE16 事务提交后发送事件场景题

**题目：** 业务事务写入“已批准”和发件箱事件后提交。后台发送成功，但在记录已发送之前崩溃。重启后事件再次发送。是否证明发件箱无用？应补哪些处理和测试？

**答案：** 不证明无用。发件箱把业务状态和待发送事实原子地保存，仍可能重复投递。接收方应使用稳定事件标识去重，并将去重记录与本地业务效果置于适当的原子边界；发送方有重试、退避、监控和失败处理。

**推理：** 发送成功与“已发送”标记之间跨系统，崩溃后本地无法仅凭未标记就确定外部没执行。至少测试：发送前崩溃后补发、发送后标记前崩溃后重投、同事件并发到达、处理后响应丢失、不同事件不被误去重、持续失败可被发现。

**易错点：** 网络返回成功、数据库事务提交和外部副作用恰好一次，是不同层面的保证。关联知识：幂等、事务边界、可靠消息与故障注入。

拓展达标：能手算SE12并说明各指标口径；能用真值表区分覆盖要求；能解释XSS、CSRF和对象越权分别怎样发生；能为重复投递写出数据层预期，而不只检查返回值。
