## 一 先建立做题顺序

| 问题 | 应先做的事 | 不能只凭什么判断 |
|---|---|---|
| 求候选键 | 写属性闭包，再检验最小性和是否枚举完整 | 某一张样例表没有重复 |
| 判范式 | 找全部候选键、主属性，再逐条检查依赖 | 只看选定的主键 |
| 判断分解 | 分别检查无损连接和依赖保持 | 表更小、没有重复字段 |
| 判断串行化 | 列冲突边，检查先行图 | 最后金额恰好正确 |
| 判断可恢复性 | 找读自关系，再看提交次序 | 调度没有死锁 |
| 计算执行代价 | 明确页数、缓冲页、索引和输出是否计费 | SQL语句更短 |

数据库约束应表达所有合法状态。眼前只有两行数据，不能据此证明永远成立的函数依赖。例如员工姓名目前唯一，不等于业务允许把姓名用作候选键。

## 二 函数依赖、闭包与候选键

### 2.1 闭包为什么要反复计算

`X → Y` 表示在任意合法关系实例中，两行只要X相同，Y就必须相同。`X+` 是依据给定依赖能从X推出的全部属性。

闭包计算从X自身开始。只要某条依赖左边已经全部包含在当前集合中，就加入右边；反复扫描直到不再增长。不能只扫一遍，因为后面的依赖可能使前面的依赖变得可用。

Armstrong公理可记为：自反性、增广性、传递性。自反性解释为什么X能决定自身；增广性允许在两边同时加相同属性；传递性允许沿依赖链继续推。分解、合并等规则可以从它们推导。

### 2.2 超键、候选键与主属性

若 `X+` 包含关系全部属性，X是超键。若去掉X中任意一个属性都不再是超键，X才是候选键。“最小”指集合不能再删，不是候选键之间只保留属性数量最少的一组。主属性是属于至少一个候选键的属性，不能只按已选主键判定。

在给定依赖集合中，从未出现在任何右侧的属性不能从其他属性产生，因此每个候选键都必须包含它。它是枚举起点，不是万能捷径；所有属性都在右侧时，仍需系统枚举。找到候选键后，不再检查包含它的更大集合是否也是候选键。

### 2.3 最小覆盖怎么求

常用步骤：右边拆成单属性；逐一删除左边多余属性；再删除整条冗余依赖。每次修改后重新计算，保持与原集合等价。检验 `XA → B` 中A是否多余，可以求X在当前依赖集下的闭包，看是否包含B；检验整条依赖是否冗余，必须先暂时移除该条，再求闭包。最小覆盖可能不唯一。

### DBX-01 候选键为什么只有一个

**题目：** R(A,B,C,D,E)，F={A→BC，B→D，CD→E}。求所有候选键，并解释为什么不是AB。

**解析：** 从A开始，依次得到BC、D，再由CD得到E，所以 `A+ = ABCDE`。A从未在依赖右边出现，因此任意候选键必须含A；而A本身已经是超键，加入其他属性就不再最小。因此唯一候选键是A，AB只是超键。

**易错点：** 算出一个键后就停笔。本题还必须利用“A不能由其他属性产生”证明没有遗漏。

### DBX-02 最小覆盖中的两种删除

**题目：** F={A→BC，B→C，A→B，AB→D}，求一个最小覆盖。

**解析：** 拆右边并去重得 {A→B，A→C，B→C，AB→D}。因A→B，从A就能凑齐AB并推出D，所以AB→D中的B多余，改为A→D。移除A→C后，A仍通过B推出C，因此它也冗余。结果为 **{A→B，B→C，A→D}**。

反向核对：结果能推出原来的A→BC及AB→D；原集合也能推出结果三条。剩余三条中删任一条，都会失去相应能力。本题不是从样例行猜依赖，而是比较两个依赖系统。

## 三 范式与分解的两个独立目标

### 3.1 判定条件

| 范式 | 在既定关系模型下应检查什么 |
|---|---|
| 1NF | 每个属性取值来自其规定的原子域；“原子”与建模需求有关 |
| 2NF | 满足1NF，非主属性不部分依赖于任何候选键的真子集 |
| 3NF | 对F+中每个非平凡依赖X→A，X是超键，或A是主属性 |
| BCNF | 对F+中每个非平凡依赖X→A，X必须是超键 |

这里讨论依赖右边为单属性的形式。不能把3NF简写成“没有任何传递依赖”，否则会错判右侧是主属性的情况。理论定义涉及F+；实际做题可结合等价覆盖和候选键推导，不必把所有依赖逐条列满。

### 3.2 无损连接不等于依赖保持

**无损连接**要求任意满足原约束的关系，投影到子表后再自然连接，恰好还原原关系。关系投影再连接通常不会遗漏原元组，所谓“有损”常体现为混出了伪元组，使原来的关联信息丢失。

对仅由函数依赖刻画的二元分解R→R1、R2，无损的充要条件是交集属性能在F+中决定R1或R2。三张及以上表不能简单拿“每两张有公共字段”代替完整证明；可以逐步使用已证明无损的二元分解。

**依赖保持**要求子表中能局部检查的投影依赖合起来，足以推出原依赖。否则写入时可能需要跨表连接检查，或采用额外业务约束。BCNF分解能做到无损，但不保证同时保持全部依赖。[依据：Berkeley CS186 数据库设计](https://cs186berkeley.net/notes/note13/)

### 3.3 3NF综合算法与4NF的边界

3NF综合算法可从最小覆盖出发：为依赖X→A建立包含XA的关系；相同左部可以合并；删除被其他关系包含的冗余子关系；如果没有一个子关系包含原关系的候选键，再补一张候选键关系。标准算法保证依赖保持与无损，并不承诺所有子表都达到BCNF。

4NF处理的不是普通“一个单元格填多个值”，而是多值依赖。若一个员工会哪些语言，与持有哪些技能在业务上相互独立，把二者组合存储就会产生笛卡尔积式冗余。对非平凡多值依赖X↠Y，4NF要求X是超键。是否独立必须来自业务规则，不能看到多行就机械拆表。多值依赖与4NF的正式定义见[《Database System Concepts》作者课件第7章](https://www.db-book.com/Previous-editions/db4/slide-dir/ch7.pdf)。

### DBX-03 分解为什么多出了行

**题目：** R(A,B,C)只有两行 `(1,x,p)`、`(2,x,q)`，没有额外函数依赖。分成AB与BC后自然连接，是否无损？

**解析：** AB为 `(1,x),(2,x)`；BC为 `(x,p),(x,q)`。连接得到四行，额外出现 `(1,x,q)` 和 `(2,x,p)`，所以该实例不能还原，足以反证这种分解不是无损分解。

交集B不能决定AB或BC。“都有B”只说明能写连接条件，不能说明连接结果正确。反过来，如果业务保证B→C，这个二元分解就满足无损条件。

### DBX-04 3NF为什么仍可能违反BCNF

**题目：** R(A,B,C)，F={AB→C，C→B}。求候选键与最高范式；分解成CB、AC是否无损、依赖保持？

**解析：** A必须出现在键中。AB能决定C，AC通过C→B得到B，因此候选键为AB与AC。A、B、C都是主属性。C→B左边不是超键，但右边B是主属性，所以满足3NF、违反BCNF。

分成CB与AC后，交集C能决定CB，故无损。CB本地检查C→B；AC没有能帮助恢复AB→C的非平凡投影依赖，因此不保持AB→C。

用反例检验：AC存 `(a,c1),(a,c2)`，CB存 `(c1,b),(c2,b)`。两个子表均满足局部约束，连接却让同一个AB对应两个C。这不否定无损：无损讨论的是合法原表的投影能否还原；依赖保持讨论的是独立更新子表后能否局部守住原约束。

### DBX-05 独立多值信息怎么拆

**题目：** 某员工会中文、英语，有SQL、Python、Linux三项技能；业务规定语言与技能相互独立。用R(员工,语言,技能)完整表示，需要几行？应怎么拆？若技能实际要求指定工作语言，还能照样拆吗？

**解析：** 完整组合需2×3=6行。员工↠语言和员工↠技能成立，员工不能唯一决定语言或技能，存在非平凡多值依赖且决定项不是超键，应拆成员工语言表2行、员工技能表3行，连接可恢复全部独立组合。

若只允许“英语—Python”“中文—SQL”等特定配对，独立性前提消失。拆开再连接会制造不允许的搭配，必须保留表达配对约束的关系。不能为了范式数字更高而删除业务信息。

## 四 调度的正确性分成三条轴

### 4.1 冲突可串行化

串行调度让事务一个完成后另一个才开始。可串行化允许交错执行，但等价于某个串行次序。冲突可串行化是可串行化的一种充分条件；视图可串行化范围更宽，存在盲写时二者可能不同。

两个操作冲突需要同时满足：不同事务、同一数据项、至少一个是写。读—读不冲突。按执行顺序为冲突操作画事务间有向边；先行图无环，当且仅当该调度冲突可串行化；拓扑序就是可等价的串行顺序。[依据：Berkeley 并发控制I](https://cs186berkeley.net/notes/note11/)

### 4.2 恢复性看谁读取了谁的写入

使用 `ri(X)`、`wi(X)`、`ci`、`ai` 分别记事务i的读、写、提交、回滚。下面是在经典读写调度模型下的定义：

| 性质 | 约束 | 解决的风险 |
|---|---|---|
| 可恢复 | 若Tj读到Ti写入的值，Tj不能早于Ti提交 | 已提交事务依赖后来回滚的事务 |
| 无级联 | 只读已经提交事务写入的值 | 一个回滚引发一串读者回滚 |
| 严格 | 某事务写X后，其他事务在它结束前不能读或写X | 脏读、脏写以及复杂恢复 |

严格 ⇒ 无级联 ⇒ 可恢复。可恢复性与可串行化不是同一个条件；需要分别检查。多版本实现涉及版本选择，不能把这个单版本调度表直接当作某数据库内部全部行为。

### 4.3 两阶段锁协议与死锁

2PL把每个事务的加解锁分成增长阶段和收缩阶段；第一次解锁后不能再申请新锁。符合协议的完整调度可以保证冲突可串行化，但可能死锁，普通2PL也不保证无级联回滚。

“严格2PL”的命名存在教材差异：有的定义为排他锁持有至事务结束；把共享锁也持有至结束的版本常称严谨2PL，也有课程直接把它叫严格2PL。答题应先采用题目定义，不能只靠名称推断共享锁何时释放。[Berkeley课程采用结束时释放所有锁的版本](https://cs186berkeley.net/notes/note12/)。

先行图的边表示已经发生的冲突次序；等待图的边表示当前等待另一个事务释放资源。前者用于可串行化判断，后者用于死锁检测。2PL也不是分布式提交协议2PC；一个约束锁的时序，另一个协调多个参与者提交。

### DBX-06 把冲突边完整列出来

**题目：** 调度 `r1(X), r2(Y), w1(Y), w2(X), c1, c2` 是否冲突可串行化？

**解析：** X上的 `r1(X)` 在 `w2(X)` 前，产生T1→T2；Y上的 `r2(Y)` 在 `w1(Y)` 前，产生T2→T1。存在环，所以不是冲突可串行化。这里两个事务读的都是初值，不是脏读导致的问题。不能因为没有读未提交值，就推出可串行化。

### DBX-07 提交顺序能修复什么

**题目：** 比较三种调度：①`w1(X), r2(X), c2, a1`；②`w1(X), r2(X), c1, c2`；③`w1(X), c1, r2(X), c2`。r2均读取最近一次写入。分别判断可恢复与无级联。

**解析：** ①T2提交时依赖尚未提交的T1，随后T1回滚，调度不可恢复。②T2等T1提交后再提交，可恢复，但它读时T1尚未提交，所以不是无级联；如果T1当时回滚，T2必须跟着回滚。③先提交再读，既无级联也可恢复；本例没有其他交错写入，也严格。

**易错点：** 把“延后提交”误当成“没有脏读”。它只改变提交依赖，没有改变读取发生的时刻。

### DBX-08 保证串行化为什么还会死锁

**题目：** T1先获得A的排他锁，T2先获得B的排他锁；T1申请B，T2申请A，两者都尚未解锁。这违反2PL吗？怎么处理？

**解析：** 不违反；两者都仍处于增长阶段。T1等T2，T2等T1，等待图成环而死锁。系统可检测后选一个事务回滚释放锁，让另一个推进；应用应重试完整事务并处理重试次数。若所有相关路径事先都按统一A→B次序申请这两把锁，则可消除这个反向次序造成的死锁条件。

统一锁序不代表生产数据库永远没有死锁，实际还有隐式锁、不同索引路径和其他资源。仅超时也不能证明发生了死锁，可能只是长事务。

## 五 快照隔离与写偏斜

快照隔离可让事务看到一致的已提交快照，并检测某些并发写冲突，但两个事务更新不同的行，仍可能共同破坏跨行约束。其关键是“各自检查成立，合在一起不成立”。

以下按明确的快照隔离模型讨论，不把所有产品的“可重复读”当作同一实现。PostgreSQL 18的Repeatable Read基于快照隔离，仍可能出现串行化异常；Serializable使用额外机制检测危险依赖，事务可能因冲突失败，需要应用从头重试。[官方隔离级别说明](https://www.postgresql.org/docs/18/transaction-iso.html)

### DBX-09 两名值班人员同时下班

**题目：** A、B最初都值班，规则要求至少一人值班。两个事务在同一个初始快照下分别查询值班人数，看到2人后，各自将自己的行改成“不值班”。假设系统只检查写同一行的并发冲突，会怎样？如何防止？

**解析：** 两个写集合分别是A行、B行，没有同一行写冲突，可能都提交，最终0人值班。这是写偏斜，不是把同一行的新值覆盖掉的丢失更新。串行执行时，后执行的事务会看到只剩1人而拒绝下班。

可选方案：在真正可串行化的事务中检查并更新，遇到串行化失败重试；或让所有修改该班次的操作都先锁同一班次守卫行，再读取最新值并检查。后一方案要求所有入口遵守协议，也要核对引擎隔离级别和读取语义，不能锁完后继续用旧快照的计数。单纯给“自己那一行”加锁不足以保护整个班次。

## 六 查询代价要先写计算模型

磁盘页I/O模型把读取一页记作一次，忽略CPU和缓存命中差异。它用于比较计划，不等于真实耗时。连接代价还取决于外表/内表选择、缓冲页数、已有索引、输出写盘、排序和数据倾斜。

页嵌套循环连接把外表每一页与内表全部页匹配，输入读取代价为 `B(R) + B(R)×B(S)`。块嵌套循环可把M个缓冲页中的M−2页给外表块，另留一页读内表、一页输出，代价为 `B(R) + ceil(B(R)/(M−2))×B(S)`。这两个公式假定没有索引、每次内表扫描都要读盘、忽略输出写盘。

索引嵌套循环可能按外表每条记录探测索引；估计时必须知道树高、缓存与回表次数。Hash Join理想情况下很快，但哈希表装不进内存会分区落盘，数据倾斜也可能恶化代价。SQL结果相同，不代表优化器一定选你手算的计划。

### DBX-10 外表应该选择哪一张

**题目：** R有100页，S有40页，M=12。按上述块嵌套循环模型，分别计算两种外表选择的I/O。若改为每次只放一页外表，结果如何？

**解析：** 可放外表的缓冲为10页。R作外表：`100 + ceil(100/10)×40 = 500`；S作外表：`40 + ceil(40/10)×100 = 440`，本题选S更少。若每次仅一页外表，分别为4100与4040。块算法避免了反复扫描内表的许多轮次。

不要把M=12全部用作外表，也不要忘记向上取整。外表较小在本例占优，但带取整、缓存、索引的其他模型仍应计算，不能只背结论。

- [ ] 独立给出一个3NF但非BCNF的关系，并说明分解代价。
- [ ] 用伪元组解释有损，用局部合法而整体违法解释不保持依赖。
- [ ] 分别画先行图和等待图，不混用二者。
- [ ] 区分可恢复、无级联、严格和可串行化。
