## 二、关系模型、键与完整性约束

### 2.1 用一张表理解基本术语

假设 `客户(customer_id, id_number, name, branch_id)`：一行代表一个客户，列代表属性。关系模式是表的结构；关系实例是某一时刻的具体数据。关系理论把关系看作元组集合；实际 SQL 表和查询结果可能出现重复行，不能把“理论集合”直接套到每个 SQL 结果上。

| 概念 | 定义 | 本例 |
| --- | --- | --- |
| 超键 | 能唯一确定一行的属性集合，允许有多余属性 | `{customer_id}`、`{customer_id, name}` |
| 候选键 | 最小的超键；去掉其中任何属性后都不再能唯一确定一行 | 若业务保证身份证号唯一且必填，则 `{customer_id}`、`{id_number}` 都可能是候选键 |
| 主键 | 从候选键中选定的一组，作为主要行标识 | 选 `customer_id`；一张表有一个主键约束，可由多列组成 |
| 外键 | 对另一张表或本表的键建立引用约束 | `branch_id` 引用 `网点(branch_id)` |
| 主属性 | 至少出现在一个候选键中的属性 | 候选键为 `{customer_id}`、`{id_number}` 时，这两列均为主属性 |

候选键来自**业务规则和函数依赖**，不是看现有五行数据“恰好没有重复”。姓名当前不重复，不代表姓名将来能当候选键。外键列通常可以重复，例如很多客户属于同一网点；外键也不会自动变成主键。

### 2.2 主键、UNIQUE 与 NULL 的边界

| 约束 | 作用 | MySQL 8.4 的常见考点 |
| --- | --- | --- |
| `PRIMARY KEY` | 唯一且非空地标识一行 | 所有主键列隐含 `NOT NULL`；可为联合主键 |
| `UNIQUE` | 限制键值重复 | 若列允许 `NULL`，唯一索引允许多个 `NULL` |
| `NOT NULL` | 列不允许空值标记 | 不等于唯一，也不禁止空字符串 |
| `FOREIGN KEY` | 保证引用关系 | 非空外键值必须符合引用约束；不是要求本表中外键唯一 |
| `CHECK` | 检查业务条件 | 如余额不得小于 0；与唯一、引用约束分工不同 |

`NULL` 表示未知或缺失，不是数值 0，也不是空字符串。`NULL = NULL` 的结果不是 TRUE；检查空值使用 `IS NULL`。在 MySQL 中，可空的 `UNIQUE` 列不能简单等同于关系理论中“唯一且必有值”的候选键。版本依据见 [CREATE TABLE：PRIMARY KEY 与 UNIQUE](https://dev.mysql.com/doc/refman/8.4/en/create-table.html)。

## 三、函数依赖与范式：知道为什么拆表

### 3.1 先理解依赖，再背范式

`X → Y` 表示：任何合法数据中，只要两行的 X 相同，Y 就必须相同。例如 `网点编号 → 网点名称`。它描述业务约束，不意味着 Y 能反过来决定 X，也不是指程序先计算 X 再计算 Y。

- **完全函数依赖**：Y 依赖整个 X，不能仅依赖 X 的真子集。例如一名学员在一门课程中的成绩依赖 `(学员编号, 课程编号)`。
- **部分函数依赖**：Y 已能由联合候选键的一部分决定，例如学员姓名只依赖学员编号。
- **传递依赖**：候选键先决定一个非键属性，该属性再决定另一个非主属性，例如 `学员编号 → 网点编号 → 网点名称`。
- **平凡依赖**：右侧包含于左侧，例如 `(学员编号, 课程编号) → 学员编号`。

判断步骤：写业务依赖 → 求全部候选键 → 标出主属性 → 检查部分依赖、传递依赖和决定因素。不要只检查选定的主键；范式定义涉及全部候选键。

### 3.2 四个层次怎样区分

| 范式 | 判断条件 | 典型反例 |
| --- | --- | --- |
| 1NF | 每个单元格是当前建模粒度下的单一值，没有重复组 | “课程列表”单元格写 `数据库, 网络, 测试`，而业务需要分别管理课程 |
| 2NF | 满足 1NF，且每个非主属性完全依赖每个候选键 | 联合候选键 `(学员,课程)`，却有 `学员 → 学员姓名` |
| 3NF | 对每个非平凡依赖 `X → A`，X 是超键，或 A 是主属性 | `学员 → 网点编号 → 网点名称`，网点名称不是主属性 |
| BCNF | 对每个非平凡函数依赖，决定因素 X 都必须是超键 | 存在 `顾问 → 产品`，但顾问不能唯一确定整行 |

入门可把 3NF 记为“在 2NF 基础上消除非主属性对候选键的传递依赖”；有多个候选键时，用表中的正式定义更稳妥。BCNF 比 3NF 严格，BCNF 一定满足 3NF，反过来不成立。定义可对照 [UTA 数据库范式讲义](https://idir.uta.edu/~nyan/cse3330/slides/lecture%20notes%20on%20database%20normalization.pdf)。

### 3.3 一个从 1NF 拆到 3NF 的完整例子

建立培训成绩表：

`培训(学员编号 S, 课程编号 C, 学员姓名 N, 网点编号 B, 网点名称 BN, 课程名称 CN, 成绩 G)`

规定：学员只归属一个网点；每门课程只有一个名称；一个学员在一门课程中只有一条成绩。只考虑这些业务规则及其推导，没有其他独立函数依赖。

```text
S → N, B
B → BN
C → CN
(S, C) → G
```

第一步求键：`(S,C)` 可以推导 N、B、BN、CN、G，因而能确定全部属性；只有 S 得不到课程与成绩，只有 C 得不到学员与成绩。因此 `(S,C)` 是候选键，且在上述依赖下是唯一候选键。

第二步判 2NF：原表所有值均单一，满足 1NF；但 N、B、BN 只依赖 S，CN 只依赖 C，都是非主属性对联合候选键的部分依赖，因此不满足 2NF。

第三步消除部分依赖：

```text
学员(S, N, B, BN)       主键 S
课程(C, CN)             主键 C
成绩(S, C, G)           联合主键 (S, C)
```

此时学员表仍有 `S → B → BN`。同一网点名称会在多名学员记录中重复，改名时可能只改到一部分；这是更新异常。没有学员时可能无法单独登记网点，是插入异常；删掉最后一位学员时可能连网点信息也丢失，是删除异常。

第四步消除传递依赖：

```text
学员(S, N, B)           S 为主键；B 引用网点
网点(B, BN)             B 为主键
课程(C, CN)             C 为主键
成绩(S, C, G)           (S,C) 为主键；S、C 分别引用学员、课程
```

在限定的依赖下，这四张表满足 3NF，也满足 BCNF。连接键被保留，能还原原培训信息；给定的业务依赖也能在对应表中检查。拆表的目标包括**无损连接、依赖保持、减少冗余**，不是表越多越好。BCNF 分解可以无损，但未必保留全部依赖；3NF 分解常用于兼顾这两项性质，参见 [RPI：BCNF 与 3NF 分解](https://www.cs.rpi.edu/~sibel/csci4380/fall2026/lecture_notes/lecture7.html)。

### 3.4 为什么有 3NF 却不满足 BCNF

关系 `服务(客户 K, 产品 P, 顾问 A)`，仅有 `(K,P) → A` 与 `A → P`：一个客户对一种产品只有一名顾问；一名顾问只负责一种产品，但可服务多个客户。

候选键为 `(K,P)` 和 `(K,A)`，因此 K、P、A 全是主属性。`A → P` 的右侧 P 是主属性，符合 3NF；但 A 不能决定客户 K，不是超键，违反 BCNF。可分成 `顾问产品(A,P)` 与 `客户顾问(K,A)`；此分解无损，但原来的 `(K,P) → A` 未必能仅靠分别检查两张表保证，需要额外约束。DB-04 会具体推导。

## 四、事务、并发异常与隔离级别

### 4.1 ACID 用转账理解

将 100 元从账户甲转到账户乙，包含“甲减 100、乙加 100”两个变化：

| 属性 | 含义 | 转账中的表现 |
| --- | --- | --- |
| 原子性 A | 事务内的变化整体提交或整体撤销 | 不能只扣甲却不给乙入账 |
| 一致性 C | 在正确事务逻辑及约束下，事务把数据库从合法状态带到另一合法状态 | 金额守恒、余额约束等业务不变量继续成立 |
| 隔离性 I | 并发事务的相互影响受到隔离规则约束 | 不随意读到别人尚未提交的中间结果 |
| 持久性 D | 成功提交的结果在所要求的故障条件下可恢复 | 重启后已成功转账仍然存在 |

数据库不会自动判断你是否写错了“乙加 90”。一致性需要正确业务逻辑和必要约束。隔离性也不是所有事务必须物理上排成一列执行；可串行化要求的是结果等效于某个串行顺序。持久性依赖日志刷盘配置与存储可靠性，不能概括为“任何配置和任何硬件损坏都不会丢”。MySQL 的说明见 [InnoDB 与 ACID](https://dev.mysql.com/doc/refman/8.4/en/mysql-acid.html)。

### 4.2 四类异常分别看什么

| 异常 | 核心判断 | 极简例子 |
| --- | --- | --- |
| 脏读 | 读到了另一事务尚未提交的值 | T2 把余额改成 800，T1 读到 800，T2 后来回滚 |
| 不可重复读 | 同一事务再次读取原来的行，其值因别人提交而改变 | T1 两次读同一账户，先 1000 后 800 |
| 幻读 | 同一谓词查询的匹配行集合因别人提交而改变 | 两次查“余额大于 1000 的账户”，多出一行；删除或更新使行进入/退出集合也可能造成集合变化 |
| 丢失更新 | 并发读后写覆盖了另一方的更新 | T1、T2 都读到 100；各自计算并写 110、120，最终 120，T1 的加 10 被覆盖 |

脏读看“是否提交”；不可重复读看“原行的值”；幻读看“条件对应的行集合”；丢失更新看“写入覆盖”。丢失更新不能只按下面的三列标准隔离表死记解决方案，还要检查具体读写模式。前三类定义与标准能力可对照 [PostgreSQL 官方文档对 SQL 标准隔离规则的解释](https://www.postgresql.org/docs/18/transaction-iso.html)。这里只引用其中标准规则，不把 PostgreSQL 的具体实现当成 MySQL 行为。

### 4.3 标准隔离能力与 InnoDB 实现分开记

下表是笔试常见的 SQL 标准最低约束，“允许”代表标准不要求杜绝，**不是每个产品一定会出现**。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| Read Uncommitted，读未提交 | 允许 | 允许 | 允许 |
| Read Committed，读已提交，RC | 禁止 | 允许 | 允许 |
| Repeatable Read，可重复读，RR | 禁止 | 禁止 | 允许 |
| Serializable，可串行化 | 禁止 | 禁止 | 禁止 |

**MySQL 8.4 InnoDB 默认是 RR**；部署可以修改默认值，题干指定时以题干为准。实现中要先区分读取方式：

| 方式 | 常见语句 | 可见性及并发特点 |
| --- | --- | --- |
| 普通一致性快照读 | RC、RR 下的普通 `SELECT` | 通过 MVCC 选择可见版本，一般不为所读行加记录锁 |
| 当前读 / 加锁读 | `SELECT ... FOR UPDATE`、`FOR SHARE` | 为业务保护读取最新可用状态；冲突时可能等待，并依条件与级别加锁 |
| 修改操作 | `UPDATE`、`DELETE` | 对要处理的当前记录进行判断和修改，不能简单理解为只修改旧快照可见行 |

MVCC（多版本并发控制）不是“为事务复制整张表”。它结合读视图、行版本与 undo 信息判断版本是否可见，并能重建历史记录。详见 [InnoDB Multi-Versioning](https://dev.mysql.com/doc/refman/8.4/en/innodb-multi-versioning.html)。

RC 的每次普通一致性读建立新快照；RR 的普通一致性读通常共用**第一次一致性读**建立的快照，单独 `START TRANSACTION` 通常还没有固定它。`START TRANSACTION WITH CONSISTENT SNAPSHOT` 在 RR 下可以主动建立快照。本事务内前面语句的写入对自身可见，不能说 RR “整场事务绝对看不到新变化”。时点规则见 [一致性非锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html) 与 [START TRANSACTION](https://dev.mysql.com/doc/refman/8.4/en/commit.html)。

对于 RR，重复普通快照读通常看不到别人后来提交的新匹配行；对相应范围进行加锁读取时，gap / next-key 锁还可阻止其他事务向被保护范围插入。**这两种机制不同**：前者让查询仍读旧视图，后者让某些插入等待。若先普通读、后当前读，可能看到不同的匹配集合；若本事务随后修改了其他事务后来提交的行，也可能使这些行对自身可见。因此“RR 在所有读写组合下绝对消除幻读”不严谨。MySQL 官方也提醒谨慎混用 RR 中的锁定语句与普通读，见 [InnoDB 隔离级别](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)。

## 五、索引：用有序目录找到数据

### 5.1 B+ 树为什么适合数据库

教材常用 B+ 树解释 InnoDB 普通索引：多路分叉让树较矮，非叶节点提供搜索导航，叶层存放索引记录并按键有序，便于范围扫描。和二叉树比较，它通常能在每次页访问中利用更多分支；和哈希索引比较，它擅长顺序与范围查找。MySQL 官方文档把这类结构归在 B-tree 索引名下，参见 [InnoDB 索引物理结构](https://dev.mysql.com/doc/refman/8.4/en/innodb-physical-structure.html)。

“树很矮”不等于查询一定快：返回数百万行、需要大量回表、排序或锁等待，都可能耗时。索引还占空间，并在插入、删除、修改索引列时增加维护成本。

### 5.2 聚簇索引、二级索引、回表与覆盖

假设 `账户(id PRIMARY KEY, customer_id, status, balance)`，另有索引 `(customer_id, status)`。

- **聚簇索引**：叶节点保存行数据。InnoDB 选主键；无主键时选第一组所有列均非空的唯一索引；再没有则生成隐藏行标识建立聚簇索引。
- **二级索引**：索引记录保存索引列与主键值。通过 customer_id 找到主键 id 后，再到聚簇索引读取 balance，这一步称为**回表**。
- **覆盖索引**：所需列都能从所选索引获得。例如查 `id, status` 且按 customer_id 过滤，结构上可由上述二级索引覆盖。

这些结构规则见 [聚簇与二级索引](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)。覆盖是“所需列可由索引提供”的概念，不意味着执行时永远零聚簇访问；MVCC 可见性检查在一些情况下仍需要访问聚簇记录，见 [多版本与二级索引](https://dev.mysql.com/doc/refman/8.4/en/innodb-multi-versioning.html)。

### 5.3 联合索引左前缀要带条件理解

索引 `(customer_id, status, created_at)` 按三列依次排序。常规定位可用 `(customer_id)`、`(customer_id,status)`、三列完整组合。只给 status 时，缺少第一列，不能按普通左前缀查找直接缩小到该 status 的连续区间。`WHERE` 中条件书写顺序不决定索引列顺序，优化器可以整理条件，参见 [联合索引](https://dev.mysql.com/doc/refman/8.4/en/multiple-column-indexes.html)。

若先固定 customer_id，再对 status 做范围过滤，created_at 常不能像前两列一样继续组成简单、紧凑的定位区间；它仍可能用于索引条件过滤或覆盖。不要把“范围后条件不能继续同等定位”记成“后面的列完全没用”。

同样，“没有最左列就绝对不会访问这个索引”过强：优化器可能采用全索引扫描，某些满足限制的查询还可以采用 skip scan。版本能力见 [Range Optimization：Skip Scan](https://dev.mysql.com/doc/refman/8.4/en/range-optimization.html)。实际选不选由数据分布、成本估算及查询决定，需查看执行计划，不能只凭索引存在下结论。

## 六、执行计划、锁与安全更新

### 6.1 EXPLAIN 是估计，EXPLAIN ANALYZE 会执行

| 项目 | 入门读法 | 常见误判 |
| --- | --- | --- |
| `possible_keys` | 可供选择的候选索引 | 出现在这里不等于实际使用 |
| `key` | 当前计划选择的索引 | 使用索引不保证更快 |
| `type` | 访问方式，如 ALL、index、range、ref、eq_ref | index 通常是全索引扫描，不能等同于精准定位 |
| `rows`、`filtered` | 优化器估计扫描规模与过滤比例 | 不是实际精确行数 |
| `Extra: Using index` | 常表示结果可从索引获得 | 与 `Using index condition` 不是同一个含义 |

普通 `EXPLAIN` 提供优化器计划与估计；`EXPLAIN ANALYZE` **实际执行支持的语句**，返回实际时间、行数、循环数等，用来比较估计与实际。不能把后者当作“只看不执行”的命令；练习应在可控测试数据上进行。MySQL 8.4 的 ANALYZE 输出使用 TREE 格式，依据见 [EXPLAIN 语句](https://dev.mysql.com/doc/refman/8.4/en/explain.html) 与 [EXPLAIN 输出字段](https://dev.mysql.com/doc/refman/8.4/en/explain-output.html)。

### 6.2 锁保护的是实际访问路径

S 锁（共享）之间通常可共存；X 锁（排他）与同一记录上的其他 S / X 锁通常冲突。InnoDB 的行锁落实在索引记录上；不合适的索引可能导致扫描、锁住更多记录。不要简单说“WHERE 写主键以外的列就一定升级成表锁”。

| 锁 | 保护对象 | 用途 |
| --- | --- | --- |
| record lock | 索引记录 | 保护已存在的记录 |
| gap lock | 相邻索引值之间的空隙 | 阻止往被保护空隙插入 |
| next-key lock | 记录与其前方间隙的组合 | 在相应范围扫描中防止匹配集合被插入扩展 |

RR 下通过唯一索引等值命中已存在记录时，通常只锁该记录；范围查找则可能使用 gap / next-key。未命中、非唯一条件等不能无条件套用前一句。RC 下通常不对普通搜索保留间隙锁，但外键与重复键检查等有例外。依据见 [InnoDB Locking](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html)。

`FOR UPDATE` 必须放在明确事务边界内才能保护“先读后改”的连续步骤；提交或回滚释放相关锁。普通快照读不等于锁住读取结果，见 [Locking Reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

### 6.3 防止丢失更新的三条思路

**第一种：把条件和变化放在同一条原子更新中。** 库存扣减可以采用 `UPDATE 库存 SET 数量 = 数量 - 1 WHERE 商品编号 = ? AND 数量 > 0`，然后检查受影响行数，判断是否成功。数据库对同一记录的并发更新会协调；不要先读取旧值再把应用计算好的常量直接写回。

**第二种：确需先读后判断时，在同一事务中先加锁读，再写入。** 如读取余额使用 `FOR UPDATE`，做完关联修改后提交；任一步失败整体回滚。转账还应按固定账户顺序取得锁，并处理账户不存在、余额不足等情况。

**第三种：乐观并发控制。** 使用 version 列；更新带 `WHERE id = ? AND version = 旧版本`，同时版本加 1，检查受影响行数。0 行意味着条件不满足或发生并发冲突，应重新读取和决定是否重试。适用于需要检测“我读取以后已被别人修改”的场景。

上述办法也需要事务和业务错误处理。单独“把隔离级别改成 RR”不保证应用层读后写常量的逻辑安全。

### 6.4 死锁是循环等待，需要完整事务重试

T1 持有账户 1 的锁再等待账户 2；T2 持有账户 2 的锁再等待账户 1，形成循环。开启死锁检测时 InnoDB 可以选择一个事务回滚以打破环路；检测关闭时还可能依赖锁等待超时，不能说所有情况都会立刻自动解决。

常见降低方法：按固定顺序访问资源、缩短事务、合理索引减少扫描和锁范围。应用收到死锁失败后，应重新执行**完整业务事务**，采用有界重试并保证幂等；只重试最后一条扣款语句可能破坏转账原子性。实现建议见 [减少与处理死锁](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks-handling.html)。

## 七、日志与缓存：先掌握分工，再扩展细节

| 项目 | 所在层次与主要职责 | 先记住的边界 |
| --- | --- | --- |
| redo log | InnoDB；记录可重放的数据页修改，用于崩溃恢复 | 不是供用户执行 ROLLBACK 的日志 |
| undo log | InnoDB；保存撤销修改所需信息，并支持重建历史版本 | 同时关联原子性与 MVCC，不能只记“回滚” |
| binlog | MySQL Server；记录数据变化事件，用于复制和结合备份恢复 | 不等同于 redo，也不保证只保存 SQL 文本 |
| buffer pool | InnoDB 内存；缓存表与索引页 | 是页缓存，不是按完整 SQL 文本缓存结果集 |

分工依据分别为 [Redo Log](https://dev.mysql.com/doc/refman/8.4/en/innodb-redo-log.html)、[Undo Logs](https://dev.mysql.com/doc/refman/8.4/en/innodb-undo-logs.html)、[Binary Log](https://dev.mysql.com/doc/refman/8.4/en/binary-log.html) 与 [Buffer Pool](https://dev.mysql.com/doc/refman/8.4/en/innodb-buffer-pool.html)。

复习第二层再理解“先写日志，再把脏页逐步刷入数据文件”的思路；持久性不能只看脏页是否即时落盘。`innodb_flush_log_at_trx_commit`、`sync_binlog` 等设置会影响性能和故障时的持久性边界。第三层再学 checkpoint、LSN、redo 与 binlog 提交协调；不用在第一轮记所有参数。

MySQL 8.4 没有传统 query cache。历史上的查询结果缓存已在 8.0.3 移除，见 [MySQL 8.0.3 官方发布说明](https://dev.mysql.com/doc/relnotes/mysql/8.0/en/news-8-0-3.html)。因此“第二次 SQL 更快”可能来自 buffer pool、操作系统缓存等，不能直接归因于已移除的 query cache。应用层 Redis 缓存又是另一层。

## 八、基础 12 道原创练习与逐题解析

做题方法：先遮住答案，写出选择和判断依据；多选题要逐项判断。下面没有预填作答记录，答案中的分析不代表你已经掌握。

### DB-01：候选键、主键与外键（多选）

**题干：** 某客户表有 `customer_id、id_number、name、branch_id`。业务保证 customer_id 与 id_number 各自唯一且必填；name 可以重复；branch_id 引用网点表。表选 customer_id 为主键。哪些说法正确？

- A. `{customer_id}` 与 `{id_number}` 都是候选键。
- B. `{customer_id, name}` 是候选键。
- C. branch_id 是外键，因此客户表中不能出现重复 branch_id。
- D. 一个主键约束可以包含多列。

**答案：A、D。**

**推理与错因：** A 中两组都能唯一确定一行且无法继续删减；D 是联合主键的定义。B 虽然能唯一确定一行，却包含多余的 name，只是超键；C 混淆引用约束与唯一约束，同一网点可以有许多客户。

**易错点：** “能唯一标识”只够成为超键；成为候选键还要满足最小性。**知识关联：** 2.1 键与主属性，后续范式要先求全部候选键。

### DB-02：UNIQUE 与 NULL（单选）

**题干：** MySQL 8.4 表中 `id` 为主键，`email VARCHAR(100) UNIQUE` 允许 NULL。表已有 `(id=1, email=NULL)`。以下哪次插入本身符合这些约束？假设无其他约束。

- A. 插入 `(id=1, email='a@example.com')`。
- B. 插入 `(id=2, email=NULL)`。
- C. 插入 `(id=NULL, email='b@example.com')`。
- D. 只要 email 写了 UNIQUE，它就必定是候选键，因而题干配置不能成立。

**答案：B。**

**推理与错因：** MySQL 可空 UNIQUE 允许多个 NULL，且 id=2 不重复。A 重复主键；C 违反主键非空；D 忽略了 UNIQUE 允许 NULL，与理论候选键的“必有值”要求不等价。规则已按 [MySQL 8.4 CREATE TABLE](https://dev.mysql.com/doc/refman/8.4/en/create-table.html) 核对。

**易错点：** 不要推导成“NULL 等于 NULL，所以可重复”；SQL 的空值比较不是普通相等比较。**知识关联：** 2.2 完整性约束、SQL 第 03 章的 NULL 三值逻辑。

### DB-03：从依赖推导范式（单选）

**题干：** 使用 3.3 的培训关系，所有单元格为单一值，仅有 `S→N,B`、`B→BN`、`C→CN`、`SC→G` 及其推导。该原始关系最高满足哪一项？

- A. 1NF。
- B. 2NF。
- C. 3NF。
- D. BCNF。

**答案：A。**

**推理：** `(SC)+={S,C,N,B,BN,CN,G}`，S、C 单独都不足以确定全行，因此 SC 是候选键。主属性只有 S、C。非主属性 N、B 依赖 S，CN 依赖 C，存在部分依赖，未达到 2NF。单元格已满足单一值要求，因此是 1NF。

**其他选项错因：** B 忽略部分依赖；C 除部分依赖外，还忽略 `S→B→BN`；D 对决定因素要求更严格，S、B、C 都不是原关系的超键。

**易错点：** 不是“表里有联合主键就违反 2NF”；问题在于非主属性是否只依赖联合候选键的一部分。**知识关联：** 3.3 完整拆表例子。自测时应能不看答案写出四张最终表、主外键和拆分理由。

### DB-04：3NF 为什么不等于 BCNF（单选）

**题干：** `服务(K,P,A)` 中仅有 `KP→A` 和 `A→P` 及其推导。每一列均为单一值。关于该关系，正确的是哪项？

- A. 唯一候选键是 KP，最高仅满足 2NF。
- B. KP 与 KA 都是候选键，满足 3NF，但不满足 BCNF。
- C. A 能决定 P，因此 A 就是候选键，关系满足 BCNF。
- D. 所有属性都是主属性，所以必然满足 BCNF。

**答案：B。**

**推理：** KP 可推导 A；KA 可通过 A→P 得到 P，二者都能确定全行且是最小的。A 单独无法得到 K，故不是超键。全部属性都在某个候选键中，是主属性；A→P 的右侧为主属性，因此可满足 3NF，但其左侧不是超键，违反 BCNF。

**其他选项错因：** A 漏掉 KA；C 把“能决定某一列”当成“能决定全行”；D 把 3NF 对主属性的例外错误套到 BCNF。

**易错点：** 分成 AP 与 KA 虽能无损连接，仍可能无法在单表局部保证 KP→A。例如 AP 有 `(a1,p1)、(a2,p1)`，KA 有 `(k1,a1)、(k1,a2)`，连接后同一客户产品对应两名顾问。**知识关联：** 3.4、无损连接与依赖保持的区别。

### DB-05：ACID 对应哪种保证（多选）

**题干：** 关于一笔从甲转 100 元给乙的数据库事务，哪些解释正确？

- A. 原子性要求扣款与入账整体提交或整体撤销。
- B. 一致性意味着数据库会自动纠正应用把“乙加 100”写成“乙加 90”的错误。
- C. 隔离性用于约束该事务与其他并发事务之间的影响。
- D. 持久性关注成功提交后的结果在要求的故障条件下可恢复。

**答案：A、C、D。**

**推理与错因：** A 是事务整体性；C 是并发约束；D 是提交后的恢复保证。B 错在数据库并不知道全部业务含义；正确代码和必要约束才能维护转账不变量。

**易错点：** “余额合计不变”是业务一致性规则；“中途失败时全部撤销”是原子性，二者相关但不是同义词。**知识关联：** 4.1 ACID、7 日志分工、6.3 安全更新。

### DB-06：未提交值的读取时间线（单选）

**题干：** 账户余额最初已提交为 1000。某数据库执行如下时间线，T1 确实能读到第 2 步的 800。该现象首先属于什么？

| 时刻 | T1 | T2 |
| --- | --- | --- |
| 1 | 开始事务 | 开始事务，把余额改成 800，尚未提交 |
| 2 | 读取余额，得到 800 | 仍未提交 |
| 3 | — | ROLLBACK，余额恢复到 1000 |

- A. 脏读。
- B. 不可重复读。
- C. 幻读。
- D. 丢失更新。

**答案：A。**

**推理与错因：** T1 读取的是 T2 未提交的中间结果，A 正确；B 通常需要两次读取已提交版本之间的值变化，这里核心是未提交；C 关注谓词匹配集合变化，题干没有新增集合；D 关注更新互相覆盖，T1 没有执行写操作。

**易错点：** 是否最终回滚不是判定脏读的必要条件；只要读时另一方还未提交，就已经是脏读。题干不声明为默认 InnoDB RR，因为该级别普通读不会这样读到别人的未提交值。**知识关联：** 4.2 异常定义、4.3 标准隔离表。

### DB-07：RC 与 RR 的快照从何时开始（单选）

**题干：** MySQL 8.4 InnoDB，初始余额 100。T1 使用普通 SELECT，从未写入，执行时间线如下。分别在 RC 和 RR 下重复此场景，两次 SELECT 的结果是什么？不使用 WITH CONSISTENT SNAPSHOT。

| 时刻 | T1 | T2 |
| --- | --- | --- |
| 1 | START TRANSACTION，尚未查询 | — |
| 2 | — | 将余额从 100 改为 110 并提交 |
| 3 | 第一次普通 SELECT | — |
| 4 | — | 将余额从 110 改为 120 并提交 |
| 5 | 第二次普通 SELECT | — |

- A. RC 是 100、120；RR 是 100、100。
- B. RC 是 110、120；RR 是 110、110。
- C. RC 是 110、110；RR 是 110、120。
- D. RC 与 RR 都是 110、120，因为都禁止脏读。

**答案：B。**

**推理：** T1 第一次一致性读发生在时刻 3，因此两种级别第一次都看到已经提交的 110。RC 第二次读建立新快照，看到 120；RR 共用第一次快照，仍看到 110。

**其他选项错因：** A 把 BEGIN 时点误当成普通 RR 快照必然建立的时点；C 颠倒 RC / RR；D 把“禁止脏读”错误扩展为两者每次都读最新提交值。规则见 [一致性读](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)。

**易错点：** 如果 T1 自己写过此行，或改成 FOR UPDATE，结果判断条件就变了。**知识关联：** 4.3 两种读取方式；不可重复读与 snapshot 时点。

### DB-08：RR 快照读与当前读的区别（多选）

**题干：** MySQL 8.4 InnoDB，T1 为 RR，`账户(id PRIMARY KEY, balance, INDEX(balance))` 初始没有 balance≥5000 的行。忽略其他会话，按下表执行，T1 未做自己的写入。

| 时刻 | T1 | T2 |
| --- | --- | --- |
| 1 | 开始事务，普通 SELECT 查 balance≥5000，返回空 | — |
| 2 | — | 插入 `(id=9,balance=6000)` 并提交 |
| 3 | 再次执行相同普通 SELECT | — |
| 4 | 执行相同条件的 SELECT ... FOR UPDATE | — |

哪些判断正确？

- A. 时刻 3 的普通读仍返回空。
- B. 时刻 4 的加锁读可以看到 id=9。
- C. 如果时刻 1 已执行相应范围的 FOR UPDATE 并保持事务未结束，T2 向受保护范围插入通常会等待。
- D. T1 第一次普通 SELECT 已锁住所有将来满足条件的记录，所以题干时刻 2 必然无法提交。

**答案：A、B、C。**

**推理与错因：** A 依靠既有 RR 快照；B 的加锁读处理当前状态，T2 此时已提交；C 依靠范围上的 gap / next-key 锁保护；D 错在普通一致性读并没有承担该加锁保护。

**易错点：** B 中集合变化涉及快照读和当前读的混用，不能用它证明“相同快照连续普通读也会任意变化”；同样不能从 A 推出 RR 的任何读写组合都绝无幻读。依据见 [隔离级别](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html) 与 [InnoDB Locking](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html)。**知识关联：** 4.3、6.2、MVCC 和范围锁分工。

### DB-09：联合索引、覆盖与回表（多选）

**题干：** InnoDB 表 `账户(id PRIMARY KEY, customer_id, status, balance)` 有完整二级索引 `(customer_id,status)`。考虑 `SELECT id,status FROM 账户 WHERE customer_id=7 AND status='正常'`，以及增加返回 balance 的变体。哪些说法正确？

- A. 原查询所需列在结构上可由该二级索引覆盖。
- B. 增加返回 balance 后，若仍采用该二级索引且没有其他覆盖索引，通常需访问聚簇记录获得 balance。
- C. 把 WHERE 中 status 与 customer_id 的文字顺序调换，就会违反左前缀规则。
- D. 只有 status 条件时不能按常规左前缀直接定位，但不能据此断言优化器绝不访问该索引。
- E. 给所有列都建立索引一定能同时提高查询和写入速度。

**答案：A、B、D。**

**推理与错因：** 二级索引包含索引列与主键，A 正确；balance 不在其中，因此 B 通常需要回表；D 保留了全索引扫描、满足限制的 skip scan 等可能。C 错在 WHERE 的书写顺序不等于索引排序；E 忽略空间与维护成本，查询也由成本决定。

**易错点：** “可覆盖”是结构分析，执行中仍可能有 MVCC 聚簇访问；“索引可用”与“计划真的选用”不同。**知识关联：** 5.2、5.3、6.1；可对照 [联合索引](https://dev.mysql.com/doc/refman/8.4/en/multiple-column-indexes.html) 与 [Skip Scan](https://dev.mysql.com/doc/refman/8.4/en/range-optimization.html)。

### DB-10：执行计划里哪些是实际值（单选）

**题干：** 看到普通 EXPLAIN 输出中 `rows=1000`，后续使用 EXPLAIN ANALYZE 检查查询。哪种理解正确？

- A. rows=1000 证明本次已经真正读取恰好 1000 行。
- B. EXPLAIN ANALYZE 仍只计算计划，不会运行查询。
- C. 普通 EXPLAIN 中 rows 通常是估计；EXPLAIN ANALYZE 通过执行语句提供实际行数、时间等信息。
- D. Extra 出现 Using index，说明所有场景查询延迟必然最低。

**答案：C。**

**推理与错因：** C 正确区分预计与实测。A 把估计当精确事实；B 忽略 ANALYZE 会执行；D 把访问方式当作无条件性能排名，过滤比例、数据量、锁等待仍影响速度。

**易错点：** 同一执行计划也可能因缓存状态和并发负载出现不同耗时。本文的讲解不是对真实数据库的执行报告。**知识关联：** 6.1，依据见 [MySQL 8.4 EXPLAIN](https://dev.mysql.com/doc/refman/8.4/en/explain.html)。

### DB-11：死锁与业务重试（多选）

**题干：** 两个转账事务分别按以下顺序锁定账户，锁直到事务结束才释放。假设死锁检测开启。哪些说法正确？

| 时刻 | T1 | T2 |
| --- | --- | --- |
| 1 | 获得账户 1 的 X 锁 | — |
| 2 | — | 获得账户 2 的 X 锁 |
| 3 | 请求账户 2 的 X 锁，等待 | — |
| 4 | — | 请求账户 1 的 X 锁，等待 |

- A. 形成循环等待，属于死锁。
- B. 双方按统一的账户编号顺序取得锁，可降低这种死锁风险。
- C. 被数据库回滚的事务，只重试最后一条入账语句即可恢复完整转账。
- D. 应捕获死锁失败，按业务幂等规则有界重试完整事务。
- E. 只要使用行锁，就不可能死锁。

**答案：A、B、D。**

**推理与错因：** A 存在 T1→T2→T1 的等待环；B 避免相反顺序产生环；D 重建完整业务步骤。C 错在事务先前修改已被撤销，单独补最后一步可能造成金额不守恒；E 错在多个行锁同样能形成循环。

**易错点：** 单向等待不一定是死锁；不要把“锁等待超时”与“已检测到死锁”完全当成同一错误。统一顺序能处理此类风险，不意味着整个系统再无其他死锁来源。**知识关联：** 6.3、6.4、4.1 原子性；依据见 [处理死锁](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks-handling.html)。

### DB-12：日志与缓存分工（多选）

**题干：** 以下关于 MySQL 8.4 / InnoDB 的说法，哪些正确？

- A. undo 信息可用于撤销修改，也可用于重建一致性读需要的历史版本。
- B. redo 用于数据页修改的崩溃恢复，其职责与 undo 不同。
- C. binlog 与备份配合可以用于恢复到备份之后的时间点，也用于复制。
- D. buffer pool 按完整 SQL 文本缓存查询结果；同一 SQL 第二次更快必然是 query cache 命中。
- E. MySQL 8.4 仍保留传统 query cache，因此配置 query_cache_size 是标准优化步骤。

**答案：A、B、C。**

**推理与错因：** A 是 undo 的双重用途；B 是 redo 的恢复职责；C 是 Server 层 binlog 的重要用途。D 混淆页缓存与查询结果缓存；E 使用了过时的功能与配置，传统 query cache 已移除。

**易错点：** binlog 不等同于“只记录 SQL 文本”；redo 不等同于“只有已提交事务的日志”；崩溃恢复还需要正确识别并处理未完成事务。**知识关联：** 7 的分工表及其官方来源，4.1 原子性与持久性。

## 十、知识拓展：从业务建模到运行可靠性

这一节在原有关系、事务与索引知识上补充常见笔试方向。先读 10.1～10.6，再读恢复、复制与缓存。能解释条件和例子比机械背“数据库一定怎样”更重要。

### 10.1 ER 模型：实体、属性、联系如何建表

**实体**是需要独立标识和管理的对象，如客户、账户、网点；**属性**描述对象，如账户编号、余额；**联系**描述对象之间的业务关系，如客户持有账户。ER 图首先描述业务，转成表时再安排主键、外键与约束。

| 联系类型 | 业务例子 | 常见落表方式 | 必须确认的规则 |
| --- | --- | --- | --- |
| 一对一 | 每名员工最多有一份独立保管的档案，每份档案只属于一名员工 | 档案表的员工编号设 NOT NULL、外键与 UNIQUE，或直接作为主键并设外键 | 是“最多一份”还是“必须有一份”？外键不能自动强制每名员工都已有档案 |
| 一对多 | 一个网点管理多个账户，一个账户归属一个网点 | 把网点外键放在“多”的账户表 | 账户必须归属网点时，外键列还应 NOT NULL |
| 多对多 | 一客户可持有多个账户；联名账户可有多个客户 | 建“客户账户”联系表，保存两侧外键 | 是否允许同一客户账户对出现多次？若不允许，约束该组合唯一 |

联名账户示例：

```text
客户(customer_id 主键, name)
账户(account_id 主键, balance)
客户账户(customer_id 非空外键, account_id 非空外键, role, opened_at)
        联合主键或 UNIQUE(customer_id, account_id)
```

role 是“客户对某账户的身份”，属于**联系属性**；不能简单塞到客户表，因为同一客户在不同账户中身份可能不同。若业务要保存反复开立、解除的历史，每条联系可能还需独立标识或生效区间，不能照搬“两个外键永远就是全部主键”。

联系的“可选 / 必须参与”与“一 / 多”是两件事。`NOT NULL + FOREIGN KEY` 能约束每条子记录指向存在的父记录，却不能单独保证每个父记录至少有一个子记录。外键引用目标通常选主键或完整唯一键；不要沿用 InnoDB 对非唯一引用键的历史扩展，MySQL 8.4 已限制并弃用这类非标准用法，见 [FOREIGN KEY Constraints](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html)。

### 10.2 关系代数：选择行、投影列、连接关系

| 运算 | 记号 | 本质 | SQL 中的近似表达 |
| --- | --- | --- | --- |
| 选择 | σ 条件 (R) | 从关系中保留满足条件的元组，列不因此减少 | WHERE 筛行 |
| 投影 | π 属性列表 (R) | 保留指定属性；经典集合关系代数会去重 | SELECT DISTINCT 列列表 |
| 笛卡尔积 | R × S | 两边每行配对，理论结果规模为 m×n | CROSS JOIN |
| 条件连接 | R ⋈ 条件 S | 根据条件保留配对结果 | JOIN ... ON ... |
| 并 / 差 / 交 | R∪S、R−S、R∩S | 对类型兼容的关系做集合运算 | 对应 UNION、EXCEPT、INTERSECT；ALL 变体另有重复语义 |

“选择”是选行，“投影”是选列，不能因为 SQL 命令叫 SELECT 就把两者混淆。没有连接条件时，常见错误不是“连接自动只配同编号”，而是产生大量笛卡尔组合。

例如 `账户(account_id, branch_id)` 有 `(1,10)、(2,10)、(3,20)`：理论 `π branch_id(账户)` 是 `{10,20}`；普通 `SELECT branch_id FROM 账户` 可返回 `10,10,20`；加 DISTINCT 才得到两种值。SQL 默认保留重复的查询行为要与理论集合分开记，语义见 [MySQL 8.4 SELECT](https://dev.mysql.com/doc/refman/8.4/en/select.html)。

自然连接会对同名列建立相等联系；表新增同名列可能改变连接含义。实际查询应把业务关联条件写清楚。没有 ORDER BY 时，SQL 结果没有保证的行顺序；不能因索引存在就认定所有查询天然按主键排序。

### 10.3 类型选择：金额、字符与时间的不同要求

| 类型组 | 应理解的区别 | MySQL 8.4 易错边界 |
| --- | --- | --- |
| CHAR / VARCHAR | CHAR 按声明长度处理固定长度字符值；VARCHAR 保存变长数据与长度信息 | 声明 n 主要是字符数，实际字节取决于字符集，不能把 VARCHAR(100) 一律算成 100 字节 |
| DECIMAL / FLOAT、DOUBLE | DECIMAL 表示指定精度的小数；浮点数表示近似值 | 金额优先使用明确精度的 DECIMAL，或统一单位的整数；不要要求浮点小数计算总能精确相等 |
| DATETIME / TIMESTAMP | 都有日期和时间；TIMESTAMP 在普通存取中按会话时区与 UTC 转换 | DATETIME 的普通无偏移值不按同一方式自动转换；两者都不保存原始时区名称 |

**字符细节：** VARCHAR 需要 1 或 2 字节的长度前缀，取决于该列可能占用的字节长度；还受行大小与字符集限制。CHAR 检索通常去除尾部填充空格，VARCHAR 保留存入的尾部空格；但**比较时**是否忽略尾部空格由 collation 的 PAD SPACE / NO PAD 等规则决定。存储、取回、比较是三个问题，不能据此说“VARCHAR 的尾部空格比较一定不同”。依据见 [CHAR and VARCHAR](https://dev.mysql.com/doc/refman/8.4/en/char.html)。

**数值细节：** `DECIMAL(6,2)` 的 6 是总十进制位数，2 是小数位数，整数部分最多 4 位，常见有符号范围为 -9999.99～9999.99。它不是“小数点前 6 位再加 2 位”。精度与范围有限，额外小数位、溢出和模式设置仍需考虑；若程序先把金额转成浮点再传入，也不能用 DECIMAL 自动找回已丢失的精度。依据见 [定点类型](https://dev.mysql.com/doc/refman/8.4/en/fixed-point-types.html) 与 [浮点类型](https://dev.mysql.com/doc/refman/8.4/en/floating-point-types.html)。

**时间细节：** 对未指定小数秒精度的常见形式，DATETIME 范围为 `1000-01-01 00:00:00`～`9999-12-31 23:59:59`，TIMESTAMP 的 UTC 范围为 `1970-01-01 00:00:01`～`2038-01-19 03:14:07`。两者均支持最多 6 位小数秒，也都支持按声明设置自动初始化 / 更新，不是 TIMESTAMP 专属。需要存 2040 年合同到期日期时，不能无条件选 TIMESTAMP。以上是 **MySQL 8.4** 规则，别把其他数据库或 Unix 时间函数的范围套过来，见 [DATE、DATETIME、TIMESTAMP](https://dev.mysql.com/doc/refman/8.4/en/datetime.html)。

时区例子：会话设为 +08:00，向 TIMESTAMP 存入无偏移文本 `2026-10-03 12:00:00`，代表 UTC 的 04:00；改为 +00:00 读取时显示 04:00。同样普通输入的 DATETIME 仍显示 12:00。真正需要跨地域表达一个时间点时，要在应用和数据库之间约定时区；当地“每天 09:00 开门”还包含地点与日历规则，不能仅靠一种时间列解决。

### 10.4 SQL 分类与 DELETE / TRUNCATE / DROP

| 类别 | 管理什么 | 常见语句 |
| --- | --- | --- |
| DDL，数据定义 | 表、索引等对象结构 | CREATE、ALTER、DROP、TRUNCATE |
| DML，数据操作 | 行的读取或修改 | INSERT、UPDATE、DELETE；MySQL 文档也把 SELECT 列在数据操作语句下 |
| DCL，数据控制 | 权限 | GRANT、REVOKE |
| TCL，事务控制 | 事务边界与保存点 | START TRANSACTION、COMMIT、ROLLBACK、SAVEPOINT |

部分教材把 SELECT 单独称为 DQL。先看题干采用的分类，别把命名差异误解成实际执行语义不同。

下面限定 **MySQL 8.4、普通非临时 InnoDB 表、语句成功执行**。DELETE 的回滚还要求显式事务未提交，且期间没有隐式提交。

| 比较项 | DELETE | TRUNCATE TABLE | DROP TABLE |
| --- | --- | --- | --- |
| 删除对象 | 指定行，或不带条件删全表行 | 清空整张表的行 | 表结构与全部数据 |
| WHERE | 可以 | 不可以 | 不适用 |
| 用户事务 ROLLBACK | 未提交的 InnoDB 删除可撤销 | 引起隐式提交，不能由用户回滚恢复 | 普通表引起隐式提交，不能由用户回滚恢复 |
| DELETE 触发器 | 对实际删除行触发对应触发器 | 不触发 | 不逐行触发；该表的触发器一并被删除 |
| AUTO_INCREMENT | 普通 DELETE 不按 TRUNCATE 的方式重置计数器 | 重置起始值 | 表已不存在 |

TRUNCATE 不是“自动提交的 DELETE 别名”，它是 DDL；存在其他表外键引用时，InnoDB 通常禁止该表 TRUNCATE，不能想当然地绕开引用完整性。依据见 [DELETE](https://dev.mysql.com/doc/refman/8.4/en/delete.html)、[TRUNCATE TABLE](https://dev.mysql.com/doc/refman/8.4/en/truncate-table.html) 与 [DROP TABLE](https://dev.mysql.com/doc/refman/8.4/en/drop-table.html)。

特别注意：`BEGIN → UPDATE → TRUNCATE 另一普通表 → ROLLBACK` 不能保证撤销前面的 UPDATE，因为 TRUNCATE 之前会结束当前事务。MySQL 8.4 支持的**原子 DDL**关注 DDL 自身在故障中的整体性，不等于“用户能把 DDL 与 DML 放在一个可自由撤销的事务里”。临时表 CREATE / DROP 有不隐式提交的例外，但这类创建 / 删除本身仍不可用户回滚；具体边界见 [隐式提交语句](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html)。

### 10.5 CHECK、NULL 与联合唯一：约束要一起看

1. `CHECK(amount > 0)` 拒绝 FALSE，但接受 TRUE 或 UNKNOWN；当 amount 为 NULL 时，通常得到 UNKNOWN。因此若要求金额必须有值且大于 0，应结合 `NOT NULL`。WHERE 只保留 TRUE，与 CHECK 的通过条件不同。
2. `UNIQUE(user_id, request_key)` 限制的是**组合键值**，不要求 user_id 或 request_key 各自全局唯一；`(7,'a')` 和 `(8,'a')` 可以同时存在。
3. 在 MySQL 可空联合唯一索引中，若组合的某列为 NULL，可以出现多条相同非空部分加 NULL 的记录，例如多条 `(7,NULL)`。用联合唯一约束防重复请求时，还需要求参与键列非空。
4. CHECK 默认 ENFORCED；显式 NOT ENFORCED 不检查数据。它也不能直接使用子查询去统计其他行，例如仅靠 CHECK 表达“全表账户总余额固定”不可行。

8.4 的 CHECK 核心规则见 [CHECK Constraints](https://dev.mysql.com/doc/refman/8.4/en/create-table-check-constraints.html)，唯一索引规则见 [CREATE TABLE](https://dev.mysql.com/doc/refman/8.4/en/create-table.html)。旧资料中“MySQL 只解析 CHECK、不实际检查”针对早期版本；8.0.16 起开始支持核心 CHECK 功能，历史说明见 [MySQL 8.0 CHECK](https://dev.mysql.com/doc/refman/8.0/en/create-table-check-constraints.html)，不能用于否定本章 8.4 的约束。

### 10.6 视图、存储过程与触发器：谁主动执行

| 对象 | 主要作用 | 典型例子 | 不提供的自动保证 |
| --- | --- | --- | --- |
| 普通视图 View | 为查询提供逻辑接口；封装列、过滤与连接 | 只显示客户编号和脱敏信息的查询入口 | 不是创建时冻结的数据快照；不能认为所有视图都可写 |
| 存储过程 Procedure | 在数据库端封装一组操作，由调用者 CALL | 统一校验与更新一组关联记录 | 不因封装就天然原子，也不保证比普通 SQL 快 |
| 触发器 Trigger | 由指定表的 INSERT / UPDATE / DELETE 事件自动触发 | 行变更时维护另一张审计表 | 不是应用显式 CALL 的过程；TRUNCATE 与外键级联动作不调用对应行触发器 |

普通视图不持久保存查询结果；MySQL 8.4 不提供原生持久化物化视图。查询过程中优化器使用临时物化结果，不等于存在可长期刷新管理的物化视图，见 [Views FAQ](https://dev.mysql.com/doc/refman/8.4/en/faqs-views.html)。含 GROUP BY、聚合、DISTINCT 等的视图通常不可更新；不能把汇总行当作唯一基础行直接修改，见 [视图可更新性](https://dev.mysql.com/doc/refman/8.4/en/view-updatability.html)。视图可以配合权限隐藏数据，但权限配置和 SQL SECURITY 边界仍须正确。

存储过程减少重复步骤、可能减少客户端往返；实际性能仍看查询、索引、数据量和执行计划。过程内的 `BEGIN ... END` 是**语句块**，不是 START TRANSACTION 的别名；过程是否自己控制事务，必须与调用者约定，不能假定过程失败就自动回滚调用者的全部事务。基础语法见 [定义存储程序](https://dev.mysql.com/doc/refman/8.4/en/stored-programs-defining.html)。

MySQL 触发器是行级：一次 UPDATE 改 100 行，对应触发器可能执行 100 次。INSERT 中 NEW 表示新行；DELETE 中 OLD 表示旧行；UPDATE 可以比较 OLD 与 NEW。触发器不能显式开始或结束事务，也不能另发 UPDATE 去修改触发它的语句已经使用的表；BEFORE 触发器可用 `SET NEW.列 = ...` 调整待写入值，是不同机制。相关限制见 [触发器语法](https://dev.mysql.com/doc/refman/8.4/en/trigger-syntax.html) 与 [存储程序限制](https://dev.mysql.com/doc/refman/8.4/en/stored-program-restrictions.html)。

采用 InnoDB 审计表时，触发器写入通常随原语句和事务一起成功或回滚；如果审计表是非事务引擎，不能套用同样保证。触发器失败使调用语句失败，**不代表事务更早的所有语句一定已经整体回滚**，应用仍要处理事务边界。触发器中的工作还会增加写入开销与隐含依赖。

### 10.7 WAL、崩溃恢复与备份恢复各解决什么

**WAL（预写日志）原则**：与某次修改有关的日志先持久化，再允许相应的数据文件页面落盘。它不是要求每个事务提交时都立刻刷新所有修改页，也不是“只在 COMMIT 时才开始产生日志”。这一通用原则可对照 [PostgreSQL 官方 WAL 解释](https://www.postgresql.org/docs/18/wal-intro.html)；这里不把 PostgreSQL 日志格式或参数当成 InnoDB 实现。

把 InnoDB 中的数据页、redo 与 undo 串起来理解：修改先发生在内存页上，生成相应恢复信息；脏页可能随后逐步落盘。崩溃恢复利用 redo 补齐需要重做的修改，并处理崩溃时尚未完成的事务。**未提交的修改也可能涉及已落盘页面和 redo**，因此不能把恢复概括成“重放日志就把所有事务当作成功”。日志刷盘配置影响可承诺的持久性；checkpoint 标记恢复与日志回收进度，不是一次“全体业务提交”。具体恢复流程见 [InnoDB Recovery](https://dev.mysql.com/doc/refman/8.4/en/innodb-recovery.html)。

| 恢复材料 / 策略 | 能做什么 | 边界 |
| --- | --- | --- |
| 全量备份 | 保存一个基准数据状态 | 只能直接恢复到该备份状态，之后变化需要其他材料 |
| 增量备份 | 保存某基准之后的一段变化 | 依赖基准备份和完整变化链，不是任意单份增量都可独立恢复 |
| 逻辑备份 | 保存 SQL / 行等逻辑内容 | 便于逻辑迁移，恢复大型数据可能较耗时 |
| 物理备份 | 保存数据文件等物理内容 | 需匹配备份工具、版本与一致性要求，不能随意复制运行中的文件就称为可靠备份 |
| binlog 时间点恢复 | 在恢复基准后重放后续变化到目标边界 | 需保留覆盖区间的完整日志，并确认备份对应位置和事务边界 |

“全量 / 增量”与“逻辑 / 物理”是两组不同维度；binlog 事件可用于增量恢复，不等于所有增量备份工具都只能备份 binlog。分类见 [Backup and Recovery Types](https://dev.mysql.com/doc/refman/8.4/en/backup-types.html)。

误删例子：00:00 有一致全量备份，10:00 提交了错误 DELETE；若保留了从备份位置到 10:00 的完整 binlog，可在**隔离恢复环境**加载备份，重放到错误事务开始前，再核验数据。不能把错误 DELETE 也重放后期待它自动被忽略。应识别事件位置和事务边界，时间字符串不是处理跨时区或并发提交的万能定位器，见 [binlog 恢复](https://dev.mysql.com/doc/refman/8.4/en/point-in-time-recovery-binlog.html) 与 [按事件位置恢复](https://dev.mysql.com/doc/refman/8.4/en/point-in-time-recovery-positions.html)。本文仅解释流程，不执行用户真实库上的恢复命令。

RPO 是目标可容忍的数据损失窗口，RTO 是目标恢复所需时间；它们是方案指标，不是“买了备份就自动得到”的保证。只有实际恢复演练、校验备份可读性与日志链，才能知道恢复目标能否达到。

### 10.8 主从复制：收到日志不等于查询已能读到

MySQL 官方常用 source / replica，也就是学习资料中的主库 / 从库。可概括为：主库发送 binlog → 从库接收并写 relay log → 应用线程执行对应事务。接收和应用是不同阶段，网络、长事务、从库资源不足等均可能造成延迟，见 [Replication Threads](https://dev.mysql.com/doc/refman/8.4/en/replication-threads.html)。

```text
时刻 1：主库写入新余额并提交，向客户端返回成功。
时刻 2：客户端读从库；该从库尚未应用对应事务，仍返回旧余额。
时刻 3：从库应用完成；在合适的新读视图中可读到该变化。
```

这属于复制可见性延迟，不必然是单个数据库事务中的脏读或幻读。读写分离不能自动保证**读己之写**：用户刚写成功，随后就能看到自己的提交结果。

常见应对：对紧跟写入的关键读取路由到主库；或携带已提交事务的 GTID，等待目标从库执行完成再在该从库建立合适的新读视图。`WAIT_FOR_EXECUTED_GTID_SET` 应检查成功、超时和错误，不能等完一个从库却转去另一从库读，见 [GTID 等待函数](https://dev.mysql.com/doc/refman/8.4/en/gtid-functions.html)。固定“等 1 秒再读”只能降低部分场景出现旧值的概率，不能在所有负载下证明复制已完成。

半同步复制通常等待指定数量从库收到并落下日志的确认，**不是等待所有从库都执行并提交了事务**；还要考虑超时后的模式行为，见 [Semisynchronous Replication](https://dev.mysql.com/doc/refman/8.4/en/replication-semisync.html)。复制也不能代替独立历史备份：误删可能同步到从库。即便从库已应用完成，复用此前建立的 RR 快照仍可能读旧值；读取路由、复制进度与事务快照要一起判断。

### 10.9 乐观锁版本列：一次完整的冲突时序

假设账户 `(id=1, balance=100, version=9)`，版本列非空。两个业务操作读后计算新余额，且**所有修改路径都遵守版本检查和递增规则**：

| 时刻 | 业务 A | 业务 B |
| --- | --- | --- |
| 1 | 读到余额 100、版本 9，计划加 10 | — |
| 2 | — | 读到余额 100、版本 9，计划加 20 |
| 3 | 条件更新：余额设 110，版本加 1，WHERE id=1 AND version=9；影响 1 行并提交 | — |
| 4 | — | 条件更新：余额设 120，版本加 1，WHERE id=1 AND version=9；影响 0 行 |

B 不能把“SQL 没报语法错误”当作更新成功；版本已经是 10，不再满足条件。B 若允许重试，必须读取新值并重新验证、计算：如重新读到 110 后加 20，应写 130，而不是强行把旧计算结果 120 覆盖回去。若使用 RR 长事务，反复普通读可能还停留在旧快照，重新开始事务等合适的重读方式也要设计。

示意语句中的问号由驱动参数绑定，不是直接字符串拼接：

```sql
UPDATE account
SET balance = ?, version = version + 1
WHERE id = ? AND version = ?;
```

同时检查账户存在、金额合法、余额限制等业务条件。0 行也可能因为账户不存在或其他条件不满足，不应无条件断言“必然是版本冲突”。跨多行操作仍需事务；外部请求重复还需幂等规则。乐观锁的“乐观”是先允许业务读与计算、写时检测冲突，**不是底层 UPDATE 不加锁**；冲突多时也可能反复失败，不能声称始终比加锁读更快。底层更新访问规则可对照 [InnoDB 隔离级别](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)。

### 10.10 Redis / NoSQL 与缓存三类问题：先看需求和一致性

关系数据库适合需要关系约束、连接查询和明确事务边界的数据模型。Redis 提供字符串、哈希、集合、有序集合等数据结构，可承担缓存、计数、排名等职责，结构依据见 [Redis 数据类型](https://redis.io/docs/latest/develop/data-types/)。文档数据库、宽列数据库、图数据库解决的模型与访问需求也不同，不能把 NoSQL 当作一种统一实现。

不应背“NoSQL 没有事务”或“Redis 永远不会丢数据”：事务范围、持久化、复制与故障保证都要查具体产品、版本及配置。例如 MongoDB 支持多文档事务，见 [MongoDB Transactions](https://www.mongodb.com/docs/manual/core/transactions/)。本节只要求会按数据模型、读取方式、一致性需求与故障恢复成本进行比较，不扩展成产品安装清单。

**旁路缓存（cache-aside）**：读时先查缓存，未命中再查数据库并填入缓存；修改时通常先提交数据库，再使相关缓存失效。缓存与数据库是两个状态存储，流程本身不提供强一致保证，见 [Microsoft 官方 Cache-Aside 模式](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside)。

| 中文资料常用名称 | 主要触发条件 | 常见缓解办法与边界 |
| --- | --- | --- |
| 缓存穿透 | 反复查根本不存在的数据，缓存不命中且数据库也查不到 | 校验输入、短期缓存空结果、布隆过滤器；空结果不能永久屏蔽后来创建的数据，过滤器可能有假阳性 |
| 缓存击穿 | 某个热点键失效，大量并发同时回源 | 合并同键请求、单飞重建、预热或受控使用旧值；重建失败、等待超时仍需处理 |
| 缓存雪崩 | 大量键集中失效或缓存整体不可用，数据库承受集中流量 | 分散过期时间、限流与降级、提高可用性；不能仅靠 TTL 随机化解决缓存整体故障 |

这些是工程教学分类，不是三条 Redis 命令。“热点过期并发重建”在英文文档中常称 cache stampede，参考 [Redis Cache-Aside](https://redis.io/docs/latest/develop/use-cases/cache-aside/)。

**为什么先改数据库再删缓存也不是绝对安全？** 读者 R 未命中后读到了旧值，暂未回填；写者 W 提交新值并删除缓存；R 随后把先前读取的旧值填入缓存，仍会短暂读旧。必要时引入版本校验、可靠失效事件、过期兜底等，并针对业务定义可接受窗口；延迟双删也依赖时序、成功重试等条件，不能说一次操作就彻底解决所有并发一致性。

账户实际扣款不应只相信缓存余额。缓存命中、数据库版本检查、授权和事务原子性分别解决不同问题，不能彼此替代。

## 十一、补充 8 道原创练习：DB-13～DB-20

与原有 DB-01～DB-12 合计 **20 题**。下面仍按题目条件作答，没有预填个人作答结果；各选项应独立判断。

### DB-13：多对多与联系属性（多选）

**题干：** 联名账户允许一个客户持有多个账户、一个账户有多个客户；同一客户账户对最多保存一条当前联系。每位客户在不同账户中的 role 可以不同。哪些建模方式合理？

- A. 客户和账户各有独立主键，再用客户账户表保存两侧外键。
- B. 把 role 只存客户表，可完整表达客户在所有账户中的不同身份。
- C. 客户账户表中将 `(customer_id, account_id)` 设为联合主键或联合唯一，并使两列非空。
- D. 给账户表只放一个 customer_id 字段，就能完整表达任意联名客户。

**答案：A、C。**

**逐项推理：** A 的联系表能表达任意合法配对；C 防止同一对当前联系重复。B 把依赖具体配对的联系属性错放到单个客户上；D 只能记录一个客户，不能完整表达账户的多方持有人。

**易错点：** 两个独立外键不自动限制配对唯一；若要保存联系历史，主键设计还需考虑多次生效记录。**知识关联：** 10.1、2.1 键与引用完整性。

### DB-14：理论投影和普通 SELECT（单选）

**题干：** 账户关系中有三行 `(account_id, branch_id)`：`(1,10)、(2,10)、(3,20)`。经典集合关系代数中的 `π branch_id(账户)` 与 SQL `SELECT branch_id FROM 账户`，各有多少结果行？没有 DISTINCT、分组或其他处理。

- A. 3、3。
- B. 2、3。
- C. 3、2。
- D. 2、2，因为 SQL 总会自动去重。

**答案：B。**

**步骤与错因：** 先投影成 branch_id，理论集合消除重复 10，剩 10、20 两个元组；普通 SQL 保留两条 10 和一条 20，共三行。A 忽略理论集合语义；C 颠倒两种行为；D 把 DISTINCT 的作用错误赋予所有 SELECT。

**易错点：** 结果的两种值不代表返回两行；没有 ORDER BY 时也不能保证返回顺序。**知识关联：** 10.2、2.1 理论关系与 SQL 表的区别。

### DB-15：金额与时间类型边界（多选）

**题干：** 按 MySQL 8.4 规则分析，哪些说法正确？

- A. `DECIMAL(6,2)` 的 6 是总位数，不是整数部分位数。
- B. 精确到分的结算金额，直接用 FLOAT 并依赖浮点相等判断，总能准确处理。
- C. TIMESTAMP 常规存取涉及会话时区与 UTC 的转换，换会话时区可能改变显示文本。
- D. 因为数据库运行在 64 位机器上，TIMESTAMP 列就必然能存 2040 年。
- E. VARCHAR(100) 表示最多 100 个字符，不等于所有字符集下都只需 100 字节。

**答案：A、C、E。**

**逐项推理：** A 正确，整数部分最多 4 位；C 描述同一时间点在不同会话时区的常规显示；E 区分字符数和编码字节数。B 把近似类型当精确小数；D 混淆机器字长与 MySQL 8.4 TIMESTAMP 数据类型的范围。

**易错点：** DECIMAL 也有精度范围，不能保证无限大金额；DATETIME 与 TIMESTAMP 都可声明自动时间属性。**知识关联：** 10.3 及其 MySQL 类型文档。

### DB-16：删除方式、隐式提交与触发器（多选）

**题干：** MySQL 8.4 中有普通非临时 InnoDB 表 t 和对应 DELETE 触发器。没有外键、其他会话或错误。各选项在独立、重新准备的初始数据上讨论。哪些说法正确？

- A. `START TRANSACTION; DELETE FROM t WHERE id=1; ROLLBACK;` 可恢复该未提交删除；若触发器只向 InnoDB 审计表写入，该事务内审计写入也随之回滚。
- B. `START TRANSACTION; TRUNCATE TABLE t; ROLLBACK;` 一定恢复全部原行。
- C. TRUNCATE 会逐行调用该 DELETE 触发器，效果与 DELETE 完全相同。
- D. DROP TABLE t 删除表结构和数据，并删除该表的触发器。
- E. 先 UPDATE 其他表再 TRUNCATE t，最后 ROLLBACK，必然能撤销前面的 UPDATE。

**答案：A、D。**

**逐项推理：** A 是未提交事务性 DML 的撤销，触发器限定写入 InnoDB 表；D 是 DROP 的对象删除语义。B 忽略 TRUNCATE 隐式提交；C 错在 TRUNCATE 不触发 DELETE 触发器；E 忽略该 DDL 前会结束当前事务，把先前 UPDATE 提交。

**易错点：** 原子 DDL 解决故障时 DDL 自身的一致性，不能据此声称用户 ROLLBACK 能撤销它。**知识关联：** 10.4、10.6、4.1 原子性；参见 [隐式提交](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html)。

### DB-17：CHECK 与联合唯一中的 NULL（单选）

**题干：** MySQL 8.4 表 t 有 `id PRIMARY KEY`、`user_id NOT NULL`、可空 `request_key`、可空 `amount`，以及 `UNIQUE(user_id,request_key)`、默认 ENFORCED 的 `CHECK(amount>0)`。已有 `(1,7,NULL,NULL)`。下面四次插入分别独立进行，哪次符合给定约束？

- A. `(2,7,NULL,NULL)`。
- B. `(2,8,'x',0)`。
- C. `(2,7,NULL,-1)`。
- D. `(1,8,'x',10)`。

**答案：A。**

**逐项推理：** A 的 id 新增，联合 UNIQUE 允许另一条 `(7,NULL)`；amount 为 NULL，CHECK 为 UNKNOWN，可通过。B 与 C 的 amount>0 为 FALSE，被 CHECK 拒绝；D 的 id=1 重复主键。

**易错点：** “CHECK 通过”不等于值必非空；若用 request_key 去重请求却允许 NULL，就无法覆盖该空值路径。**知识关联：** 10.5、2.2、SQL 三值逻辑；见 [CHECK](https://dev.mysql.com/doc/refman/8.4/en/create-table-check-constraints.html)。

### DB-18：视图、过程和触发器的作用（多选）

**题干：** 关于 MySQL 8.4 的普通视图与存储程序，哪些说法正确？

- A. 普通视图保存逻辑查询定义，不等于创建时冻结的持久化结果快照。
- B. 含 GROUP BY 和 SUM 的汇总视图必然支持任意 UPDATE。
- C. 把两条 UPDATE 写进过程的 BEGIN ... END，就自动成为不可分割且失败时整体回滚的事务。
- D. 行级 UPDATE 触发器可查看 OLD、NEW，按规定的行事件自动执行。
- E. 触发器可以在内部 COMMIT，独立提交触发器自己的事务。

**答案：A、D。**

**逐项推理：** A 区分查询定义与持久化快照；D 是行级触发器的读取与执行方式。B 忽略视图可更新限制；C 把语句块当事务边界；E 违反触发器不能显式结束事务的限制。

**易错点：** 触发器失败会使引发它的语句失败，但不要自动推断更早所有语句都已回滚；应用还需整体事务处理。**知识关联：** 10.6，参见 [视图可更新性](https://dev.mysql.com/doc/refman/8.4/en/view-updatability.html) 与 [触发器规则](https://dev.mysql.com/doc/refman/8.4/en/trigger-syntax.html)。

### DB-19：备份恢复与复制读取（多选）

**题干：** 系统 00:00 完成一致全量备份，之后 binlog 完整保留，10:00 错误 DELETE 事务已提交。另一个正常写请求主库提交成功后，客户端立即向尚未应用该事务的异步从库读取。哪些判断正确？

- A. 可在恢复环境加载基准备份，按正确起点重放到错误 DELETE 事务之前的边界，核验后取得目标状态。
- B. 只要有实时从库，就无需保留历史备份，因为错误 DELETE 不会复制过去。
- C. 主库已提交意味着任意从库立即读取都必然得到新值。
- D. 为保障紧跟正常写入的读，可选择主库，或确认目标从库已执行对应 GTID 后在该从库使用合适的新读视图。
- E. 使用半同步复制就等于所有从库已经执行并提交完该事务。

**答案：A、D。**

**逐项推理：** A 组合完整基准备份、日志区间与正确事务边界；D 同时处理复制进度、路由和快照。B 忽略误操作传播；C 忽略接收与应用延迟；E 把半同步的接收确认当成所有节点应用完成。

**易错点：** 已提交误删不能直接用事后的 ROLLBACK 撤销；固定睡眠时长也不能证明从库已应用。**知识关联：** 10.7、10.8、4.3 RR 快照，参见 [按事件位置恢复](https://dev.mysql.com/doc/refman/8.4/en/point-in-time-recovery-positions.html)。

### DB-20：乐观锁时序与缓存失效（多选）

**题干：** 两个业务都读取 `(余额100,版本9)`。A 使用 `WHERE id=1 AND version=9` 把余额改为110、版本加1并提交。B 随后用同样版本条件，准备把自己计算的余额120写入。同时系统使用旁路缓存。哪些说法正确？

- A. B 通常影响0行，应检查结果，并按业务规则重新读取、验证和计算。
- B. B 只要把 WHERE 版本改成10，继续写旧计算结果120，就完整保留了两次加款。
- C. 采用业务乐观锁后，InnoDB UPDATE 完全不需要底层记录锁。
- D. 先提交数据库再删缓存，也仍可能遇到并发读者把旧查询结果迟到回填的情况。
- E. 一个热点键过期导致大量并发同时查询数据库，通常归为缓存击穿。
- F. 版本列条件更新自动保证缓存与数据库在所有时刻强一致。

**答案：A、D、E。**

**逐项推理：** A 中版本已变10，旧版本条件不匹配；D 存在“先读旧值→写者提交并失效→迟到回填”的竞态；E 对应单个热点失效。B 写120只保留累计20，丢失A的加10，重算应为130；C 混淆业务冲突检测与数据库写锁；F 把数据库版本校验错误扩展成跨存储一致性保证。

**易错点：** 重试不能无限循环或重复产生外部副作用；RR 下重读方式、缓存版本和请求幂等也要设计。**知识关联：** 10.9、10.10、6.3，缓存边界参见 [Cache-Aside](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside)。

- 能为一对一、一对多、多对多分别画出主外键，并指出联系属性应放在哪里。
