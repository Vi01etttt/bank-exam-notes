## 1. 这一章到底在学什么

假设你写了一个测试报告工具：最开始只能生成文本，后来要生成 HTML、PDF；最开始只发邮件，后来要发企业消息；同一种报告又要加脱敏、压缩、访问控制。如果所有变化都塞进一个大函数，修改一个需求就容易影响其他功能。

**设计模式就是对经常出现的设计问题，总结出的职责分配和对象合作方式。** 它帮助我们决定“谁负责创建对象”“谁包装谁”“谁通知谁”。它不是可以直接粘贴的完整程序，也不是排序、搜索这类计算步骤。

笔试先掌握三个词：

| 词 | 通俗解释 | 小例子 |
|---|---|---|
| 接口 / 抽象 | 对外约定能做什么，不先限定内部怎么做 | 所有发送器提供 `send(message)` |
| 耦合 | 一个模块需要知道另一个模块多少细节 | 报告器必须知道邮件服务器参数，耦合就比较强 |
| 内聚 | 一个模块内部工作是否围绕同一个目的 | 报告格式化集中在格式化模块里，内聚较好 |

“面向接口编程”指依赖稳定的行为约定。Python 不必每次都写抽象基类：传入一个支持 `send()` 的对象或一个满足约定的函数，也能表达这个思想；但参数、返回值和异常约定仍然要清楚。

**做题顺序：找变化 → 判断变化在创建、结构还是行为 → 找最贴合的模式 → 排除只长得像的选项。**

建议分三轮学习：第一轮读 §1—§3，能认出模式解决的问题；第二轮读 §4—§5，专门区分易混项；第三轮先做 §6，再读 §7 的解释，随后完成 §8 的补充题。§3.15—§3.23 补齐其余 9 种模式，§4.3—§4.5 帮助读懂对象关系并作设计取舍。不要一开始就背所有类图。

## 2. 23 种 GoF 模式总览

GoF 是 Gamma、Helm、Johnson、Vlissides 四位作者的常用简称。经典目录有 23 种模式，分创建型、结构型、行为型三类；这项目录背景可核对 [Pearson 出版社的原书介绍](https://www.pearson.com/en-us/subject-catalog/p/design-patterns-elements-of-reusable-object-oriented-software/P200000009480/9780321700698)。下表用学习用语概括各自意图。

### 2.1 创建型：对象怎么产生（5 种）

| 模式 | 英文 | 识别问题 / 记忆线索 |
|---|---|---|
| 单例 | Singleton | 在规定范围内只保留一个实例，并提供访问入口 |
| 工厂方法 | Factory Method | 保留创建入口，让子类决定创建哪种产品 |
| 抽象工厂 | Abstract Factory | 一次切换一套相互配合的产品 |
| 建造者 | Builder | 按步骤构造复杂对象，把组装过程和最终表示分开 |
| 原型 | Prototype | 从已有样本复制出新对象 |

### 2.2 结构型：对象怎么连接（7 种）

| 模式 | 英文 | 识别问题 / 记忆线索 |
|---|---|---|
| 适配器 | Adapter | 旧接口与新要求不兼容，在中间做转换 |
| 桥接 | Bridge | 两个独立变化的维度，通过组合分别扩展 |
| 组合 | Composite | 叶子和整体组成树，用相同接口处理 |
| 装饰器 | Decorator | 包装对象，按需叠加职责 |
| 外观 / 门面 | Facade | 为复杂子系统提供简单入口 |
| 享元 | Flyweight | 共享可复用的内部状态，减少大量相似对象的开销 |
| 代理 | Proxy | 代表真实对象，控制对它的访问 |

### 2.3 行为型：对象怎么分工协作（11 种）

| 模式 | 英文 | 识别问题 / 记忆线索 |
|---|---|---|
| 责任链 | Chain of Responsibility | 请求沿候选处理者传递，发送者不指定某个处理者 |
| 命令 | Command | 把请求封装成对象，便于排队、记录或撤销 |
| 解释器 | Interpreter | 用语法规则对象解释简单语言或表达式 |
| 迭代器 | Iterator | 按约定遍历聚合对象，不暴露其内部表示 |
| 中介者 | Mediator | 集中协调多个对象之间的交互 |
| 备忘录 | Memento | 保存并恢复状态，同时尽量保持封装 |
| 观察者 | Observer | 状态变化时，通知已登记的依赖者 |
| 状态 | State | 把不同状态下的行为放到不同对象中 |
| 策略 | Strategy | 把可替换的算法 / 规则分开封装 |
| 模板方法 | Template Method | 固定流程骨架，让子类定制某些步骤 |
| 访问者 | Visitor | 为稳定的对象结构增加操作，操作与元素类分离 |

**数量速记：创建 5，结构 7，行为 11，共 23。** “简单工厂”常在教材和笔试里出现，但不属于上述 23 种 GoF 模式。组合模式是一种具体模式；“组合优于继承”则是一条设计建议，二者不是同一概念。

## 3. 重点模式：问题、做法、代价

### 3.1 单例：为什么大家要拿到同一个对象

**问题：** 一个进程里有一个统一的配置管理器，调用者希望通过统一入口取得同一实例。单例控制实例数量，并提供访问方式。

常见实现思路：

- **提前创建（常被称为饿汉式）**：第一次需要前已经创建，逻辑较直观，但可能提前占用资源。
- **需要时创建（常被称为懒汉式）**：首次请求才创建，节省未使用资源的开销，但并发初始化需要额外考虑。

Python 中可把实例放在模块内，并通过函数返回。是否需要写严格的“单例类”，取决于对象生命周期和调用约束。不要把“模块里放了一个变量”解释成任何路径、任何运行环境都绝不可能产生第二个实例。

**笔试最容易出错的四个边界：**

1. 多个线程同时执行“检查是否为空 → 创建 → 保存”，可能重复创建。整体动作需要合适的同步，不能凭一句“有 GIL”就断言安全。
2. **创建阶段安全，不等于实例上的所有操作都安全。** 共享计数器、可变配置等仍要考虑并发读写。
3. 普通单例通常讨论一个进程及约定的访问入口，不会自动保证多个进程或多台机器共用同一个对象。
4. 缓存不等于严格只初始化一次。Python `functools.cache` / `lru_cache` 维护缓存的一致性，但首次并发调用仍可能多次执行被包装函数。[Python 官方 functools 文档](https://docs.python.org/3.14/library/functools.html#functools.cache)

锁可以让同一时间只有一个线程进入相应临界区；Python 也存在可关闭 GIL 的构建，不能把实现环境当成所有并发设计的保障。[Python 官方 threading 文档](https://docs.python.org/3.14/library/threading.html#lock-objects)

**代价与边界：** 单例易形成隐藏的全局依赖，导致测试互相影响。只读配置可以考虑；每个用户、请求或测试案例都有不同状态的对象，往往更适合显式传入。数据库连接池可以有统一管理入口，但不是把所有并发请求都塞进同一条数据库连接。

### 3.2 工厂方法：谁决定具体造哪一个

**问题：** 报告导出流程大体相同，但有的子类生成文本报告，有的生成 HTML 报告。希望复用流程，同时把“具体产品类型”留给子类决定。

**做法：** 基类定义创建方法，子类覆盖它返回不同产品；客户端或公共流程依赖产品的共同接口。

```python
class TextReport:
    def render(self):
        return "report"

class HtmlReport:
    def render(self):
        return "<p>report</p>"

class Exporter:
    def export(self):
        return self.create_report().render()

    def create_report(self):
        raise NotImplementedError

class HtmlExporter(Exporter):
    def create_report(self):
        return HtmlReport()

print(HtmlExporter().export())  # <p>report</p>
```

此例的识别点不是方法叫 `create_report`，而是公共流程调用创建入口，具体子类决定产品。

**与简单工厂区别：** `create_report(kind)` 内部根据 `kind` 用 `if/elif` 选择产品，是常见简单工厂写法。GoF 工厂方法的典型结构强调将具体创建决定交给子类。实际语言可以表达不同变体，笔试要按题干约定判断。

**代价：** 可能增加创建者子类；只有一两种稳定产品时，一个函数或映射表也可能够用。

### 3.3 抽象工厂：换的是整套产品

**问题：** 测试环境需要“模拟支付器 + 模拟通知器”，生产环境需要“真实支付器 + 真实通知器”。希望成套切换，避免误混。

**做法：** 同一个工厂约定 `create_payment()`、`create_notifier()` 等入口；不同具体工厂提供不同的配套产品族。客户端依赖共同接口。

关键术语：

- **产品等级 / 产品种类**：支付器、通知器是不同种类。
- **产品族**：模拟支付器和模拟通知器是一套；真实支付器和真实通知器是另一套。

**扩展方向很重要：** 新增一整套环境，通常增加具体工厂及相关产品即可；新增一个所有工厂都必须创建的产品种类，往往要改抽象工厂接口及各具体工厂。

**代价：** 工厂能组织配套创建，但不会凭空保证业务兼容性；兼容要求仍要在接口、实现和验证中体现。

### 3.4 建造者：复杂对象分几步装好

**问题：** 一份测试报告要选标题、案例明细、图表、附件，顺序和可选部分较多。把所有参数塞进一个构造函数，调用者难以理解。

**做法：** 把组装步骤放到建造者中，通过多个步骤得到最终产品。若流程需要复用，可由“指挥者”组织步骤；不是每个实现都必须有单独指挥者类。

识别点是**分步骤构造以及构造过程与表示分离**。不同建造者可以按相同构造过程得到不同形式的结果。

**代价与易错点：** 参数多是常见动机，但“方法返回 `self`、支持链式调用”本身不能证明是 GoF 建造者。简单的 Python 数据类、关键字参数已足够清楚时，不必强行增加一套建造者。

### 3.5 原型：按样本复制，而不是从零配置

**问题：** 测试案例配置复杂，大部分相同，希望复制默认样本，再修改少量字段。

**做法：** 以已有对象作为样本，复制出新的对象。复制可以是浅复制，也可以是深复制，必须按哪些部分应共享来选择。

| 操作 | 外层对象 | 嵌套可变对象 | 常见后果 |
|---|---|---|---|
| `b = a` | 还是同一个 | 还是同一个 | 只是多了一个名字，不是复制 |
| `copy.copy(a)` | 普通容器会产生新外层 | 通常保留原引用 | 改共享的内层列表可能影响原对象 |
| `copy.deepcopy(a)` | 普通容器会产生新外层 | 对支持复制的内容递归处理 | 普通嵌套列表可彼此独立，但不能假定所有资源都能复制 |

Python 官方文档说明赋值建立绑定，浅复制保留元素引用，深复制递归复制，并允许类型自定义复制行为。文件、socket 等资源不能按普通列表的方式理解。[Python 官方 copy 文档](https://docs.python.org/3.14/library/copy.html)

**代价：** 深复制可能复制了原本应该共享的数据，也可能很贵。原型不保证“复制一定比构造快”，性能取决于实际对象和复制方式。

### 3.6 适配器：两边接口不一样，帮它们接起来

**问题：** 新代码要求 `send(message)`，旧通知库只有 `push_text(text)`，又不方便改旧库。

**做法：** 适配器对外提供 `send`，内部调用旧对象的 `push_text`，必要时转换数据格式。

识别点：**解决接口不兼容**。对象适配器常通过持有旧对象实现；某些语言也可以用继承实现类适配器。

**代价与边界：** 转换不能凭空补足旧系统没有的能力，例如旧接口没有事务支持，换一个方法名也不会获得事务。不要把单纯增加日志的包装误判成适配器。

### 3.7 代理：先经过代表，再决定是否访问真实对象

**问题：** 真实服务调用昂贵，或需要权限检查。调用者希望仍按原来的服务接口调用。

**做法：** 代理代表真实对象，决定何时、如何访问它。

常见线索：远程代理、保护代理（权限控制）、虚拟代理（延迟创建）。缓存也可能放在代理中。**判断依据是意图与职责，不是“有没有一层包装”。**

**代价：** 多一层间接调用；缓存带来失效与一致性问题，远程代理也不能让网络故障自动消失。

### 3.8 装饰器：给同一个对象逐层加能力

**问题：** 发送消息时，有的需要脱敏，有的需要压缩，有的两者都要。如果每种组合都写一个子类，类的数量很快增加。

**做法：** 装饰器与被包装对象遵守相同核心接口，持有被包装对象，在委托前后加入行为；多个装饰器可以叠加。

```python
class Sender:
    def send(self, message):
        return message

class MaskSender:
    def __init__(self, inner):
        self.inner = inner

    def send(self, message):
        masked = message.replace("123456", "******")
        return self.inner.send(masked)

sender = MaskSender(Sender())
print(sender.send("code=123456"))  # code=******
```

**代价：** 叠加顺序会影响结果，排查多层包装也更难。比如先压缩再脱敏，脱敏器可能无法理解压缩后的内容。

**Python 术语提醒：** `@decorator` 是语言里的装饰器语法，可以包装函数或类；GoF 装饰器关注给对象增加职责的结构。二者有联系，但不能看到 `@` 就直接判断某题考 GoF 装饰器。

### 3.9 外观：复杂子系统留一个好用入口

**问题：** 调用者每次生成报告，都要依次调用收集器、统计器、格式化器、存储器；很容易遗漏步骤。

**做法：** 用 `ReportFacade.generate()` 提供一个较简单的入口，在里面协调多个子系统。

识别点：**简化客户端使用子系统的方式**。外观通常不要求与某个原对象保持完全相同接口，也不必禁止调用者直接访问子系统。

**代价与边界：** 外观过度膨胀会变成“什么都管”的大类；它减少客户端的使用复杂度，不代表子系统内部已经没有复杂性。

### 3.10 策略：做同一件事，具体规则可以替换

**问题：** 测试用例排序可以按耗时、风险或最近失败情况，想切换排序规则而不改执行器。

**做法：** 主流程接收一个满足约定的算法，把会变化的步骤委托给它。Python 的函数可以直接充当策略，简单问题不必创建大量策略类。

```python
def by_duration(case):
    return case["duration"]

def by_risk(case):
    return -case["risk"]  # sorted 默认升序，负值让高风险排前面

def order_cases(cases, strategy):
    return sorted(cases, key=strategy)

cases = [
    {"name": "A", "duration": 4, "risk": 8},
    {"name": "B", "duration": 1, "risk": 2},
]
print([c["name"] for c in order_cases(cases, by_duration)])  # ['B', 'A']
print([c["name"] for c in order_cases(cases, by_risk)])      # ['A', 'B']
```

**识别点：** 主流程相对稳定，可替换的是一种规则或算法。调用者通常选择策略；策略本身不一定知道其他策略。

**代价与边界：** 谁选择策略仍需设计；把一段简单且稳定的两分支逻辑拆成很多类可能得不偿失。不是所有 `if` 都需要消灭。

### 3.11 观察者：一个事件发生，让登记过的人知道

**问题：** 用例执行完毕，报告模块、告警模块、统计模块都要更新。希望执行器不直接写死每一种后续处理。

**做法：** 主题维护订阅者登记，在状态或事件变化时调用它们的更新方法；订阅者可以登记和取消登记。

核心关系是**一对多通知**。例如执行器通知 `observer.update(result)`，而不知道观察者内部怎样更新。

**代价与边界：** 要考虑取消订阅、异常处理、重复通知、通知过程中订阅列表变化等。模式本身不承诺通知顺序、异步执行、消息持久化或“恰好一次”。观察者可以同步实现；使用消息队列的发布订阅往往还引入消息中间件及额外投递语义，不能直接等同。

### 3.12 模板方法：流程顺序固定，具体步骤让子类补

**问题：** 每个导入任务都需要“读取 → 校验 → 保存”，顺序应固定，但 CSV 与 JSON 的读取方式不同。

**做法：** 基类定义总流程，在流程中调用可覆盖的步骤；子类定制步骤。可选扩展点常称为“钩子”。

识别点：**父类掌握流程骨架，子类改变局部步骤**。模板方法主要利用继承；策略主要利用组合和委托。

**代价与边界：** 子类与基类流程耦合；基类修改步骤约定，可能影响多个子类。Python 方法通常可以被覆盖，若业务要求流程绝不能被更改，还要增加相应约束与验证，不能只靠模式名称保证。

### 3.13 责任链：不确定谁处理，就沿链传下去

**问题：** 请求可以由普通处理者、特殊处理者、兜底处理者处理；发送者不想知道最后是哪一个。

**做法：** 每个处理者决定处理还是转交下一个，链的顺序可以组装。

经典识别结构是“不能处理就转交”，某个处理者接手后可以停止。实际过滤链也可能让多个节点依次执行，并在拒绝时短路；题目要看具体传递规则。

**代价与边界：** 请求可能无人处理，链序也影响结果。必须设计兜底或明确失败结果。仅仅“调用了三个函数”不够：如果固定全部执行且没有处理 / 转交责任，可能只是普通流程。

### 3.14 状态：行为跟着对象所处阶段变化

**问题：** 一笔业务处于“待确认、已成功、已关闭”等状态，同样的取消请求在不同状态下行为不同。所有分支集中在一个方法会越来越复杂。

**做法：** 把各状态的行为封装成状态对象，由上下文委托当前状态处理；状态转换可由上下文或状态对象协作完成。

识别点：**对象内部状态决定行为，并存在有意义的状态迁移**。

**代价与边界：** 简单的两三个状态用枚举和明确分支也可能更清楚；状态对象拆得过细会增加追踪成本。业务状态必须体现真实规则，模式不能代替业务校验。

### 3.15 桥接：两个维度都要变，别为每种搭配造一个子类

**问题：** 测试报告既分“简版、详版”，又分“邮件、文件”交付。如果把两种分类绑在继承层次里，就要写简版邮件报告、详版邮件报告、简版文件报告、详版文件报告；两个维度继续增加时，组合数量也增加。

**结构与原理：** 将“报告内容 / 业务抽象”和“交付实现”分成两组，通过持有实现对象连接。简版、详版负责组织内容，邮件、文件负责交付；报告调用交付接口，而不把每种交付方式写成自己的子类。这样两个维度可分别增加实现。这里的“抽象部分”指业务抽象层，不是要求 Python 一定写 `abstract` 类。

**具体场景：** `DetailedReport(sender)` 生成详细内容后委托 `sender.send(content)`；新增短信交付主要新增发送实现，新增汇总报告主要新增报告种类。若报告和交付确实独立，大体按“报告种类数 + 交付种类数”组织类，而不是为每个搭配单独造类。具体实现仍要处理哪些搭配合法。

**代价与不适用：** 多出一层接口和委托。只有一个稳定维度，或两个维度并不独立时，强行拆开可能增加绕路。桥接解决两个维度独立变化的问题；适配器解决已有接口不兼容的问题；某个对象通过构造参数获得协作者，也不能仅凭这一点断言是桥接。

### 3.16 组合：一个用例与一组用例，都可以按同一个接口处理

**问题：** 测试计划包含用例，也包含子计划；子计划还可以继续包含子计划。调用者想统计总耗时，不想在每个地方判断“这是单项还是一组”。

**结构与原理：** 叶子对象处理自己的工作；容器对象持有多个满足共同接口的子对象，递归汇总或转发请求。所有节点提供共同操作，客户端通过同一操作处理部分与整体。

```python
class Case:
    def __init__(self, seconds):
        self.seconds = seconds

    def duration(self):
        return self.seconds

class Suite:
    def __init__(self, children):
        self.children = list(children)

    def duration(self):
        return sum(child.duration() for child in self.children)

plan = Suite([Case(2), Suite([Case(3), Case(5)])])
print(plan.duration())  # 10
```

`Suite.duration()` 不需要区分子对象是 Case 还是 Suite。树形结构加上对叶子和容器的统一处理，才是这里的模式线索；单纯持有一个对象是一般的对象组合，未必是 GoF 组合模式。

**代价与不适用：** 要防止环，例如把父计划放进自己的子计划，否则递归可能无法结束；也要明确同一用例出现在两处是否应统计两次。叶子没有“添加子节点”的合理行为，接口设计可以让只有容器提供添加操作，不必强迫所有节点支持所有方法。数据没有层次，或单项与整体根本不能遵守共同操作约定时，普通列表更简单。

### 3.17 享元：相同的重数据共享，变化的位置由外部提供

**问题：** 一份大报告有十万个文本片段，许多片段使用相同字体、字号、颜色。如果每个片段都复制一份完整样式资源，会重复占空间。

**结构与原理：** 将状态分成两类：

| 状态 | 怎样理解 | 文本片段中的例子 |
|---|---|---|
| 内部状态 | 相同对象之间可复用、不随本次使用上下文变化的内容 | 字体、字号、颜色等共享样式 |
| 外部状态 | 随某次使用变化，由调用者保存或传入 | 文本内容、页面、坐标、片段所属用户 |

享元工厂按共享内容的键查找已有对象，必要时才创建新享元；客户端持有共享对象，并在使用时提供外部状态。**共享的是经过分析可共享的部分，不是所有状态。**

**具体场景：** 字体样式对象按 `(font, size, color)` 复用，多个片段指向同一样式，片段各自保留内容和坐标。样式通常设计为不可变，避免修改一个共享实例意外影响所有片段。享元可以有很多实例，例如每种样式一个；它不是要求全系统只有一个实例的单例。普通缓存重用计算结果，也不一定具有内部 / 外部状态分离的享元结构。

**代价与不适用：** 共享表本身要占空间，查找与管理也有成本；并发创建或修改需要同步策略。对象数量少、可共享部分很小，或每个对象都必须拥有独立的可变状态时，收益可能不足。不能凭“用了享元”就保证实际内存一定下降，应测量对象与索引表的总成本。

### 3.18 命令：把“待做的操作”变成能保存和传递的对象

**问题：** 测试控制台有按钮、快捷键、批量任务，都能触发同一种操作；还希望把操作排队或记录到历史。按钮不应直接包含每种具体业务实现。

**结构与原理：** 命令对象封装接收者、操作及参数，提供 `execute()`；调用者触发命令，接收者执行真正的业务。例如按钮是调用者，`RenameCaseCommand` 是命令，案例编辑器是接收者。客户端负责把三者组装好。

**具体场景：** 一个“重命名用例”命令保存编辑器、案例编号、新名称。执行时委托编辑器修改名称；若要撤销，还需保存原名称或恢复用的备忘录。队列只需要知道命令的执行入口，不必知道每条命令怎样修改案例。

**代价与不适用：** 命令数量可能增加；可序列化任务还要处理参数与接收者如何重建。**命令模式不自动保证可撤销或幂等。** 发出邮件、完成第三方扣款等外部副作用，不一定能通过“反向执行”撤销；需要业务补偿、失败处理及重试设计。一个简单、立即完成且不需要排队或历史的调用，直接调用函数也很合适。

### 3.19 迭代器：把“怎么走到下一项”从使用数据的代码中拿出去

**问题：** 用例可能保存在列表、树或分页结果中，执行器只想逐个取得案例，不想知道每种容器的内部布局。

**结构与原理：** 聚合对象提供取得迭代器的入口；迭代器保存当前位置并按约定给出下一项。遍历算法与元素的使用逻辑分开，同一个容器还可以提供不同遍历顺序。

Python 读题时区分：

- **可迭代对象（iterable）**：可通过 `iter(obj)` 取得迭代器，如列表。
- **迭代器（iterator）**：按迭代器协议提供 `__next__()`，结束时抛 `StopIteration`；其 `__iter__()` 返回自身。它自身保存进度，通常不能通过再次调用 `iter()` 回到开头。
- **生成器（generator）**：实现迭代器协议的一种方便方式，已经消耗的同一生成器不会自动从头重播。

```python
cases = ["A", "B", "C"]
first = iter(cases)
second = iter(cases)
print(next(first), next(second), next(first))  # A A B
```

两个列表迭代器分别保存位置；不是列表本身只能供一个读者按顺序使用。官方协议依据见 [Python：Iterator Types](https://docs.python.org/3.14/builtins/stdtypes.html#iterator-types)。

**代价与不适用：** 惰性读取可能把 I/O 错误推迟到遍历时；遍历期间修改容器的行为也要按具体容器约定判断，模式本身不保证线程安全。只需要固定索引访问的小列表，不必再手工造一套迭代器类；直接使用 Python 现成协议即可。

### 3.20 中介者：让相互影响的对象找一个协调者

**问题：** 筛选面板有“部门、人员、日期、查询按钮”。部门变化要重载人员，选择不完整要禁用按钮。若每个控件直接认识其他所有控件，交互规则会散落在各处。

**结构与原理：** 各参与者把事件交给中介者，中介者维护协作规则并通知相关参与者。复杂的多对多连接转为参与者与协调者的连接，参与者之间不必到处硬编码彼此。

**具体场景：** 部门控件调用 `mediator.changed("department")`，中介者重载人员候选项并重新计算按钮能否启用；日期控件变化也由中介者判断是否满足查询条件。此处中介者负责参与者之间的互动，不只是给外部用户一个简单调用入口。

**代价与不适用：** 协调规则过多时，中介者可能变成巨大类或集中瓶颈，需要按交互范围拆分。参与者本来只有一个简单、稳定关系时，直接交互也可以。与观察者比较：观察者重点是登记后的一对多通知；中介者重点是协调多个参与者的交互规则，两者可以同时使用。

### 3.21 备忘录：由对象自己保存状态，别人保管但不拆解

**问题：** 案例编辑器希望撤销修改，但外部历史管理器不应知道编辑器内部所有字段，以及字段怎样才算合法。

**结构与原理：** 发起人创建能恢复自身状态的备忘录，并负责恢复；保管者保存历史、选择要恢复的备忘录，尽量不依赖其内部内容。常见角色对应：编辑器是发起人，状态快照是备忘录，历史栈是保管者。

**具体场景：** 编辑前调用编辑器的 `save()` 得到快照，放入历史栈；撤销时取出快照交给编辑器的 `restore(snapshot)`。快照可以是不透明对象，不要求外部历史模块逐字段重建编辑器。若内部含可变列表，只保存原列表引用，后来修改会让“旧快照”一起变化，不能实现预期恢复；需要不可变表示、合适复制或增量方案。

**代价与不适用：** 大状态保存多份会占空间；要明确历史容量、敏感数据及对象版本兼容。备忘录负责状态保存 / 恢复，原型负责根据样本生成对象，命令负责封装请求；命令可以用备忘录实现撤销。内存状态恢复也不会自动撤销已发送消息或已完成的外部业务，不等同于数据库事务回滚。

### 3.22 解释器：让规则语法对应一组可求值对象

**问题：** 一个小规则语言支持数字和加法，或者支持“风险阈值 AND 分类条件”。希望规则的结构可以组合，而不是为每一种完整规则写一个特定函数。

**结构与原理：** 定义简单语法，把基本元素做成终结表达式，把组合规则做成非终结表达式，形成表达式树。各节点按共同入口解释自己，组合节点递归解释子节点；上下文可提供规则中引用的变量值。

```python
class Number:
    def __init__(self, value):
        self.value = value

    def evaluate(self):
        return self.value

class Add:
    def __init__(self, left, right):
        self.left, self.right = left, right

    def evaluate(self):
        return self.left.evaluate() + self.right.evaluate()

expr = Add(Number(2), Add(Number(3), Number(4)))
print(expr.evaluate())  # 9
```

这里 Number 是终结表达式，Add 是组合表达式。示例已经人工建好表达式树，**没有实现把输入字符串转换成树的解析器**。解析负责识别语法结构，解释负责按结构求值，这两个步骤不要混为一谈。

**代价与不适用：** 语法规则多时类数量增加，递归解释也可能成本较高；复杂语言通常需要专门的解析、编译或规则工具。只需比较一个阈值时，直接函数更清楚。Python `eval()` 会执行 Python 表达式，不能把它当作可直接接受不可信规则文本的解释器捷径。[Python 官方 eval 文档](https://docs.python.org/3.14/builtins/functions.html#eval)

### 3.23 访问者：元素种类较稳定，把经常新增的操作移出去

**问题：** 测试资产分为用例与用例组，需要统计、导出、检查命名等操作。如果每加一个操作就修改每种元素类，会不断扩大这些类的职责。

**结构与原理：** 元素提供 `accept(visitor)`，并把自己交给访问者上对应本元素类型的方法；不同访问者封装不同操作。先由具体元素选中自己的 `accept`，再由实际访问者执行相应操作，经典结构常称为双分派。Python 示例用明确的方法调用表达这种选择，不依赖 Java 式方法重载。

```python
class Case:
    def accept(self, visitor):
        return visitor.visit_case(self)

class Suite:
    def __init__(self, children):
        self.children = list(children)

    def accept(self, visitor):
        return visitor.visit_suite(self)

class CountCases:
    def visit_case(self, case):
        return 1

    def visit_suite(self, suite):
        return sum(child.accept(self) for child in suite.children)

tree = Suite([Case(), Suite([Case(), Case()])])
print(tree.accept(CountCases()))  # 3
```

新增命名检查操作，可以增加一个具备 `visit_case` / `visit_suite` 的访问者；原有 accept 入口不必为每个操作再加一个专用方法。这个示例中由访问者负责遍历子节点；其他设计也可把遍历放在元素或独立遍历器中，模式并未固定唯一遍历位置。

**代价与不适用：** 新增元素种类往往需要扩充访问者约定，并调整现有访问者；元素为访问者开放数据，也可能削弱封装。因此它较适合“元素种类稳定、操作常增加”，不适合“元素类型不停增加、只有一个简单操作”。组合描述树形整体与部分，访问者描述把操作独立组织，两者可协作而不是互相替代。

## 4. SOLID 与组合：理解“为什么这样分工”

### 4.1 五条原则

原则帮助审视设计，模式提供可选合作结构。用了某个模式，不代表所有原则自动满足。

| 原则 | 先理解问题 | 常用术语与判断 |
|---|---|---|
| S：单一职责 | 互不相关的变更挤在同一个模块，改一处容易牵连另一处 | SRP：围绕同一种职责 / 变化原因组织代码；不是“每个类只能有一个方法” |
| O：开闭 | 每增加一种规则，都要改稳定主流程 | OCP：对预期扩展提供入口，减少修改既有稳定代码；不是永远不许改任何代码 |
| L：里氏替换 | 子类表面满足类型，实际破坏父类向调用者的承诺 | LSP：可替换要保持行为契约；不能额外收紧输入要求或削弱既有结果保证 |
| I：接口隔离 | 使用者被迫依赖一大堆用不到的方法 | ISP：按使用者需要拆分接口；不是越小越碎越好 |
| D：依赖倒置 | 核心业务直接绑定经常变化的具体服务 | DIP：高层规则与低层实现依赖合适的抽象，抽象不反过来绑定易变细节 |

OCP、LSP、ISP、DIP 的概念可核对 Robert C. Martin 的原始文章 [Design Principles and Design Patterns](https://objectmentor.com/resources/articles/Principles_and_Patterns.pdf)。以上例子与学习解释为本文自行组织。

LSP 强调行为可替换，而不只是方法名一样。例如父接口承诺接受所有正数金额，子类却只接受 100 以上金额，原本合法调用就会失败。行为子类型的基础可见 Liskov 与 Wing 的原论文 [A Behavioral Notion of Subtyping](https://www.cs.cmu.edu/~wing/publications/LiskovWing94.pdf)。

**依赖注入 ≠ 依赖倒置。** 注入是从外部传入所需对象的一种手段；倒置关注依赖方向和抽象。把一个具体数据库类从构造函数参数传进来，虽然采用了注入形式，却不一定已经建立恰当的抽象边界。

### 4.2 为什么通常优先考虑组合

继承表达“是一种”：`HtmlExporter` 是一种导出器。组合表达“拥有 / 使用”：执行器拥有一个排序策略，发送装饰器拥有一个发送对象。

| 方面 | 继承 | 组合与委托 |
|---|---|---|
| 复用方式 | 子类复用 / 覆盖父类行为 | 对象持有另一个对象，并调用它 |
| 调整行为 | 常需要不同子类 | 可以替换协作对象或包装层 |
| 耦合风险 | 可能依赖父类实现细节 | 更容易围绕协作接口建立边界 |
| 成本 | 层次过深时难追踪 | 对象与委托关系过多时也难追踪 |

组合的价值在于把变化独立出来，不是禁止继承。存在清晰、稳定且满足 LSP 的“是一种”关系，或框架确实要求继承时，继承可以很合适。模板方法就是合理使用继承的一种方式。

实际取舍检查：当前确实有变化需要隔离吗？接口能否讲清楚？增加的类和间接调用是否让代码更容易维护？只为背出模式名称而增加复杂度，没有收益。

### 4.3 对象关系与 UML：先看谁使用谁，再看箭头

读类图之前先分清两个层次：类图描述类型之间的关系；运行时则是具体对象互相引用和调用。继承、关联与依赖不是同一个问题，不能把一条箭头都读成“调用”。

| 关系 | 通俗含义与例子 | 常见类图记号 |
|---|---|---|
| 一般化 / 继承 | “是一种”，HtmlExporter 是一种 Exporter | 实线加空心三角，三角指向父类 |
| 实现 | 一个类满足某个接口约定 | 虚线加空心三角，指向被实现的接口 |
| 依赖 | 定义或实现需要对方，如方法参数、创建或调用使用某类型 | 虚线普通箭头，从使用方指向被依赖方 |
| 关联 | 对象之间有结构性联系，如报告器持有发送器 | 实线；可标角色、数量与导航方向 |
| 共享聚合 | 整体与部分的分组关系，具体共享含义依模型约定 | 空心菱形放在整体端 |
| 组合聚合 | 整体对部分有较强所有权与生命周期责任；一个部分同时至多属于一个组合整体 | 实心菱形放在整体端 |

符号与聚合语义依据见 [OMG UML 2.5 规范：§7.7、§9、§11.5](https://www.omg.org/spec/UML/2.5/PDF)。共享聚合没有适用于所有模型的统一生命周期承诺；组合的删除约束也允许部分先从整体移出。**模型中的组合责任不能直接解释成 Python 执行 `del whole` 会立刻销毁所有部分。** `del` 与对象回收遵守具体语言和引用规则；不要靠一个类图符号推断运行时资源释放。[Python 官方数据模型：对象与回收](https://docs.python.org/3.14/reference/datamodel.html#objects-values-and-types)

数量标记也常考：`1` 是恰好一个，`0..1` 是零个或一个，`0..*` / `*` 是零个或多个，`1..*` 是至少一个。数量写在哪一端，就描述相对另一端对象可以关联到多少个这一端对象；例如客户到订单端为 `0..*`，表示一个客户可关联零个或多个订单。

与模式关联起来读：策略中的上下文使用 / 持有算法对象；装饰器持有一个组件；组合模式的容器持有多个共同接口的子节点。“组合优于继承”中的组合泛指对象持有与委托，**不要求所有持有关系都画成 UML 实心菱形**。

### 4.4 依赖注入与依赖倒置：一个讲对象从哪里来，一个讲代码依赖谁

直接在报告服务内部创建邮件客户端，会把服务绑定到具体邮件实现。把发送器从外部传入，可以由测试传入假发送器，由正式运行入口传入邮件发送器；这就是依赖注入的常见做法。

```python
class ReportService:
    def __init__(self, sender):
        self.sender = sender

    def publish(self, content):
        return self.sender.send(content)

class FakeSender:
    def send(self, content):
        return "saved:" + content

service = ReportService(FakeSender())
print(service.publish("report"))  # saved:report
```

**从三个角度判断：**

| 问题 | 本例如何回答 |
|---|---|
| 谁负责组装对象？ | 外部入口创建 Sender 并传入 Service，服务只接收协作者；可在专门的组装位置集中配置 |
| 谁依赖什么能力？ | 服务只依赖 `send(content)` 的约定，不使用某个邮件库的专用方法 |
| 怎样确认可替换？ | 假实现与真实现遵守同样的参数、结果和异常契约；不能只检查方法名 |

构造函数注入、方法参数注入等是传入对象的方式；DIP 是依赖方向原则。即使对象由外部传入，服务内部若判断 `isinstance(sender, SpecificMailClient)`，并调用某邮件库专用字段，仍可能依赖具体细节。Python 不必为了表达 DIP 给每个类增加抽象基类，但稳定约定必须真实存在。`Protocol`、抽象基类或清楚的文档都可帮助说明约定；类型提示本身不会自动验证运行时业务行为。[Python 官方 typing 文档](https://docs.python.org/3.14/library/typing.html)

**不必过度设计：** 一般函数参数传入就能解决的问题，不一定需要依赖注入容器。测试替身可以是简单假实现，不必强行模拟全部邮件库；生产副作用仍由真正实现负责。

### 4.5 模式选择步骤与过度设计边界

选模式时，把题干改写成一句“因为 X 经常变化，Y 不想每次跟着改”，再做下面五步：

1. **确定变化来源。** 是创建哪种对象、两个维度分别变化、算法替换、对象阶段迁移，还是保存历史 / 发出通知？
2. **确定谁承担职责。** 谁创建、谁选择、谁持有、谁通知、谁恢复？职责没说清，背名字容易混。
3. **写最小合作关系。** 例如 `执行器 → 排序函数`，或 `编辑器 → 快照，历史栈保管快照`；暂时不扩大类层次。
4. **检查边界与故障。** 共享状态是否安全，处理链有无兜底，通知失败如何处理，撤销能否覆盖外部副作用？模式没有承诺的性质要单独设计。
5. **比较更简单的实现。** 一个函数、字典映射、列表或现有协议是否已经足够？只有复杂度下降、变化更局部或契约更清楚时，再增加结构。

同一程序可同时使用多个模式。例如组合组织测试计划树，迭代器遍历计划，访问者统计资产，命令封装编辑动作，备忘录支持撤销；解释器还可生成规则树，让访问者做校验。判断笔试单选时，锁定题干正在问的职责，不必把所有协作模式都选进去。

过度设计的具体信号：为了只有一个稳定实现的步骤增加很多接口；为了可能永远不出现的需求预设层层工厂；每个简单分支都拆成一个类；把缓存、代理、装饰器叠在一起却说不清顺序。反过来，确实已有两三种独立变化或失败处理需求时，也不要因为“代码要短”把所有业务塞回一个大函数。

## 5. 易混模式对照：看意图，不只看类图

| 易混项 | 最有效的区分问题 | 识别结论 |
|---|---|---|
| 简单工厂 / 工厂方法 | 一个入口内部选择，还是让创建者子类决定？ | 前者常用集中分支，后者典型地利用子类覆盖创建方法 |
| 工厂方法 / 抽象工厂 | 决定某类产品的具体实现，还是提供一套配套产品？ | 单个创建入口与产品族是关键线索；抽象工厂可使用工厂方法实现部分创建 |
| 抽象工厂 / 建造者 | 主要关心“一套什么产品”，还是“复杂产品如何一步步构造”？ | 抽象工厂偏产品族，建造者偏构造过程与表示 |
| 原型 / 工厂 | 从样本复制，还是通过创建逻辑产生对象？ | 复制是原型的核心；它们也可以协作 |
| 适配器 / 装饰器 | 原接口不兼容，还是给原有行为增加职责？ | 适配器转换接口，装饰器保留核心接口并叠加能力 |
| 代理 / 装饰器 | 主要控制访问，还是增加可组合的职责？ | 包装结构可能相像，意图不同；日志、缓存等名字不能单独决定答案 |
| 外观 / 适配器 | 复杂入口需要简化，还是接口需要兼容转换？ | 外观简化子系统使用，适配器衔接接口 |
| 策略 / 状态 | 主动替换算法，还是当前状态决定行为及迁移？ | 两者可都用委托，但解决的问题不同 |
| 策略 / 模板方法 | 传入协作对象 / 函数，还是子类覆盖固定流程中的步骤？ | 前者偏组合，后者偏继承 |
| 观察者 / 责任链 | 通知一组依赖者，还是沿候选处理者传递请求？ | 一对多更新与处理 / 转交不同 |
| 装饰器 / 责任链 | 逐层增强同一个组件，还是寻找 / 串接请求处理者？ | 装饰器围绕统一组件职责叠加，责任链强调传递与处理规则 |
| 桥接 / 适配器 | 两个维度从设计时就要独立扩展，还是事后接入不兼容接口？ | 桥接关注独立变化维度，适配器关注兼容 |
| 享元 / 单例 | 共享哪部分相同状态，还是控制某个类型的实例数量？ | 享元可以有多个共享实例；单例关注约定范围内一个实例 |
| 命令 / 策略 | 保存与触发某个请求，还是选择完成同一任务的算法？ | 命令携带接收者与请求信息，策略提供可替换算法；可协作 |
| 命令 / 备忘录 | 保存“要执行什么”，还是“对象当时处于什么状态”？ | 前者封装请求，后者保存恢复信息，撤销可结合使用 |
| 中介者 / 观察者 / 外观 | 协调内部交互、通知依赖者，还是简化外部入口？ | 核心职责分别是协调、通知、简化使用 |
| 组合 / 访问者 / 迭代器 | 问的是树形对象结构、增加操作，还是怎样逐项遍历？ | 结构、操作、遍历分别考虑；三者可以协作 |
| 解释器 / 组合 | 问的是语法规则怎样求值，还是整体与部分怎样统一操作？ | 表达式树可具有组合结构，但解释器还强调语法和解释语义 |

补充识别：组合模式适合目录树这类“文件与文件夹统一处理”的结构；享元要求区分可共享的内部状态与由调用者提供的外部状态；命令负责把请求封装起来，是否支持撤销还需要记录足够信息；访问者适合对象结构较稳定、操作经常增加的情形，新增元素种类往往需要调整访问者。

## 7. 答案与讲解

### DP-01 解析

**答案：A、B、C。**

- A 正确：三类数量相加是 23。
- B 正确：两者处理对象如何连接和访问，归结构型。
- C 正确：两者处理协作或算法行为，归行为型。
- D 错误：简单工厂是常见创建思路，但不在 GoF 的 23 种目录中。
- E 错误：组合模式处理树形整体与部分；组合优于继承强调优先考虑持有、委托来复用行为。

**易错点：** 把所有带“工厂”“组合”的词归到同一目录。**知识关联：** §2、§4.2。

### DP-02 解析

**答案：B。**

- A 错误：集中按参数分支更像简单工厂，也不是工厂方法的必需条件。
- B 正确：典型工厂方法把具体产品的创建决定延迟给创建者子类。
- C 错误：控制实例数量是单例的主要目标。
- D 错误：从样本复制是原型的主要目标。

**易错点：** 看到 `create()` 名字就判定工厂方法，忽略谁决定产品。**知识关联：** §3.1、§3.2、§3.5。

### DP-03 解析

**答案：A。**

- A 正确：新产品族沿现有接口扩展较自然；新产品种类改变“每套要提供哪些东西”，常影响整组工厂。
- B 错误：“任意”“绝不”忽略接口变化，抽象工厂对不同扩展方向的成本不同。
- C 错误：分步骤组装是建造者的重点。
- D 错误：抽象工厂不要求单例；需要几个实例是另外的生命周期问题。

**易错点：** 不区分产品族与产品种类，以为抽象工厂对所有方向都同样容易扩展。**知识关联：** §3.3、§3.4、§5。

### DP-04 解析

**答案：B。**

逐步判断：

1. `base` 的值是包含一个列表的字典。
2. `shallow` 有新的字典外壳，但 `shallow["tags"]` 与 `base["tags"]` 指向同一列表。
3. `deep` 在追加之前创建，其普通内层列表与 `base` 的列表独立。
4. 向 `shallow["tags"]` 追加 `api`，会让 `base["tags"]` 也含有 `api`。
5. 向 `deep["tags"]` 追加 `ui`，只影响 `deep` 的列表。因此两段输出分别为 `['smoke', 'api']` 和 `['smoke', 'ui']`。

A 忽略浅复制的共享内层；C 把深复制也当成共享；D 忽略深复制发生在追加 `api` 之前。

**易错点：** 以为“外层是新对象”就表示整个对象图独立；还容易忽略语句执行顺序。**知识关联：** §3.5；[Python 官方 copy 文档](https://docs.python.org/3.14/library/copy.html)。

### DP-05 解析

**答案：A。**

- A 正确：适配器在既有接口与客户端期望接口之间转换。
- B 错误：这是备忘录的主要意图。
- C 错误：观察者模式不提供这种执行承诺，也与接口兼容无关。
- D 错误：这是责任链的主要线索。

### DP-12 解析

#### DP-13 解析

**答案：A。**

- A 正确：报告种类与交付实现是两个独立扩展的维度，持有接口对象连接二者，正是桥接的意图。
- B 错误：题干没有旧接口不兼容的要求；不能看到组合就认定适配器。
- C 错误：一个报告当前使用一个交付对象，不表示该类型只能创建一个实例。
- D 错误：交付方式不是编辑器过去状态，也没有保存 / 恢复的需求。

**易错点：** “持有一个协作者”是结构线索，不是唯一识别依据；还要检查独立变化维度。**知识关联：** §3.15、§4.4、§5。

#### DP-14 解析

**答案：A、C、E。**

- A 正确：叶子与容器使用共同接口，容器递归处理子节点，符合组合模式。
- B 错误：策略、代理和桥接等也持有协作者；一般对象组合不必形成整体与部分的递归结构。
- C 正确：三角指向较一般的父类，菱形位于整体端，两种符号含义不同。
- D 错误：设计建议中的对象组合与 UML 组合聚合并不等同，引用也可能只是关联。
- E 正确：如果形成环，朴素递归汇总可能无法结束，应对加入操作设置相应限制。

**易错点：** 把“组合模式”“组合优于继承”“UML 组合聚合”三个含有组合的术语混成一回事。**知识关联：** §3.16、§4.2—§4.3。

#### DP-15 解析

**答案：A、B、D。**

- A 正确：相同样式资源是可共享内部状态的典型候选。
- B 正确：片段位置随每次使用变化，不应被同一个共享样式对象固定为一个位置。
- C 错误：不同样式可以对应不同享元；享元关注相同部分复用，不是只有一个实例。
- D 正确：不可变的共享内容可降低意外跨对象修改风险，但不会代替所有并发管理。
- E 错误：必须把共享表、引用与查找成本一起评估，模式没有无条件的性能保证。

**易错点：** 只记“共享”而不区分内部 / 外部状态；把复用若干对象误背成单例。**知识关联：** §3.1、§3.17、§5。

#### DP-16 解析

**答案：A。**

题干保存了“向哪个接收者执行什么请求及参数”，按钮只负责触发，这符合命令模式。撤销需要能推回合法原状态的信息，例如原名称；只有新名称不能唯一推导原名称。

- A 正确：区分了请求封装与恢复能力。
- B 错误：共同接口和委托不只存在于策略；题干强调保存、触发一个具体请求。
- C 错误：外部副作用通常需要业务补偿，命令模式不自动提供完全逆操作。
- D 错误：把多个可能的原名称改成一个新名称会丢失原信息，必须额外记录。

**易错点：** 从“命令可以用于撤销”跳成“所有命令都天生可撤销”。**知识关联：** §3.18、§3.21、§4.5。

#### DP-17 解析

**答案：B。**

逐步判断：第一次 `next(cursor)` 返回 10 并前移；第一次 `list(cursor)` 消耗剩余的 20、30；此时 cursor 已结束，第二次转成列表只能得到空列表。原来的 numbers 仍是 `[10,20,30]`，如果想再次从头遍历，应重新从 numbers 取得新的迭代器。

A 忽略已消耗的 10 和迭代器进度；C 误以为第二次自动重置；D 错误，因为 list 可以消耗迭代器。

**易错点：** 混淆可重复取得新迭代器的容器，与保存当前位置的同一个迭代器。**知识关联：** §3.19；[Python 官方迭代协议](https://docs.python.org/3.14/builtins/stdtypes.html#iterator-types)。

#### DP-18 解析

**答案：A。**

- A 正确：协调对象掌握控件间互动规则，使参与者减少直接认识彼此的需要。
- B 错误：外观侧重为客户端简化子系统入口；不能把所有协调多个对象的设计都叫外观。
- C 错误：不同控件应保有各自状态，题干不要求共享相同资源。
- D 错误：没有复制样本的线索，重载选项也不等于克隆对象。

**易错点：** 仅看到“有一个中间对象”就判外观或代理，忽略它是在协调参与者的互动。**知识关联：** §3.9、§3.11、§3.20、§5。

#### DP-19 解析

**答案：A、C、E。**

- A 正确：发起人创建并恢复自己的状态，保管者管理历史。
- B 错误：保管者尽量不拆解内部状态，是保持封装的关键目标之一。
- C 正确：保留可变对象的原引用，不是真正独立的历史内容；需要选择合适快照表示。
- D 错误：内存状态恢复并不会自动取消已经完成的外部交易，二者的业务边界不同。
- E 正确：命令可保存之前的备忘录，在需要时交由发起人恢复。

**易错点：** 快照不是“随便留一个引用”，撤销也不是“所有外部副作用都自动反转”。**知识关联：** §3.5、§3.18、§3.21。

#### DP-20 解析

**答案：C。**

- A 错误：表达式对象的求值入口不自动提供字符串分词和解析。
- B 错误：历史状态与规则解释是不同职责，保存历史不是解释器的必要条件。
- C 正确：基本表达式解释自身，组合表达式解释子表达式并合并结果；字符串输入还需识别合法语法。
- D 错误：eval 执行的是 Python 表达式，不能把任意用户文本直接交给它当作安全的业务规则。

**易错点：** 把“表达式树已存在时的求值”与“字符串到表达式树的解析”混为一谈。**知识关联：** §3.22、§4.5、§5。

#### DP-21 解析

**答案：A、B、D。**

- A 正确：不同访问者承载不同操作，元素保留稳定 accept 入口。
- B 正确：每种新元素可能需要对应访问方法，因此会影响操作端；这是访问者的主要取舍。
- C 错误：遍历可以放在元素、访问者或独立遍历器，题干示例即可由访问者递归。
- D 正确：组合管理树结构，访问者管理操作，两者解决不同问题，可同时使用。
- E 错误：参数注入只说明对象传入方式；是否依赖稳定约定、遵守行为契约，仍需检查。

**易错点：** 把“新增操作方便”误解成“新增元素也永远不用改”；只看到注入形式就宣布所有原则已满足。**知识关联：** §3.16、§3.23、§4.1、§4.4。

| 按已有样本复制 | 原型 | 浅复制、深复制、共享引用 |
| 旧接口与要求不兼容 | 适配器 | 核心目的是转换接口 |
| 控制真实对象的访问 | 代理 | 权限、远程、延迟访问 |
| 同接口逐层叠加能力 | 装饰器 | 包装顺序会影响结果 |
| 子系统使用太复杂 | 外观 | 提供简单入口 |
| 同一任务有可替换算法 | 策略 | 主流程委托给外部规则 |
| 一个变化通知多个登记者 | 观察者 | 不自带异步 / 恰好一次承诺 |
| 固定骨架、子类变步骤 | 模板方法 | 主要利用继承 |
| 当前不处理就传给下一位 | 责任链 | 顺序、停止条件、无人处理 |
| 当前阶段决定行为并迁移 | 状态 | 不要只凭“有委托”判策略 |
| 两个维度分别扩展 | 桥接 | 不为每个搭配单独造子类 |
| 叶子与树形整体统一处理 | 组合 | 共同接口、递归子节点、防止环 |
| 大量重复资源共享 | 享元 | 内部 / 外部状态分离 |
| 请求要保存、排队或触发 | 命令 | 撤销与幂等需额外设计 |
| 逐项访问、不暴露容器布局 | 迭代器 | 可迭代对象与迭代器进度不同 |
| 多个参与者交互规则集中 | 中介者 | 避免协调者无限膨胀 |
| 保存历史并由对象恢复 | 备忘录 | 封装、可变引用、外部副作用 |
| 简单语法按表达式结构求值 | 解释器 | 解析与求值是两步 |
| 稳定元素类型、常新增操作 | 访问者 | 新增元素会影响访问者 |

**三组数字与五个提醒：**

- 5 / 7 / 11：创建型 / 结构型 / 行为型。
- SOLID：职责集中、可扩展、可替换、接口按需、依赖抽象。
- 单例创建一次，不代表所有操作安全。
- 工厂决定怎么获得产品；策略决定怎么完成某种行为。
- 装饰器、代理、适配器可能长得像，必须看题干意图。
- 新产品族与新产品种类，对抽象工厂的修改成本不同。
- 原型复制不自动保证深复制，也不自动保证更快。

## 12. 综合设计的选择理由与边界

补充日期：2026-10-04。本节使用原创业务场景，把前文模式放到同一条调用流程中。场景题允许不同合理实现，但必须说明职责与约束，不能看到一个关键词就确定唯一模式。

### 12.1 先找变化，再决定是否引入模式

一个需求可以按五步分析：写出稳定的业务目标；列出真正独立变化的部分；说明每部分由谁负责；检查对象的创建、调用与生命周期；最后评估失败和新增需求时要修改哪里。模式名称是对这些关系的归纳。

例如导出报表时，“选择哪个厂商的SDK”“计算哪套费用规则”“生成后如何通知”“是否记录调用指标”是不同变化点。用一个万能工厂包下所有事情，会把规则、创建和执行重新耦合在一起。

| 变化维度 | 合理分工 | 选择代价 |
|---|---|---|
| 计算规则变化 | 策略承载算法，主流程委托计算 | 策略接口过宽会强迫简单规则依赖无关数据 |
| 配套产品族变化 | 抽象工厂提供相互兼容的一组产品 | 新产品种类会影响各工厂接口和实现 |
| 遗留接口变化 | 适配器转换调用方式、数据和错误 | 不能只改方法名而忽略语义差异 |
| 能力叠加 | 装饰器包装相同接口 | 顺序、重复包装和副作用需要明确 |
| 阶段变化 | 状态对象处理阶段行为和合法迁移 | 简单枚举分支也可能足够，无需总是造类 |
| 消息接收者变化 | 观察者管理订阅与通知关系 | 持久化、重试、去重需额外机制 |

组合多个模式的前提是确有多个独立变化点。只有两个稳定分支时，一个函数参数或字典映射可能更清楚；模式收益应体现在修改范围缩小和契约清晰，而不是类的数量增加。

### 12.2 行为契约比相同方法签名更强

替换一个实现时，要检查允许的输入、承诺的输出、异常、副作用和状态不变式。子类型不能加强前置条件，不能削弱后置条件，也要维护可观察的不变式与历史约束。比如接口承诺接受非负金额，实现却拒绝0，就不能仅因方法名相同而宣布可替换。契约基础见前文[Liskov与Wing原论文](https://www.cs.cmu.edu/~wing/publications/LiskovWing94.pdf)。

缓存、代理、装饰器也要遵守这些约定。假设原查询承诺返回“调用时最新数据”，无失效策略的缓存包装会改变语义；如果契约允许最多5秒旧数据，则可据此前提设计缓存。性能、顺序和异常何时属于契约，应由接口要求明确，而不是凭模式名称自动推出。

### DP-22 多种规则与多家服务如何分工

**题目：** 报销系统按差旅或餐饮采用不同费用计算规则，同时可选择厂商甲或乙的电子凭证服务；每家厂商提供必须配套的签名器和上传器。厂商乙的旧SDK接口与系统统一接口不兼容。是否应让每一种“报销类型×厂商”对应一个子类？给出职责划分。

**解析：** 不必为所有组合造子类。费用计算可用策略对象，负责金额和规则；厂商切换可由抽象工厂创建配套签名器、上传器；乙的SDK可分别由适配器转换参数、返回值和异常。主流程依赖统一约定，将“算费用”和“生成上传凭证”组合起来。

新增费用规则通常只增加策略，新增厂商通常增加工厂及产品实现；新增整个产品种类则可能修改所有工厂，这也是抽象工厂的代价。若厂商实际上只有一个服务对象，不存在产品族，就不能仅凭“有厂商”强行选抽象工厂；简单创建函数也可能够用。

**边界：** 适配器不能凭空补齐旧服务缺少的业务保证，例如上传成功不等于对方已完成入账。需要在接口契约中明确成功的含义。

### DP-23 折扣和固定费用的包装顺序

**题目：** 基础报价100元；Discount装饰器将被包装对象返回的报价乘0.9；Fee装饰器将被包装对象返回的报价加10元。所有对象使用同一个quote接口。分别计算 `Fee(Discount(Base))` 与 `Discount(Fee(Base))`。同样的装饰器能随意交换吗？

**解析：** 内层先返回结果。前者先优惠到90，再加费到100元；后者先加费到110，再优惠到99元。两种结果都符合各包装类的局部规则，但对应的业务政策不同。业务若规定固定服务费不参加折扣，应采用前者。

用函数表达是F(D(x))与D(F(x))，加法与乘法在这里不交换。装饰器统一接口只保证可组织成调用链，不保证交换律、幂等或重复包装安全。Discount套两层会变成81折；金额精度与舍入时点还应由业务契约规定。

**延伸：** 重试包装与日志包装也会因顺序不同，记录“一次业务请求”或“每次实际尝试”。先确定希望观测的对象，再定包装顺序。

### DP-24 类型相同但行为不能替换

**题目：** Repository接口承诺 `save(record)` 接受所有合法记录，包括待分配编号的新记录，成功返回后可按返回编号查到它。某子类要求调用方预先填写编号，另一子类只是把保存任务放入队列并立即返回编号。它们都能因为方法签名相同而直接替换吗？

**解析：** 第一个实现把“编号可为空”收紧成“必须有编号”，加强前置条件，违反原契约。第二个实现如果返回时尚不能查询到记录，就削弱“成功后立即可查询”的后置条件，也不能直接替换。

可行调整要维护调用方语义：第一个实现内部生成编号，或适配到能满足原约定的服务；异步保存应使用明确的提交接口返回任务标识，并提供状态查询。若要修改原接口为最终可见，需连同调用方需求一并评估，不能只改注释宣称兼容。

**易错点：** 把继承关系、类型检查通过、依赖注入完成当作行为替换已经成立。DIP减少对具体实现的依赖，仍需要各实现遵守稳定契约。

### DP-25 观察者通知与命令重放

**题目：** 订单付款成功后，同步通知邮件、积分两个观察者；邮件发送成功，积分处理失败，系统于是重试整次通知。是否能因为用了观察者和命令对象就保证只发一封邮件、只加一次积分？应补哪些机制？

**解析：** 不能。观察者表达订阅和通知关系，命令把请求及参数封装成对象；它们都没有自动提供跨系统事务、持久化投递或恰好一次业务效果。重试整次通知可能重复邮件，也可能在积分已处理但回复丢失时重复加分。

若业务需要可靠异步处理，可在付款事务里写入业务事件记录，再由投递器发送；消费者依据事件ID持久化去重，让去重记录与积分变更在同一事务中提交。邮件服务若支持幂等键可使用其约定，否则仍需分析发送成功后记录失败造成的重复窗口。具体流程见[软件工程中的可靠消息与幂等](05_软件工程测试与安全.md)。

保存命令不意味着命令可以无限次安全重放；设计撤销也不意味着外部副作用能原样恢复。积分可按业务生成冲正记录，已经发出的邮件则不能靠恢复内存快照收回。回答场景题时，应区分对象组织方式与实际可靠性保证。

### 12.3 场景题作答模板

先写“要隔离哪种变化”，再写“哪些对象分别负责什么”，最后写“新增一种需求会改哪里、失败后会发生什么”。若题目存在多个答案，说明各自成立的条件，而不是堆砌模式名称。DP-22至DP-25都是分析题，复测时应检查推理和反例，不只核对术语。
