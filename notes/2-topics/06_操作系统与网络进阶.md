## 二、操作系统：从执行状态到文件生命周期

### 2.1 进程状态：等待事件不等于等待 CPU

常用三状态模型是就绪、运行、阻塞。就绪进程已具备运行条件，只等调度；阻塞进程还缺某个事件，例如磁盘数据到达、信号量许可或子进程退出，给它 CPU 也未必能继续。

典型转换如下：

```text
就绪 ──调度──> 运行 ──时间片到/抢占──> 就绪
运行 ──等待 I/O 或同步条件──> 阻塞
阻塞 ──相应事件完成──> 就绪 ──调度──> 运行
```

I/O 完成让进程有资格重新竞争 CPU，不保证马上运行。创建和结束状态常另外表示为新建、终止；“挂起”在扩展模型中涉及暂不参与通常调度等额外状态，不应强塞进所有三状态题中。

场景：一个报表任务等待数据库回包，另一个计算任务继续用 CPU，属于交错并发；前者回包后若仍在就绪队列，不代表回包丢失。状态与调度的基本模型见 [OSTEP：进程抽象](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-intro.pdf)。

易错边界：忙等是一直执行检查循环，可能仍处于运行/就绪状态；阻塞等待通常让出 CPU，两者不同。唤醒不是直接替被唤醒者完成后续业务。

### 2.2 IPC：共享数据后仍需定义协议

进程间通信 IPC 是跨进程交换信息的机制。选择要看通信范围、数据大小、是否需要消息边界和同步关系。

| 机制 | 工作方式与场景 | 易错边界 |
|---|---|---|
| 管道 / 命名管道 | 通过内核缓冲区交换字节，常用于本机流水处理 | 普通管道是字节流；一次写不保证对应一次读 |
| 消息队列 | 按消息组织数据，适合任务通知 | 仍需考虑容量、顺序及接收协议，不能自动当作业务事务 |
| 共享内存 | 把同一存储区域映射给多个进程，适合大量本机数据交换 | 共享可见不等于操作原子；并发访问仍需锁/信号量等 |
| 信号 | 通知事件，适合简单控制与异常通知 | 不宜当作任意大数据传输渠道；具体信号排队语义要看类型 |
| 套接字 Socket | 用端点接口通信，可用于本机或跨主机 | TCP 流仍需应用消息划分；Unix 域套接字通常用于本机 |

场景：父进程把筛选结果通过管道交给子进程；两个本机工作进程通过共享内存访问大数组，另用信号量协调读写。共享内存减少数据反复复制的机会，但不会自动解决一致性问题。

管道字节流与阻塞语义见 [Linux `pipe(7)`](https://man7.org/linux/man-pages/man7/pipe.7.html)，共享内存与同步要求见 [Linux `shm_overview(7)`](https://man7.org/linux/man-pages/man7/shm_overview.7.html)。普通管道特定大小写入的原子性，也不等于为读者保留完整业务消息边界。

### 2.3 信号量与生产者消费者：容量和互斥分别管理

有限缓冲区既不能写满后继续覆盖，也不能空了还取数据；多生产者/消费者还不能同时把索引或队列改坏，因此要管理三件事：空位数、已有项目数、队列修改权。

设容量为 N，使用 `empty=N、full=0、mutex=1`。P 表示申请许可，没有许可则等待；V 表示释放许可，必要时唤醒等待者。下面使用**非负可用许可**的直观模型；有些教材用负数表示等待者数量，做数值题时必须先确认定义。

```text
生产者：P(empty) → P(mutex) → 放入一项 → V(mutex) → V(full)
消费者：P(full)  → P(mutex) → 取出一项 → V(mutex) → V(empty)
```

先等待空位/项目，再获取修改锁。若生产者先持有 mutex，再等待 empty，缓冲区满时它可能持锁阻塞；消费者需要 mutex 才能取走项目并释放 empty，于是双方卡住。消费者在空缓冲区先持锁等 full，也有类似问题。

场景：容量有限的任务队列把生产请求与后台处理速度解耦。empty/full 解决“什么时候可以继续”，mutex 解决“谁可同时修改”。仅有 empty/full，在多线程下通常不够保护队列索引；仅有 mutex，又不能表示空/满条件。

边界：在全部操作结束、没有已预订但未完成的许可时，`empty+full=N`；并发执行中，某线程可能已 P 但未 V，所以不能把这个等式机械用于任意指令瞬间。信号量与该问题见 [OSTEP：信号量](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-sema.pdf)。

### 2.4 银行家算法：安全是一种“仍可保证”的状态

银行家算法用于死锁避免。任务先声明最大需求，系统在分配前试算：如果全部任务最终都提出剩余最大需求，是否还能找到一个让所有任务完成的顺序？它是资源模型，不是对实际银行账户业务的模拟。

三组量：`Allocation` 为已分配，`Max` 为声明上限，`Need=Max-Allocation` 为最多还要多少；`Available` 为当前空闲资源。资源有多种时，“≤”必须逐分量比较，不是比较总数。

安全性检查：

1. 令 `Work=Available`，所有任务先标为未完成。
2. 找一个未完成且 `Need ≤ Work` 的任务，假定它得到剩余需求并完成。
3. 完成后回收它原已占有的资源，执行 `Work += Allocation`，标记完成。
4. 能标记全部任务就安全；再也找不到合适任务且仍有未完成者，则不安全。

为什么不是把 Max 全部加给 Work？模拟时先从 Work 借出 Need，结束后归还 `Allocation+Need`，净增只有 Allocation。

```python
def safe_sequence(allocation, maximum, available):
    # 题设保证矩阵形状一致、资源数非负，Allocation <= Max
    need = [[m - a for a, m in zip(row_a, row_m)]
            for row_a, row_m in zip(allocation, maximum)]
    work = available.copy()
    finished = [False] * len(allocation)
    sequence = []
    while len(sequence) < len(allocation):
        progressed = False
        for i in range(len(allocation)):
            if not finished[i] and all(n <= w for n, w in zip(need[i], work)):
                work = [w + a for w, a in zip(work, allocation[i])]
                finished[i] = True
                sequence.append(i)
                progressed = True
        if not progressed:
            return None
    return sequence

allocation = [[1, 0], [0, 1], [1, 1]]
maximum = [[2, 1], [1, 2], [3, 1]]
print(safe_sequence(allocation, maximum, [1, 1]))  # [0, 1, 2]
```

n 个任务、m 种资源，朴素多轮检查最坏 `O(n²m)`，Need 表空间 `O(nm)`。新请求还应检查 `Request ≤ Need` 和 `Request ≤ Available`，试分配后检查安全，不安全则不正式分配。

安全状态一定可以在模型前提下安排完成；不安全不等于此刻已经死锁，它表示最大需求模型下不能保证完成顺序。实际任务也许并不申请全部上限，或及时释放资源。算法依赖事先知道上限，现实系统不总能使用它。安全、不安全与资源矩阵见 [UIC 操作系统官方课程笔记：死锁避免](https://www.cs.uic.edu/~jbell/CourseNotes/OperatingSystems/7_Deadlocks.html)。

### 2.5 内碎片、外碎片与 TLB 有效访问时间

**内碎片**是已经分配出去的单元内部有空间未使用。例如 4 KiB 固定页框容纳 10 KiB 数据，要 3 页、共 12 KiB，最后有 2 KiB 未用于该数据。**外碎片**是空闲空间分散在多个不相邻区域，总量够但满足不了某次连续分配。

场景：两个不相邻的 3 KiB 空洞无法直接满足连续 5 KiB 请求，虽然空闲总量 6 KiB。分页把虚拟连续页面映射到不连续物理页框，缓解物理页框分配的外碎片问题；但仍可能有页内浪费，也不能推断整个系统所有分配器从此没有任何碎片。可变大小分配与碎片见 [OSTEP：空闲空间管理](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-freespace.pdf)。

**TLB**缓存虚拟页到物理页框的转换。计算有效访问时间 EAT 时，应先写出命中和未命中两条路径，而不是直接背固定公式。本章简单题设：TLB 查找耗 t、一次内存访问耗 m；先查 TLB 再访问内存；单级页表；无缓存重叠、无缺页。

```text
命中：TLB 查找 + 取数据 = t + m
未命中：TLB 查找 + 查页表 + 取数据 = t + 2m
EAT = h(t+m) + (1-h)(t+2m)
```

若 t=10 ns、m=100 ns、h=90%，EAT=`0.9×110+0.1×210=120 ns`。多级页表、并行查找、CPU 缓存或缺页都会改变模型；缺页成本通常远大于纳秒访存，不能偷偷塞进同一个两路径公式。TLB 基本工作见 [OSTEP：TLB](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-tlbs.pdf)。

易错边界：TLB 不命中时页表可能显示页面已在内存；有页表映射缓存失效，不代表访问无效地址。命中率 90% 是概率 0.9，不是乘以整数 90。

### 2.6 I/O：调用是否等待，与结果如何通知要分开

在本章的 OS 接口模型中，**阻塞/非阻塞**主要描述调用暂时无法推进时是否等待；**同步/异步**主要描述此次读写结果是在读写调用中取得，还是提交操作后再通过通知/完成事件取得。两组词关注不同维度，不宜只背成两组互相替代的词。

- 阻塞同步读：没有数据时在 read/recv 中等，返回时给出已读数据或错误。
- 非阻塞同步读：没有数据时立即报告“暂不可用”（例如 EAGAIN/EWOULDBLOCK）；调用方之后再尝试，并非此次读取已经完成。
- 异步 I/O：提交请求后可以处理别的工作，之后取得完成结果；完成事件与“现在有机会读取”不同。

场景：一个线程要管理大量连接，若逐个阻塞等待，会被一个暂时没数据的连接拖住；使用就绪通知配合非阻塞读，可先处理已经有数据的连接。Python 等框架中的 async/await 可能基于事件循环和非阻塞接口实现，不能仅凭语法就认定底层使用了内核的完成型异步 I/O。完成型 API 例子见 [Linux `aio(7)`](https://man7.org/linux/man-pages/man7/aio.7.html)。

**select、poll、epoll 是 I/O 多路复用的就绪通知接口**：一次监视多个文件描述符，等待哪些现在适合读/写。返回“可读”后通常仍由应用执行 recv/read；可读也可能表示到达 EOF，read 返回 0，不一定有业务正文。

| 接口 | 概念 | 不宜机械背的结论 |
|---|---|---|
| select | 用描述符集合监视就绪；通常每次调用重建/检查集合 | 常见 FD_SETSIZE 限制与实现有关，不能说任意平台无限 |
| poll | 使用描述符数组，逐项报告事件 | 不受同样位图大小限制，但仍有描述符与资源限制 |
| epoll | Linux 中维护关注集合并返回就绪事件列表 | 很多空闲连接时常有优势，不代表全部操作或所有场景严格 `O(1)` |

epoll 常见两种触发方式：LT 水平触发，在状态仍就绪时可继续报告；ET 边沿触发强调状态变化，常配合非阻塞读写持续处理到“暂不可用”，否则可能留下数据却等不到新的边沿。就绪与再次读取之间也可能被其他执行者影响，仍需处理 EAGAIN。

接口语义可核对 [select](https://man7.org/linux/man-pages/man2/select.2.html)、[poll](https://man7.org/linux/man-pages/man2/poll.2.html)、[epoll](https://man7.org/linux/man-pages/man7/epoll.7.html)。本章不要求记具体内核数据结构。

### 2.7 inode 与硬链接、软链接：删除名字不等于立即抹掉数据

Unix/Linux 文件系统中，目录项将文件名关联到 inode；inode 保存文件类型、权限、大小、数据位置等元信息。文件名主要放在目录项，不应理解成 inode 必须只保存一个文件名。

**硬链接**是多个目录项引用同一个 inode，因此修改同一文件内容时各名字都能看到，硬链接计数会增加。硬链接通常不能跨文件系统，也不能普通地给目录随意建立硬链接。

**符号链接/软链接**是一个独立文件，内容记录目标路径。它可以指向跨文件系统目标，也可以在目标不存在时存在；目标路径失效就可能成为悬空链接。它不增加目标 inode 的硬链接数。

场景：a 和 b 是同一文件的两个硬链接，s 是指向路径 a 的软链接。删除 a 后，b 仍指向原 inode，文件内容仍可通过 b 访问；s 继续找路径 a，通常失效，即使原内容还通过 b 存在。

删除目录项时硬链接数减 1；一般要等硬链接数为 0 且没有仍打开的引用，内容占用才可回收。因此一个日志文件已经从目录删除，但进程仍打开它，磁盘空间可能不会马上释放。此处是普通文件模型，权限和特殊文件另有规则。

文件与链接基本概念见 [OSTEP：文件与目录](https://pages.cs.wisc.edu/~remzi/OSTEP/file-intro.pdf)，元数据与删除语义见 [inode(7)](https://man7.org/linux/man-pages/man7/inode.7.html) 和 [unlink(2)](https://man7.org/linux/man-pages/man2/unlink.2.html)。

## 三、网络：传输约束、路径选择与浏览器行为

### 3.1 TCP 滑动窗口：既别压垮接收者，也别压垮网络

TCP 可以在等待 ACK 时继续发送一定量数据，提高利用率。窗口不是“一次只能发一个包”，而是限制尚未确认数据量等发送状态。

**流量控制**保护接收端。接收者在报文中通告接收窗口 rwnd，反映它可接受的数据空间；应用读得慢时窗口可能变小。**拥塞控制**保护网络路径。发送端依据拥塞反馈维护 cwnd，避免大量流量让路径排队、丢包严重。

简化题设下，发送窗口上限取 `min(rwnd,cwnd)`；若已有未确认数据 F，新的可发送量为 `max(0,min(rwnd,cwnd)-F)`。这只是数量计算模型，还可能受应用待发数据、MSS、调度等因素限制。不要把窗口总容量直接当作“现在还能新发多少”。

场景：服务器有很大接收缓冲区，但链路拥塞，则 cwnd 限制发送；网络畅通但接收应用卡住，则 rwnd 限制发送。某一方窗口大不能解除另一方限制。

慢启动在无丢包和相应 ACK 模型下快速增大 cwnd，经典拥塞避免更缓慢增长；超时、重复 ACK、ECN 等反馈会影响策略。真实系统算法不同，不应把所有 cwnd 曲线都硬套到某一个教学版本。接收窗口见 [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)，经典拥塞控制模型见 [RFC 5681](https://www.rfc-editor.org/rfc/rfc5681.html)。

### 3.2 重传与 TIME_WAIT：处理传输异常，不是业务重做机制

TCP 用序号和确认识别已收到的字节。缺少确认时，可能是数据丢了，也可能是 ACK 丢了或延迟较大；重传并不能证明对端从未见过原数据。接收端依据序号处理重复字节，应用仍需自己定义完整消息。

**超时重传**使用重传超时 RTO，不是所有连接都固定等待同一秒数。RTO 依据往返延迟及其变化调整，重复超时还需退避。**快速重传**的经典模型利用多个重复 ACK 提示缺失段，可在 RTO 到期前处理；具体算法和选择性确认会影响行为。定时器模型见 [RFC 6298](https://www.rfc-editor.org/rfc/rfc6298.html)，经典快速重传见 [RFC 5681](https://www.rfc-editor.org/rfc/rfc5681.html)。

TIME_WAIT 常由主动关闭并发送最后确认的一端进入，但同时关闭等情况也可能影响状态。它保留关闭状态，使最后 ACK 丢失后还能回应对方重传的 FIN，也给旧报文退出网络留出时间。经典状态机等待 2MSL，MSL 是最大报文寿命模型参数，不能把 2MSL 一律背成所有系统的某个固定秒数。

场景：A 主动关闭，收到 B 的 FIN 后最后 ACK 丢失。B 尚未确认自己的关闭，可重传 FIN；A 仍在 TIME_WAIT，可再发 ACK。这里重复 FIN 不是让应用重新执行一次付款。关闭状态机见 [RFC 9293 第 3.6 节](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.6)。

### 3.3 DNS 缓存、ARP 与路由：三种映射不同

DNS 将域名映射到相应资源记录，例如 IPv4 A 记录、IPv6 AAAA 记录；缓存可减少重复查询，但有 TTL 等有效性约束。某层缓存还有效时可能继续使用旧地址，因此更改 DNS 不代表所有客户端立即切换。DNS TTL 的基本单位是秒，见 [RFC 1035](https://www.rfc-editor.org/rfc/rfc1035.html)。

ARP 在常见 IPv4 以太网链路中解析**下一跳 IP 对应的链路地址**。若目标在同一链路，下一跳可能就是目标；若目标经网关到远端，应解析网关的 MAC，而不是向整个互联网广播查远端服务器的 MAC。IPv6 使用邻居发现等机制，不能把 ARP 当作所有 IP 版本的通则。ARP 定义见 [RFC 826](https://www.rfc-editor.org/rfc/rfc826.html)。

路由表给出目标前缀对应的下一跳或出接口。多个条目匹配时，常规转发按**最长前缀匹配**选择最具体的路由；不是按表的第一行，也不是只看前缀数值大不大。默认路由 `/0` 只有没有更具体匹配时才用于兜底，见 [RFC 1812：路由选择](https://www.rfc-editor.org/rfc/rfc1812.html#section-5.2.4.3)。

例如目标 `10.20.30.77` 同时匹配 `10.0.0.0/8、10.20.0.0/16、10.20.30.0/24`，优先 `/24`。若相同前缀有多条候选，还需路由优先级、度量或等价多路径等规则，本章计算题会给出唯一最长匹配。

易错边界：DNS 正常只说明得到了地址，不保证端口、路由或应用正常；ARP 得到了 MAC 也不代表远端业务可用。链路下一跳会变化，而最终 IP 目标与逐跳帧目标不是同一概念。

### 3.4 HTTP 缓存与条件请求：先看能否直接复用

HTTP 缓存保存响应，减少重复传输。先判断响应是否允许存储，再判断是否新鲜、是否需验证。浏览器私有缓存与代理/CDN 共享缓存的范围也不同。

| 响应控制 | 含义 | 常见误读 |
|---|---|---|
| `max-age=60` | 规定新鲜生命周期，需结合响应年龄判断 | 不是保证用户每 60 秒必定访问一次源站 |
| `no-cache` | 可存储，但复用前要按规则成功验证 | 不是“绝不能缓存” |
| `no-store` | 要求不存储相应请求/响应 | 不是只让它立即过期后仍保存 |
| `private` | 不能由共享缓存存储，私有缓存可按规则保存 | 不是自动加密内容，也不等于禁止浏览器缓存 |

过期不必下载整个响应。源站可给 `ETag` 或 `Last-Modified` 验证器，客户端随后发 `If-None-Match` 或 `If-Modified-Since`。若条件表明未修改，GET/HEAD 的典型响应为 **304 Not Modified**，没有新的正文；客户端继续使用已有缓存正文，并按响应元信息更新缓存状态。若修改了，典型返回 200 和新内容。

场景：静态脚本改版后有新 ETag，客户端需要新正文；没改的资源只传确认与元信息。对同一 URL 的不同语言、编码等响应，还可能通过 `Vary` 区分缓存键，不能只把 URL 看作唯一全部依据。

边界：题设若忽略网络传输延迟与 Age，就可把生成时刻与当前时刻作简单差；真实缓存年龄计算更复杂。`no-cache` 不等于每次必有新正文，304 不是失败；鉴权资源也不能随意放入公共共享缓存。定义见 [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html)，验证示例见 [MDN HTTP 缓存](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)。

### 3.5 Cookie 与 Session：保存凭证和保存状态不是一回事

Cookie 是浏览器按域、路径、有效期等规则保存并在匹配请求中附带的一小段数据。它可保存偏好，也可保存身份凭证；并不是所有 Cookie 都表示已登录。

在常见服务器 Session 模型中，服务端保存会话状态，浏览器只持有不可预测的 Session ID，通常放在 Cookie 中。服务端拿该 ID 查会话再判断用户身份与权限。Cookie 是传递载体，Session 是会话管理方式；某些其他架构用签名令牌，不能强行套入“所有状态都在 Session 表”的模型。

- `Secure` 限制 Cookie 经安全连接发送，常见场景是 HTTPS。
- `HttpOnly` 限制 JavaScript 直接读取该 Cookie；浏览器仍可自动在请求中附带它，不能因此断言消除了 CSRF 或全部 XSS 风险。
- `SameSite` 控制部分跨站场景下的附带规则；“站点”与 CORS 的“源”不同。
- `Domain、Path、Max-Age/Expires` 影响匹配范围与保存时间，不能把 Path 当成服务端授权边界。

场景：登录后浏览器得到会话 ID，再查询自己的报销；服务器不仅查 ID 有效，还需校验这条报销是否属于当前用户。退出登录应让服务端会话或凭证失效，不能只删浏览器 Cookie 就认为已泄露的同一凭证也被撤销。

没有显式到期时间的“会话 Cookie”与服务器“Session”也不同；浏览器可能恢复会话，不能用关浏览器代替可靠注销。Cookie 属性与会话说明见 [MDN Cookies](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies)。

### 3.6 TLS 信任链：有证书还要确认“是谁的证书”

服务端证书把服务身份与公钥联系起来，由签发者签名。客户端通常从服务端证书，经中间 CA，验证到本地信任的根；根的信任来自本地信任配置，不能仅因它自签名就自动可信。

基础校验包括证书链签名与约束、有效期、用途及服务身份是否匹配；撤销检查的具体机制和客户端策略也会影响结果。访问某个域名时，需要核对证书中相应的 subjectAltName 等身份标识，而不是只看网页展示了一个证书图标。

场景：某证书链来自受信任 CA，但证书只适用于 `a.example`，客户端访问 `b.example` 时仍可能因身份不匹配而拒绝。把证书验证或主机名验证关闭后，就失去相应的身份保护，不能再仅凭“流量加密了”认为对端可靠。

易错边界：证书公钥不应理解成每次 HTTP 内容全部直接用它逐字节加密；TLS 握手建立密钥材料，后续记录用协商的对称机制等保护。证书并不保证网页业务诚实或代码没有漏洞。

证书路径与约束见 [RFC 5280](https://www.rfc-editor.org/rfc/rfc5280.html)，现代服务身份匹配见 [RFC 9525](https://www.rfc-editor.org/rfc/rfc9525.html)。TLS 保密性与业务授权仍是两层问题。

### 3.7 同源与 CORS：是否准许浏览器脚本使用响应

同源通常要求**协议、主机、端口**相同；路径不同不造成跨源。`https://example.test/a` 与同站点的 `/b` 同源；改成 HTTP、另一个主机或不同有效端口，就可能跨源。

CORS 是 HTTP 响应头等机制，让服务器声明哪些源可被浏览器允许跨源使用响应。它不是给服务器加登录，也不是阻止所有跨源数据发送的网络防火墙。某些简单跨源请求可能已经发送到服务器，只是浏览器不允许脚本读取响应；某些请求会先预检，通过后才发送实际请求。

非简单请求常先发送 OPTIONS 预检，带上 Origin 和拟使用的方法/头。典型触发包括自定义非允许列表请求头，或 `Content-Type: application/json`；是否预检还要看完整请求是否满足允许列表规则。预检成功不代表真实请求就获得了业务对象权限。

携带浏览器凭证的 CORS 请求，需要客户端相应凭证模式，也需要服务端明确允许源与凭证。不能用 `Access-Control-Allow-Origin: *` 同时授权脚本读取凭证模式请求的响应；常见配置应返回具体允许源并设置 `Access-Control-Allow-Credentials: true`。Cookie 是否实际附带还受自身域、SameSite 和浏览器策略等限制，两个响应头并不能强制它出现。

场景：前端站点跨源调用报销 API，CORS 放行表示脚本可按规则拿到响应；API 仍必须验证用户和对象权限。非浏览器客户端不受同一浏览器 CORS 读取规则约束，因此不能把 CORS 当作服务端防越权措施。

易错边界：跨源不等于跨站；CORS 不等于 CSRF 防护；预检缓存与 HTTP 资源缓存也有不同目的。规则和示例见 [MDN CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)。

## 四、12 道原创题与详解

### SYS-01｜状态与进程通信（多选题）

题目：按本章模型，哪些说法正确？

- A. 时间片到后，仍具备运行条件的进程通常从运行进入就绪。
- B. I/O 完成后，等待该 I/O 的进程一定立刻运行，不必再调度。
- C. 共享内存中的数据对双方可见，所以并发读改写无需同步。
- D. Socket 既可用于本机进程通信，也可用于跨主机通信。

**答案：A、D。**

逐项辨析：A 被抢占的是 CPU，不是运行条件，因此回就绪；B 通常是阻塞→就绪，是否立即运行取决于调度；C 共享可见不能把读改写变成原子，仍可能丢失更新；D 套接字有本机与网络通信场景，不能限定成只能跨主机。

易错点：把“被唤醒”和“已执行完后续代码”混为一谈。知识关联：2.1 状态、2.2 IPC。

### SYS-02｜生产者消费者许可（实算与分析题）

题目：缓冲区容量 2，初始为空，使用本章的非负可用许可模型。生产者先完整放入 A、B；第三次试图生产 C，在 P(empty) 等待。随后消费者完整取走 A，再让等待的生产者完整放入 C。求初始、放入 A/B 后、最终的 `(empty,full,mutex)` 及队列。若生产者先 P(mutex) 再 P(empty)，为何危险？

**答案：初始 `(2,0,1)`；A/B 后 `(0,2,1)`、队列 `[A,B]`；最终 `(0,2,1)`、队列 `[B,C]`。**

逐步推理：每次完整生产消耗一个 empty，归还 mutex，增加一个 full。满时 C 不能取得空位，等待；消费者消耗一个 full，取 A，归还 mutex 和一个 empty，等待者随后获得该许可并放入 C。所有操作结束后容量仍被两项占满，mutex 空闲。

若先锁 mutex 再等 empty，生产者可能在满队列时持锁等待空位；消费者无法拿锁取项释放空位，就会形成等待。正确顺序是先等条件再进入临界区。

易错点：混用把阻塞者记成负数的教材模型；在许可已经被预订的中间时刻硬套 `empty+full=2`。知识关联：2.3 三个信号量的不同职责。

### SYS-03｜银行家安全序列与试分配（计算题）

题目：两类资源 A/B，Available=`(1,1)`。下表为初始状态。求 Need 和一个安全序列；若 P2 请求 `(1,0)`，试分配后是否安全、是否应批准？不安全是否说明当前已死锁？

| 进程 | Allocation | Max |
|---|---|---|
| P0 | `(1,0)` | `(2,1)` |
| P1 | `(0,1)` | `(1,2)` |
| P2 | `(1,1)` | `(3,1)` |

**答案：Need 为 `(1,1)、(1,1)、(2,0)`；序列 P0→P1→P2 安全。P2 请求满足数量约束，但试分配不安全，应暂不批准；不安全不等于已死锁。**

逐步推理：

1. 初始 Work=`(1,1)`，P0 Need 不超过 Work，假定完成，Work 加其 Allocation，变成 `(2,1)`。
2. P1 可完成，Work 变为 `(2,2)`。
3. P2 Need=`(2,0)` 满足，完成后 Work=`(3,3)`，全部完成，因此安全。
4. 试给 P2 `(1,0)` 后，Available=`(0,1)`，P2 Allocation=`(2,1)`、Need=`(1,0)`；P0/P1 Need 不变。
5. 三个进程都至少还需要 1 个 A，而 Work 中 A 为 0，没有可以保证先完成的进程，因此没有安全序列。

这是对最大需求的保证失败，不代表各进程此刻都已经发出等待请求，实际还有可能不申请全部最大量。正式银行家决策拒绝/延后该试分配，以保留安全状态。

易错点：比较 A+B 总量而不是逐项；完成时加 Max；把不安全直接写成死锁。知识关联：2.4 Need 与安全模拟。

### SYS-04｜碎片与 TLB 访问时间（计算题）

题目：数据需 10 KiB，页大小为 4 KiB，按固定页分配多少页、内部未用空间多少？两个不相邻的 3 KiB 空洞，能否满足连续 5 KiB 请求？另设 TLB=10 ns、内存=100 ns、命中率90%，单级页表串行查询、无缺页和缓存重叠，求 EAT。

**答案：3 页、内部未用 2 KiB；不能直接满足连续 5 KiB，属于外碎片现象；EAT=120 ns。**

逐步推理：向上取整 `ceil(10/4)=3`，分配 12 KiB，差额 `12-10=2 KiB` 在已分配页内；两个 3 KiB 空洞总量 6，但单个最大空洞只有 3，无法直接连续分配 5。TLB 命中路径 `10+100=110 ns`，未命中路径 `10+100+100=210 ns`，加权平均 `0.9×110+0.1×210=120 ns`。

易错点：TLB 命中后忘记读数据的内存访问；未命中时把查页表和取数据只算一次；本题不含缺页，不能额外加磁盘时间。知识关联：2.5 碎片与访存模型。

### SYS-05｜非阻塞与就绪通知（多选题）

题目：使用 Linux 的非阻塞 Socket 配合 epoll，哪些说法正确？

- A. epoll_wait 返回可读，等于已经替应用完成 recv 并拿到全部业务消息。
- B. 非阻塞 recv 在暂时无数据时可能返回 EAGAIN/EWOULDBLOCK，应用需要按状态继续处理。
- C. select 等待事件时会阻塞，所以它就是完成型异步 I/O，返回后无需再读。
- D. 边沿触发常要求将就绪数据持续处理到暂不可用，否则可能留下数据却没有新的边沿通知。

**答案：B、D。**

逐项辨析：A 就绪不等于完成，也不保留 TCP 业务消息边界；B 是非阻塞调用的正常边界之一；C “等待就绪的调用可能阻塞”不改变它是就绪通知接口这一点；D 说明 ET 的常见处理要求，实际仍需处理错误、EOF 等情况。

易错点：把“异步风格程序”与“内核完成型异步接口”视为同一件事。知识关联：2.6 阻塞、同步与多路复用。

### SYS-06｜硬链接与软链接生命周期（分析题）

题目：普通文件 a 的硬链接数为 1；创建硬链接 b 指向同一 inode，再创建符号链接 s，内容为路径 a。随后删除目录项 a。此时原 inode 的硬链接数是多少？b 和 s 分别能否读到原内容？若再删除 b，但有进程仍打开该文件，空间是否必定立即回收？

**答案：硬链接数为 1；b 可访问，s 通常悬空；仍有打开引用时不一定立即回收。**

逐步推理：创建 b 后同一 inode 有 a、b 两个名字，计数为 2；创建 s 不增加目标 inode 计数。删除 a 后只剩 b，计数 1；s 的目标是路径 a，它不会自动改指向 b。再删 b 后硬链接数为 0，但打开的文件引用仍可能保留数据，直到相应引用释放才能回收。

易错点：把软链接看成目标的另一个 inode 名字；把“目录里看不见”当作磁盘数据立即不存在。知识关联：2.7 目录项、inode 与引用。

### SYS-07｜发送窗口剩余量（计算题）

题目：简化模型中 rwnd=12000 B、cwnd=8000 B，未确认数据为3000 B，应用有足够待发数据。最多还能发送多少新的未确认字节？如果随后 rwnd 降到2000 B，而已有未确认数据仍为3000 B，此时可新发多少？

**答案：先为5000 B，后为0 B。**

逐步推理：窗口上限 `min(12000,8000)=8000 B`，减去在途3000 B，得到5000 B。后来上限为2000 B，已有在途超过上限，新的可发量按 `max(0,2000-3000)=0`。窗口变小不表示把已发出的字节从网络中撤回；需等待确认/窗口变化再推进。

易错点：把 rwnd 与 cwnd 相加，或直接把8000当成还可新发的量。知识关联：3.1 接收者流控与网络拥塞控制。

### SYS-08｜最后 ACK 丢失（单选题）

题目：A 主动正常关闭 TCP，收到 B 的 FIN 后发送最后 ACK，但 ACK 在网络中丢失。哪项正确？

- A. B 的 FIN 从不重传，因为只有业务数据才需要确认。
- B. B 可以重传未获确认的 FIN；A 在 TIME_WAIT 中可再次确认，帮助完成关闭。
- C. TIME_WAIT 永远只存在服务器端，与关闭顺序无关。
- D. 所有系统的 TIME_WAIT 都固定为120秒，协议与实现没有差别。

**答案：B。**

逐项辨析：A FIN 占序号并需要确认，未获确认时可重传；B TIME_WAIT 保留关闭状态，能够回应重复 FIN；C 客户端也可能主动关闭，角色不是判断依据；D 协议使用 2MSL 模型，具体参数与实现不能一概固定。

易错点：把重复传输控制报文理解为重新提交业务；认为关闭后立刻丢弃全部状态一定更好。知识关联：3.2 关闭确认与旧报文。

### SYS-09｜最长前缀、ARP 与 TTL（计算题）

题目：路由表如下，目标为 `10.20.30.77`，选哪条？主机 `192.168.1.10/24` 通过网关 `192.168.1.1` 向该远端发数据且 ARP 缓存为空，应查询哪个 IP 的 MAC？另在时刻0收到 TTL=120秒的 DNS 记录，忽略传输延迟，时刻50剩余多久，时刻130能否按原 TTL 继续直接复用？

| 前缀 | 下一跳标签 |
|---|---|
| `0.0.0.0/0` | R4 |
| `10.0.0.0/8` | R1 |
| `10.20.0.0/16` | R2 |
| `10.20.30.0/24` | R3 |

**答案：选 R3；ARP 查询网关 `192.168.1.1`；剩余70秒；时刻130原缓存已过期。**

逐步推理：四条都能匹配，/24 最长、最具体，优于/16、/8、/0；目标不在主机的本地 /24 链路，主机先把帧交给网关，应获取网关 MAC。DNS 缓存剩余 `120-50=70`，130超过120，不能仅依赖原 TTL 直接当作仍新鲜；后续是否获得其他缓存/新查询结果另看解析流程。

易错点：路由只用第一条；对远端 IP 广播 ARP；每次读取记录都把 TTL 重新置120。知识关联：3.3 三种映射与缓存寿命。

### SYS-10｜HTTP 新鲜与验证（追踪题）

题目：时刻0，GET响应200，正文为 v1，带 `Cache-Control: max-age=60` 和 `ETag: "v1"`。忽略 Age、网络延迟与其他缓存指令。时刻20再次请求可怎样处理？时刻80缓存过期、服务器内容未变，验证请求与响应是什么，正文从哪里来？`no-cache` 和 `no-store` 是否等价？

**答案：时刻20可直接复用新鲜缓存；时刻80可发 `If-None-Match: "v1"`，典型收到304，正文复用已有缓存；两个指令不等价。**

逐步推理：20小于新鲜生命周期60，不要求为了本题规则再下载；80超过60，可向源站验证。ETag匹配表示内容未改变，304没有新的正文，客户端使用缓存的v1并更新元信息。no-cache可存储但复用前需验证，no-store要求不存储。

易错点：把304当错误要求重新下载；把no-cache理解成完全不能保存；真实Age与时间重叠未在题设中给出时不能擅自简化。知识关联：3.4 缓存控制与条件请求。

### SYS-11｜Cookie、Session 与 TLS（多选题）

题目：哪些说法正确？

- A. Session ID 放在 HttpOnly Cookie 中，就自动防止所有 CSRF，服务端不必再检查授权。
- B. 在常见服务器 Session 模型中，Cookie可传递会话ID，服务端仍负责验证会话与对象权限。
- C. HTTPS 身份验证既要检查信任路径与相关证书约束，也要匹配客户端要访问的服务身份。
- D. 退出时仅删除本地Cookie，必定让攻击者复制的同一会话ID也立即失效。

**答案：B、C。**

逐项辨析：A HttpOnly主要限制脚本读取，浏览器仍可能附带Cookie，不能替代CSRF与授权控制；B正确，传递凭证与执行授权是不同职责；C正确，只链可信但域名不匹配也不够；D本地删除不自动撤销服务端会话，需相应失效机制。

易错点：把浏览器保存的标识当作整个服务端状态；认为任意受信CA证书都适用于任意域名。知识关联：3.5 会话、3.6 信任链与身份。

### SYS-12｜CORS 预检与授权（多选题）

题目：浏览器页面跨源发送 JSON POST，并带自定义头 X-Request-ID，使用凭证模式，且没有可用的预检缓存。哪些说法正确？

- A. 该请求通常不满足简单请求允许列表，需要先进行相应 OPTIONS 预检。
- B. 设置 `Access-Control-Allow-Origin: *` 和 `Access-Control-Allow-Credentials: true` 就能让脚本读取该凭证请求的响应。
- C. CORS放行后，API仍需认证用户并检查对象和操作权限。
- D. 任何CORS读取失败都证明服务器从未收到相关请求，更不可能发生状态变更。

**答案：A、C。**

逐项辨析：A JSON Content-Type及自定义非允许列表头是典型预检触发条件；B凭证模式下不能用通配源授权响应读取，需要明确允许源等相应配置；C浏览器读取策略不等于业务权限；D过度推广，某些简单请求可已发送但响应不能读，本题预检失败可能阻止实际请求，但不能因此推断所有CORS失败都未发出请求。

Cookie是否真的随请求发送还受自身规则和浏览器策略影响，不能只看服务端两个头。

易错点：把预检成功看成登录成功；把CORS当服务器防火墙或CSRF控制的完整替代。知识关联：3.7 源、预检、凭证与业务边界。

## 五、速记、自测与答案核对

### 5.1 考前速记

| 主题 | 完整规则 |
|---|---|
| 进程唤醒 | 阻塞事件结束通常进就绪，仍等调度 |
| IPC | 传数据与同步访问分开设计，共享内存不自动原子 |
| 生产者消费者 | empty=N、full=0、mutex=1；先等条件再拿互斥 |
| 银行家 | Need=Max-Allocation；逐资源比较；完成净回收Allocation |
| 安全状态 | 有完成序列可保证；不安全并不等于当前死锁 |
| 碎片 | 内部是已分配单元浪费；外部是空闲块分散 |
| TLB EAT | 先写命中/未命中路径，注意页表层数、串行与缺页前提 |
| I/O多路复用 | select/poll/epoll主要报告就绪，应用仍需读写 |
| 文件链接 | 硬链接共inode；软链接记路径；打开引用影响回收 |
| TCP窗口 | 上限取min(rwnd,cwnd)，再扣未确认量 |
| 重传与关闭 | RTO与延迟有关；TIME_WAIT帮助处理最后确认与旧报文 |
| DNS/ARP/路由 | 域名→地址；下一跳IP→MAC；最长前缀→下一跳 |
| HTTP缓存 | no-cache可存但需验证；no-store不存；304复用旧正文 |
| Cookie/Session | 载体与会话管理不同；删本地凭证不自动撤销服务端 |
| TLS | 链可信还要身份匹配；证书不保证业务正确 |
| CORS | 浏览器响应使用规则；凭证响应不允许通配源；仍需授权 |

### 5.2 闭卷自测

2. 不看答案重算SYS-02、SYS-03、SYS-04、SYS-07、SYS-09，并写明采用的计数/时间模型。
